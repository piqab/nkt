# NetKnownsThat

[English](README.md) | **Русский**

Смотрит на Linux-хост и отвечает на вопрос, который обычно решается
вручную полудюжиной команд: **что на самом деле слушает сеть здесь,
совпадает ли это с конфигурацией, и что сломано.**

Разбирает **nginx**, **haproxy**, **docker/compose**, **podman**, **LXD**,
**libvirt**, **iptables** и **ufw** — и сверяет прочитанное с тем, что
реально происходит на машине: вывод `ss`, счётчики пакетов, живые
контейнеры, настоящее TLS-соединение к сокету самого сервиса.
Расхождения превращаются в список проблем, связи между конфигами — в
карту ресурсов, а история проверок — в расписание доступности. И всё
это тут же чинится: редактор конфигов с валидацией и авто-откатом,
управление сервисами и контейнерами, правила firewall, выпуск и
продление сертификатов.

Один статический бинарник (~16 МБ), три интерфейса:

```
nkt          веб-панель и фоновый сбор данных
nkt tui      терминальный интерфейс для работы по SSH
nkt scan     разовая проверка, код выхода 2 при критичных находках
nkt hub      центр управления несколькими хостами
```

Никакого Python, Node, отдельных статических файлов на хосте не нужно:
веб-интерфейс встроен в бинарник.

## Запуск на хосте

**Целевая платформа — только Linux.** Продакшен-бинарник собирается для
Linux и больше нигде не запускается: попытка включить `NKT_MODE=local`
на Windows или macOS падает с понятной ошибкой, а не полурабочей
панелью.

### 1. Получить бинарник

Самый быстрый путь — готовый бинарник со страницы
[Releases](https://github.com/piqab/nkt/releases): для каждого тега
`vX.Y.Z` `.github/workflows/release.yml` собирает и публикует
статический ELF для `linux/amd64`, `linux/arm64` и `linux/arm`
(armv6+), вместе с `SHA256SUMS`.

```bash
# подставьте свою архитектуру и нужную версию
curl -fsSLO https://github.com/piqab/nkt/releases/download/v1.8.33/nkt-linux-amd64
curl -fsSLO https://github.com/piqab/nkt/releases/download/v1.8.33/SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
chmod +x nkt-linux-amd64
sudo mv nkt-linux-amd64 /usr/local/bin/nkt
```

Сборка из исходников (нужен только `make` — он сам решает, собирать
через Docker или `native-build` на голом хосте) описана в
[DEVELOPMENT.md](DEVELOPMENT.md).

### 2. Проверить, что хост читается

Перед установкой сервиса убедитесь, что приложение вообще видит
конфигурацию:

```bash
sudo nkt scan
```

Команда печатает найденные слушатели, контейнеры, правила firewall и
проблемы. Нужен root: `iptables-save` и `systemctl` недоступны обычному
пользователю.

Продакшен-режим включён по умолчанию на Linux — `NKT_MODE` задавать не
нужно. Состояние пишется в `/var/lib/netknownsthat` — туда же, куда
пишет systemd-юнит: запуск `nkt tui` вручную читает ту же базу, что
заполняет сервис, а не заводит рядом пустую.

### 3. Установка

Бинарник уже на месте (шаг 1) — осталось положить конфиг и
systemd-юнит. Клонировать репозиторий не нужно: оба файла можно
забрать прямо с GitHub:

```bash
sudo install -d -m 0750 /etc/netknownsthat
curl -fsSL https://raw.githubusercontent.com/piqab/nkt/main/deploy/nkt.env.example \
  | sudo install -m 0640 /dev/stdin /etc/netknownsthat/nkt.env
curl -fsSL https://raw.githubusercontent.com/piqab/nkt/main/deploy/netknownsthat.service \
  | sudo install -m 0644 /dev/stdin /etc/systemd/system/netknownsthat.service
sudo $EDITOR /etc/netknownsthat/nkt.env
sudo systemctl daemon-reload
sudo systemctl enable --now netknownsthat
sudo journalctl -u netknownsthat -n 30     # здесь будет пароль администратора
```

Если вы вместо этого собрали из исходников (см.
[DEVELOPMENT.md](DEVELOPMENT.md)) — `sudo make install` делает всё то
же самое, включая копирование бинарника, одной командой; существующий
`nkt.env` он не перезапишет.

Пароль администратора выводится в журнал **один раз**, при первом
запуске, и больше никогда не хранится где-либо в открытом виде. Чтобы
задать его заранее, положите `NKT_BOOTSTRAP_ADMIN_PASSWORD` в `nkt.env`
до первого старта. После этого пароли меняются командой `nkt passwd`
(см. [Учётные записи и пароли](#учётные-записи-и-пароли)).

### 4. Открыть его

По умолчанию сервис слушает `127.0.0.1:8077`. Открывать наружу
**только** через обратный прокси с TLS: `NKT_COOKIE_SECURE=true`
включён по умолчанию, и браузер просто не примет cookie сессии без
HTTPS.

Быстрый доступ без прокси — SSH-туннель:

```bash
ssh -L 8077:127.0.0.1:8077 user@host
```

Туннель отдаёт браузеру обычный HTTP, поэтому добавьте
`NKT_COOKIE_SECURE=false` в `nkt.env`, чтобы через него можно было
войти.

Третий вариант — пусть `nkt`/`nkt hub` сами отдают HTTPS, без
отдельного nginx/Caddy впереди:

```
NKT_TLS_ENABLED=true
```

При первом запуске приложение генерирует и сохраняет самоподписанный
сертификат в `NKT_DATA_DIR/tls/` (браузер один раз покажет
предупреждение «небезопасно» — придётся принять его/добавить
исключение, как с любым самоподписанным сертификатом) и переиспользует
его при следующих запусках вместо перевыпуска каждый раз. По умолчанию
сертификат покрывает `127.0.0.1`, `::1` и имя хоста этой машины —
достаточно для SSH-туннеля или локального доступа; чтобы открыть его по
другому адресу (имя в локальной сети, публичный IP VPS) без
несовпадения имени в сертификате, задайте его явно:
`NKT_TLS_HOSTS=127.0.0.1,::1,vps.example.internal`. Свой сертификат
(например, уже выпущенный) — через `NKT_TLS_CERT`/`NKT_TLS_KEY` вместо
самоподписанного.

> **Доступ к приложению равносилен root на хосте** — оно правит
> конфиги, управляет сервисами и меняет firewall. Не открывайте его в
> интернет без отдельного слоя аутентификации.

## Запуск хаба в Docker

Готовый образ (`Dockerfile.hub`) публикуется
`.github/workflows/release.yml` для каждого тега `vX.Y.Z` в
`ghcr.io/piqab/nkt-hub` — его можно развернуть без клонирования
репозитория, `docker login` не нужен.

### Docker Compose

```bash
curl -fsSLO https://raw.githubusercontent.com/piqab/nkt/main/deploy/docker-compose.hub.release.yml
docker compose -f docker-compose.hub.release.yml up -d
docker compose -f docker-compose.hub.release.yml logs hub    # пароль администратора
```

Сборка из исходников тем же `docker compose`, но локально (`make hub`),
использует `deploy/docker-compose.hub.yml` — подробнее про сам хаб в
[разделе ниже](#хаб-много-хостов-из-одного-места).

### Kubernetes

Манифест — [deploy/k8s/hub.yaml](deploy/k8s/hub.yaml): `Namespace`,
`PersistentVolumeClaim` для базы хаба, `Deployment` (**строго одна
реплика** — хаб хранит реестр хостов в SQLite на томе ReadWriteOnce и
генерирует собственный ключ шифрования при первом старте; второй под,
делящий тот же том, не сможет с этим согласоваться) и `Service` на
порту 8077.

```bash
kubectl apply -f deploy/k8s/hub.yaml
kubectl logs -n netknownsthat deploy/nkt-hub       # пароль администратора
kubectl port-forward -n netknownsthat svc/nkt-hub 8443:8077
```

Доступ извне кластера идёт через свой Ingress с TLS перед этим
`Service` (намеренно не включён в манифест — у каждого кластера свой
контроллер). Резервный канал (см.
[Хаб, пункт 5](#хаб-много-хостов-из-одного-места)) не требует отдельной
настройки Ingress/сети — хаб сам дозванивается из пода до каждого
хоста, обычным исходящим трафиком.

## Сначала попробовать локально

Самый быстрый способ увидеть рабочий продукт — режим `fixtures`. Он не
читает ваш компьютер — он читает **снапшот** реального продакшен-сервера
из каталога `fixtures/host`, намеренно засеянный проблемами. Работает на
Windows, macOS и Linux, ничего не требует от системы и ничего в ней не
трогает.

```bash
make build-dev        # нативный бинарник под вашу ОС
./nkt                 # на Windows: .\nkt.exe
```

Этот режим сам включается на Windows и macOS. Если пробуете **на
Linux**, задайте его явно, иначе приложение попытается читать реальный
хост:

```bash
NKT_MODE=fixtures ./nkt
```

Пароль администратора при первом запуске печатается в консоль.
Откройте <http://127.0.0.1:8077> — панель сразу показывает 25 находок:
Redis, открытый всему миру, конфликт порта 8443, контейнер, застрявший
в цикле перезапуска, панель haproxy без пароля, просроченный TLS.

**О синтетических данных.** Сокеты, описанные в снапшоте, не существуют
на вашей машине, а его счётчики заморожены — поэтому пробы и метрики
симулируются, и при первом запуске один раз засеивается 14 дней
истории. Интерфейс сообщает об этом баннером, API возвращает
`"simulated": true`, отключить можно через `NKT_DEMO_BACKFILL=false`. В
продакшен-режиме всё измеряется по-настоящему.

Если хочется настоящих nginx, haproxy и docker вместо снапшота, есть
[проверочный стенд](DEVELOPMENT.md#проверочный-стенд) на docker
compose.

## Терминальный интерфейс

Если вы уже на хосте по SSH, браузер и проброс порта — лишний шаг,
который не нужен:

```bash
sudo nkt tui
```

Те же данные и те же действия, что и в веб-интерфейсе. Экраны
переключаются цифрами `1`…`9`, `0` или `Tab`:

| Экран | Что показывает и делает |
|---|---|
| Обзор | плитки статуса, список проблем, сервисы, firewall, доступность |
| Находки | таблица находок с деталями; `f` фильтрует по серьёзности |
| Карта | дерево «внешняя сеть → слушатель → пул → бэкенд → контейнер → сеть» |
| Доступность | тепловая карта простоев по часам недели, графики, список сбоев; `p` проверяет сейчас, `space` ставит на паузу |
| Нагрузка | тренды, рейтинг главных потребителей, расписание использования; `m` переключает метрику |
| Конфигурации | просмотр и редактирование; `e` редактор, `v` история версий, `u` откат |
| Сервисы | systemd, docker/podman, LXD, libvirt; `s` `x` `t` `l` — старт, стоп, рестарт, релоад; `c` проверка конфига |
| Firewall | правила ufw и пакетный фильтр; `a` добавить, `x` удалить |
| Сертификаты | истечение, расписание истечения, автопродление, сверка с сокетом; `Enter` показывает файл, `r` продлевает, `g` самоподписанный, `c` собирает PEM для haproxy |
| Журнал | каждое изменение — с пользователем и результатом |

Общие клавиши: `F5` обновить, `r` пересканировать хост, `?` помощь, `q`
выход. В редакторе `Ctrl+S` сохраняет — с той же серверной валидацией и
авто-откатом при ошибке, что и в веб-интерфейсе.

Две вещи, которые стоит знать заранее:

* **TUI не собирает историю.** Пробы, метрики и разбор логов делает
  фоновый планировщик — то есть запущенный сервис `netknownsthat`.
  Терминал читает ту же базу; без сервиса экраны доступности и нагрузки
  будут пустыми. Разовая проверка ресурса — клавиша `p`.
* **Входа по паролю нет.** Если вы на хосте — вы уже root. Действия
  логируются под именем `tui:<логин>`, а под `sudo` записывается
  исходный пользователь, а не `root`. Ограничение
  `NKT_ALLOW_MUTATIONS=false` действует и здесь.

## Хаб: много хостов из одного места

Обычный `nkt` управляет одним хостом. `nkt hub` — тот же бинарник в
другом режиме: он разворачивается на отдельном VPS и управляет
остальными **по SSH**, показывая для каждого ту же панель, что показал
бы обычный `nkt` — просто с выбором хоста в интерфейсе вместо отдельного
развёртывания на каждый.

```bash
make hub                # в Docker: docker compose -f deploy/docker-compose.hub.yml up -d --build
```

Без Docker хаб сам кросс-компилирует бинарник `nkt` для каждого вновь
добавленного хоста — для этого на машине, где работает хаб, нужны
исходники самого репозитория, а не только бинарник `nkt`:

```bash
git clone https://github.com/piqab/nkt.git /opt/netknownsthat
cd /opt/netknownsthat
make build
sudo make hub-install
```

`deploy/hub.env.example` (копируется в `/etc/netknownsthat/hub.env`
при первой установке) уже указывает `NKT_HUB_SOURCE_ROOT` на
`/opt/netknownsthat` — держите клон именно там. Он лежит вне
`StateDirectory` systemd-юнита, поэтому не зависит от каталога данных
хаба; обновляйте его вместе с самим хабом (`git pull && make build &&
sudo make hub-install`). Если установка хоста падает с ошибкой
«исходники nkt не найдены», значит `NKT_HUB_SOURCE_ROOT` в `hub.env`
не задан или указывает на каталог без `go.mod` — пропишите
абсолютный путь к клону и выполните
`systemctl restart netknownsthat-hub`.

Пароль администратора генерируется при первом старте и печатается в
лог — как и у обычного `nkt`.

Дальше на странице «Хосты» вводится имя, адрес и SSH-пользователь, а
сам хаб:

1. подключается по SSH и определяет архитектуру (`uname`);
2. собирает под неё бинарник `nkt` — кросс-компиляция кешируется, так
   что второй хост той же архитектуры разворачивается без пересборки;
3. загружает бинарник, systemd-юнит и сгенерированный `nkt.env` по
   SFTP;
4. поднимает `nkt` как обычный systemd-сервис — точно тот же `deploy/`,
   что и при ручной установке;
5. входит с сгенерированной учётной записью администратора через
   SSH-туннель и запоминает её, зашифрованно, чтобы с этого момента
   проксировать запросы к API этого хоста без повторного входа.

По умолчанию хаб **сам генерирует пару ключей** для каждого хоста: вы
только вставляете публичную половину в `authorized_keys`, приватная
половина никогда не покидает хаб. Свой уже существующий ключ или
пароль остаются запасным вариантом.

Что ещё умеет хаб, кроме проксирования:

* **сканирует машину, на которой сам работает** — строка «localhost»
  закреплена первой в таблице «Хосты», без установки и без SSH (см.
  HUB.md, раздел 4); требует, чтобы сам хаб работал с тем же профилем
  привилегий (root + capabilities), что и обычный `nkt`, а не в
  изолированном `DynamicUser`;
* **старт/стоп `nkt`** на одном хосте или на всех сразу;
* **веб-терминал** — чекбокс на хосте включает полноценную root-оболочку
  в браузере; изменение чекбокса сразу переустанавливает `nkt` на
  хосте, чтобы настройка реально вступила в силу;
* **резервный канал на случай недоступности SSH** — включён по
  умолчанию для новых хостов: хаб открывает на самом хосте ещё один
  порт (по умолчанию `8078`) и сам дозванивается в него — используя тот
  же адрес хоста, что и SSH, поэтому не нужно настраивать отдельный
  адрес для хаба, даже если сам хаб сидит в приватной сети без
  публичного адреса. Если что-то блокирует входящие не целиком, а
  именно на порту 22 хоста (упавший или неправильно настроенный sshd,
  протухшие учётные данные), панель, терминал и «обновить»/
  «переустановить» продолжают работать через этот канал; если firewall
  блокирует входящие целиком, резервный канал идёт в том же
  направлении, что и SSH, и упирается в ту же блокировку. Хаб всегда
  сначала пробует обычный SSH, переключаясь на этот канал только если
  дозвон не удался — кроме самой первой установки хоста, для которой
  всегда нужен настоящий SSH. Таблица хостов показывает бейдж,
  подключён ли канал и используется ли он прямо сейчас — см. HUB.md,
  раздел 5;
* **обновления пакетов ОС** — живой `apt-get upgrade` в окне терминала,
  намеренно без `-y`: подтверждение `[Y/n]` даёте сами, глядя на
  реальный вывод. Процесс переживает закрытие окна, вместо того чтобы
  оборвать транзакцию dpkg на середине;
* **экспорт и импорт конфигурации** — реестр хостов со всеми секретами,
  опционально вместе с мастер-ключом, чтобы секреты расшифровывались
  сами при переезде на новый VPS (перешифровываются ключом нового хаба
  при импорте).

Сеть между хабом и управляемыми хостами наружу не выставляется — виден
только тот порт хаба, который вы сами решили опубликовать.

Известные ограничения:

* SSH-секреты хранятся на хабе, зашифрованные мастер-ключом
  (`NKT_HUB_MASTER_KEY` — генерируется при первом старте и хранится в
  томе данных, если не задан явно). Хаб — единая точка доступа ко всем
  управляемым хостам: относитесь к нему как к любой машине с
  продакшен-доступом. `sudo nkt hub delete` необратимо стирает этот
  ключ и всю базу целиком (с обязательным предложением сначала
  сохранить экспорт с ключом — и зашифровать сам файл экспорта паролем
  — для восстановления через `nkt hub import`) — см. HUB.md, «Остановка
  / удаление».
* Ключ SSH-хоста принимается при первом подключении без сверки с
  `known_hosts` — та же модель доверия при первом использовании, что и
  у интерактивного `ssh`.
* Управляющие операции идут через SSH-туннель к собственному API
  хоста, который полностью применяет свои правила (`NKT_ALLOW_MUTATIONS`,
  роль пользователя); хаб их не переопределяет.

**Пошаговый запуск, добавление первого хоста и решение проблем —
[HUB.md](HUB.md).**

## Что находит

Конфиги не просто читаются — они сверяются друг с другом и с реальным
состоянием хоста. Каждая находка включает объяснение, ссылку на файл и
строку, и конкретное действие для исправления.

**Сеть и firewall**

| Правило | Серьёзность | Что находит |
|---|---|---|
| `port-conflict` | высокая | Два сервиса объявляют один и тот же порт на пересекающихся адресах |
| `declared-not-listening` | высокая | Порт описан в конфиге, но ничего его не слушает |
| `listening-not-declared` | средняя/инфо | Процесс слушает порт, не описанный ни в одном конфиге |
| `no-default-deny` | высокая | Политика INPUT — ACCEPT, а ufw выключен |
| `public-port-blocked` | средняя | Сервис слушает 0.0.0.0, но firewall его блокирует |
| `docker-bypasses-firewall` | критическая/высокая | Контейнер публикует порт на 0.0.0.0 — DNAT обходит INPUT и ufw |
| `stale-firewall-rule` | низкая | Правило разрешает порт, который никто не слушает |
| `sensitive-port-public` | критическая/высокая | Redis, PostgreSQL, MongoDB и подобные слушают все интерфейсы |

**TLS и сертификаты**

| Правило | Серьёзность | Что находит |
|---|---|---|
| `weak-tls` | средняя | TLSv1 / TLSv1.1 оставлены в `ssl_protocols` |
| `missing-hsts` | низкая | TLS-сервер не отправляет Strict-Transport-Security |
| `tls-cert-missing` | высокая | `listen ... ssl` без `ssl_certificate` |
| `tls-cert-expired` / `-expiring` | критическая / высокая-средняя | Просрочен, либо истекает через 7–30 дней |
| `tls-cert-not-yet-valid` | высокая | Ещё не действителен — обычно неверные часы на хосте |
| `tls-cert-unreadable` | высокая | Файл, на который указывает конфиг, не читается |
| `tls-cert-name-mismatch` | высокая | Сертификат не покрывает имя, которым отвечает сервер |
| `tls-cert-renewal-not-automatic` | средняя | certbot знает о сертификате, но ни таймер, ни cron его не продлят |
| `tls-cert-orphan-lineage` | высокая | Лежит в `/etc/letsencrypt/live`, но конфига продления нет |
| `tls-cert-self-signed` / `-weak-key` / `-weak-signature` | низкая / средняя | Самоподписанный, RSA короче 2048, или подпись SHA-1/MD5 |
| `tls-cert-not-reloaded` | высокая | Сокет отдаёт другой сертификат, чем указан в конфиге — сервис не перечитал файл |
| `public-plaintext-proxy` | средняя | Публичный HTTP-слушатель проксирует трафик без шифрования |

**Пулы и контейнеры**

| Правило | Серьёзность | Что находит |
|---|---|---|
| `upstream-undefined` / `-orphan` | высокая / низкая | Маршрут ссылается на несуществующий пул; пул объявлен, но нигде не используется |
| `upstream-member-down` | высокая | Локальный бэкенд пула не слушает свой порт |
| `all-backends-disabled` | критическая | Все серверы в пуле помечены down/backup |
| `single-backend` / `backend-no-healthcheck` | инфо / средняя | Нет избыточности; нет health-check при нескольких серверах |
| `container-restarting` | высокая | Контейнер застрял в цикле перезапуска |
| `container-not-running` / `-undeclared` / `-no-restart-policy` | средняя / низкая / низкая | Объявлен, но не запущен; запущен, но не объявлен; нет политики перезапуска |
| `admin-interface-open` | высокая/средняя | Панель статистики haproxy доступна без пароля |

### Карта ресурсов

Граф, где трафик читается слева направо:

```
внешняя сеть → сервис → слушатель → пул → адрес бэкенда → контейнер → docker-сеть
```

Связи берутся из конфигов (`proxy_pass`, `upstream`, `use_backend`,
`default_backend`, опубликованные порты); состояние узлов — из реальных
слушателей, состояний контейнеров и находок. Раскладка по колонкам, а
не силовая (force-directed): карта остаётся стабильной между сканами и
читается как диаграмма потока запросов. Терминальный интерфейс
показывает ту же карту в виде дерева.

### Доступность и нагрузка

**Доступность.** Каждый объявленный слушатель и каждый бэкенд пула
проверяется по расписанию — TCP-соединение или HTTP-запрос с верным
заголовком `Host`. История превращается в тепловую карту «час недели ×
простой», графики доступности и задержки, список сбоев.

**Нагрузка.** Приращения счётчиков iptables, `docker stats` и разбор
логов доступа nginx/haproxy. Записи логов сортируются по собственной
временной метке записи, поэтому график показывает, когда нагрузка
реально была, а не когда её собрали.

### Сертификаты: не только даты истечения

Пути берутся из `ssl_certificate` в nginx и `crt` в haproxy; файлы
разбираются как X.509: дата истечения, покрываемые имена, издатель,
алгоритм и длина ключа, самоподписанный или нет. `crt` у haproxy может
указывать на каталог — он разворачивается в список отдельных
сертификатов по SNI.

Но просроченный сертификат почти никогда не забывчивость — это
**сломанная автоматизация** — поэтому само продление проверяется
отдельно: знает ли certbot об этом сертификате, активен ли
`certbot.timer` или задача cron, и является ли файл производной копией
для haproxy (certbot не пишет напрямую в haproxy — deploy-хук склеивает
`fullchain.pem`+`privkey.pem` в отдельный файл, который может нигде не
упоминаться в конфиге; такие копии находятся сверкой SHA-256-отпечатков
и наследуют статус оригинала вместо ложного «ручной»).

Чинится прямо здесь, из интерфейса:

* **продлить** существующую линейку — всегда через `--standalone`
  (сохранённый аутентификатор оказался слишком хрупким — сломанный
  webroot падает с голым «code 1»), останавливая nginx/haproxy перед
  этим и гарантируя, что они запустятся снова после, независимо от
  результата продления; перед вызовом проверяется, свободен ли порт 80,
  поэтому ошибка называет блокирующий процесс, а не голое «Problem
  binding to port 80»;
* **выпустить новый** сертификат Let's Encrypt для домена, о котором
  certbot ещё не знает (без формы wildcard — `--standalone` доказывает
  владение только точным именем);
* **собрать PEM для haproxy** из уже выпущенной линейки — перезаписывая
  конкретный файл и делая `reload`, либо записывая в каталог `bind ...
  crt`, если он настроен;
* **самоподписанный** сертификат, когда TLS вообще не настроен: RSA
  2048/3072/4096, несколько имён, включая wildcard и юникод
  (`испытание.рф` → punycode автоматически).

Всё это занимает минуты (обращение к Let's Encrypt, остановка сервисов),
поэтому кнопка не блокирует интерфейс спиннером: операция уходит на
сервер в фоне, а окно показывает живой построчный лог. Окно можно
закрыть — на хосте ничего не остановится.

Автопродление (`NKT_AUTO_RENEW_CERTS=true`) делает то же самое по
расписанию. Учтите: это значит, что фоновая задача при каждом продлении
ненадолго останавливает сайт сама, без участия человека.

**Сверка с реальным сокетом.** Файл на диске может быть здоровым — и
всё равно не тем, что реально видят клиенты: `certbot renew` подменил
файл, но сервис так и не сделал `reload` и продолжает отдавать старый
сертификат из памяти. Разница не видна нигде, кроме самого
TLS-соединения, поэтому при каждом скане реального хоста приложение
**открывает настоящее TLS-соединение** к первому известному адресу
каждого сертификата, с соответствующим SNI, и сравнивает отпечатки.
Ошибка соединения не считается несовпадением — она помечается «не
проверено», чтобы сетевая проблема не превращалась в ложное обвинение
сервиса.

### Управление

* **systemd**: `start` / `stop` / `restart` / `reload`, валидация
  конфига.
* **docker** и **Podman**: жизненный цикл контейнера, создание и
  удаление — через Engine API и собственный unix-сокет соответственно,
  на отдельных страницах.
* **LXD**: контейнеры и виртуальные машины одним инструментом
  (`lxc list --format json`), включая `lxc launch` и удаление.
* **libvirt/QEMU**: жизненный цикл VM через `virsh`, переключатель
  автостарта, удаление определения (диски — отдельно). Создание и
  редактирование VM намеренно не получили отдельного API: домен
  описывается через тот же редактор конфигов — путь
  `/etc/libvirt/qemu/<name>.xml` распознаётся автоматически, XML
  проверяется `virt-xml-validate`, а сохранение с флагом «применить»
  регистрирует домен через `virsh define`.
* **Конфигурации**: редактор с версионированием. Перед записью
  содержимое проверяется самим сервисом (`nginx -t`, `haproxy -c -f`,
  `docker compose config -q`); **если валидация не прошла, файл
  автоматически возвращается в прежнее состояние**. Любую версию можно
  посмотреть, сравнить (unified diff) и откатиться к ней.
* **firewall**: добавление и удаление правил через `ufw`.
  Редактирование iptables напрямую из интерфейса намеренно не
  поддерживается.
* **Веб-терминал** (`NKT_TERMINAL_ENABLED=true`): полноценная
  интерактивная оболочка на хосте прямо в браузере. По умолчанию
  выключен — это прямой доступ к shell, а не ограниченное действие.
* **Обновления пакетов ОС**: живой `apt-get update && apt-get upgrade`
  в окне терминала, намеренно без `-y`.

Каждое изменение логируется вместе с пользователем, результатом и
выводом команды.

## Учётные записи и пароли

Пароли хранятся только в собственной базе приложения (`argon2id`,
необратимо) — восстановить «текущий» пароль неоткуда, даже напрямую из
базы. Сброс всегда идёт через выпуск нового.

```bash
sudo nkt passwd                      # сменить пароль администратора
sudo nkt passwd ops -role viewer     # создать учётку только для чтения
sudo nkt passwd -random              # сгенерировать пароль вместо ввода
sudo nkt users                       # кто есть, кто когда входил, кто отключён
echo 'new-password' | sudo nkt passwd ops    # неинтерактивно, для скриптов
```

`nkt passwd` устанавливает пароль прямо в базе, без входа в
существующую сессию — этим же лечится «забыл пароль и не могу войти».

Из веб-интерфейса: кнопка «Сменить пароль» внизу боковой панели (после
смены все сессии этой учётки завершаются, включая текущую), и страница
«Пользователи» для `admin` — создание, смена роли, отключение,
удаление. Страница не может сбросить чужой забытый пароль — только
`sudo nkt passwd <логин>` на хосте. Понизить, отключить или удалить
собственную учётку нельзя — это исключает случайную потерю доступа.
Минимальная длина пароля везде — 10 символов.

Каждая смена пароля и создание учётки логируются с меткой `cli:<логин
на хосте>`.

## Конфигурация

Каждая настройка — переменная окружения `NKT_*`; полный список с
пояснениями — в [deploy/nkt.env.example](deploy/nkt.env.example).
Главное:

| Переменная | Значение |
|---|---|
| `NKT_MODE` | `local` — читать реальный хост, `fixtures` — снапшот. По умолчанию `local` на Linux, `fixtures` везде остальном |
| `NKT_DATA_DIR` | Где хранить базу и историю конфигов. По умолчанию `/var/lib/netknownsthat` в `local`, `./data` в `fixtures` |
| `NKT_ADDR` | Адрес прослушивания, по умолчанию `127.0.0.1:8077` |
| `NKT_ALLOW_MUTATIONS` | `false` переводит всё приложение в режим только для чтения |
| `NKT_COOKIE_SECURE` | по умолчанию `true` (cookie ходит только по HTTPS); `false` для обычного HTTP, например SSH-туннеля |
| `NKT_TLS_ENABLED` | `true` — отдавать HTTPS самому вместо обычного HTTP (см. [Открыть его](#4-открыть-его)), с самоподписанным сертификатом, если не заданы `NKT_TLS_CERT`/`NKT_TLS_KEY`. По умолчанию `false` |
| `NKT_TLS_HOSTS` | Какие имена/IP должен покрывать сгенерированный самоподписанный сертификат. По умолчанию `127.0.0.1,::1,<hostname>` |
| `NKT_TLS_CERT`, `NKT_TLS_KEY` | Свой сертификат/ключ вместо самоподписанного — оба должны быть заданы вместе |
| `NKT_COMPOSE_FILES` | Список compose-файлов через запятую |
| `NKT_PODMAN_SOCKET` | Сокет Podman, по умолчанию `/run/podman/podman.sock` |
| `NKT_LIBVIRT_URI` | URI подключения к libvirt, по умолчанию `qemu:///system` |
| `NKT_PROBE_INTERVAL` | Как часто проверять доступность; голое число — секунды |
| `NKT_AUTO_RENEW_CERTS` | `true` — продлевает сертификаты certbot по расписанию (`NKT_AUTO_RENEW_INTERVAL`, по умолчанию 6ч) не позже чем за `NKT_AUTO_RENEW_WITHIN` (30 дней) до истечения. По умолчанию `false` |
| `NKT_CERTBOT_TIMEOUT` | Сколько ждать `certbot renew` — отдельно от `NKT_COMMAND_TIMEOUT`, поскольку это сетевой вызов к Let's Encrypt, а не быстрая команда. По умолчанию `3m` |
| `NKT_TERMINAL_ENABLED` | `true` включает веб-терминал — полноценную оболочку на хосте в браузере, поверх уже обязательной роли admin и `NKT_ALLOW_MUTATIONS=true`. По умолчанию `false` для обычного `nkt` и для управляемых хабом хостов (отдельный чекбокс на хост — см. HUB.md); по умолчанию `true` для самого хаба (`NKT_MODE=hub`) — это тот же терминал для строки «localhost», то есть той же машины, на которой уже работает хаб, так что это не дополнительный доступ |
| `NKT_TERMINAL_IDLE_TIMEOUT` | Закрыть терминал после этого времени без ввода/вывода — забытая вкладка не держит оболочку открытой вечно. По умолчанию `30m` |

## Безопасность

* Пароли — argon2id (64 МиБ, t=3, p=2). Сессии — случайные, отзываемые
  токены в SQLite; cookie — `HttpOnly`, `SameSite=Lax`. После пяти
  неудачных попыток вход блокируется с нарастающей задержкой.
* Роли: `viewer` — только чтение, `admin` — изменения. Плюс глобальный
  рубильник `NKT_ALLOW_MUTATIONS=false`.
* Редактирование конфигов ограничено списком разрешённых каталогов
  (корни nginx и haproxy, перечисленные compose-файлы,
  `/etc/libvirt/qemu`). Пути с `..` отклоняются.
* Действия над сервисами и firewall принимают значения только из
  фиксированных списков — имя сервиса или действие нельзя подставить в
  команду.
* Удаление правила ufw сверяется с точным текстом, который видел
  оператор: номера смещаются после каждого изменения, а удаление
  «не того» правила может отрезать SSH.
* Оптимистичная блокировка при сохранении конфига, по SHA-256: файл,
  изменившийся на диске после открытия в редакторе, не будет молча
  перезаписан.
* Каждое изменяющее действие логируется в `audit_log`.
* systemd-юнит в `deploy/` сужает привилегии: `ProtectSystem=strict` с
  явным списком доступных на запись каталогов, урезанный
  `CapabilityBoundingSet`, `SystemCallFilter=@system-service`.

  **Веб-терминал, обновления пакетов ОС и самообновление по резервному
  каналу — единственное намеренное исключение.** Они выполняются через
  `systemd-run --pty` в отдельном, полностью неограниченном
  transient-юните, а не как дочерние процессы самого `nkt`: иначе
  интерактивная root-оболочка, или собственный сброс привилегий
  `apt-get` (setuid/setgid в `_apt`), упёрлись бы в те же ограничения,
  что защищают демон. Собственные ограничения демона существуют, чтобы
  ограничить радиус поражения при компрометации **его самого**, а не
  действий уже аутентифицированного администратора, явно запросившего
  root-доступ. Это срабатывает только когда `nkt` реально запущен как
  юнит (`INVOCATION_ID` есть в окружении) и `systemd-run` есть в PATH.

  Самому `systemd-run` нужен живой D-Bus/systemd-manager — на хосте без
  него (некоторые минимальные образы, например Debian 11, не ставят
  dbus по умолчанию) это падает с ошибкой соединения с шиной. Запасной
  путь — `CAP_SYS_ADMIN` в `CapabilityBoundingSet` юнита и
  `nsenter --mount` прямо в пространство имён PID 1, вообще без D-Bus;
  `RestrictNamespaces` сужен ровно до `mnt`, ничего шире не разрешено
  даже с этой capability. Страница «Терминал» сообщает, если недоступен
  ни один из путей, и предлагает кнопку установки dbus всякий раз, когда
  сработал бы путь через `nsenter`.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| Страница «frontend не собран» | Бинарник собран раньше UI. Выполните `npm run build`, затем `go build` **заново**: `go:embed` запекает файлы во время компиляции |
| `production mode only works on Linux` | Продакшен-режим не работает на Windows или macOS. Для разработки используйте `NKT_MODE=fixtures` |
| `snapshot directory ... not found` | Включён `fixtures`, но рядом нет каталога с образцами. Продакшен-хосту нужен `local` (он уже по умолчанию на Linux — значит, переменная где-то задана явно). Для разработки запускайте из корня репозитория или задайте `NKT_FIXTURES_ROOT` |
| `could not create data directory /var/lib/netknownsthat` | Запущено не от root. Либо `sudo`, либо укажите `NKT_DATA_DIR` в своё место |
| `failed to connect to the docker API` | Docker не запущен |
| Источники `firewall` и `services` недоступны | Нужен root: `iptables-save` и `systemctl` не работают для обычного пользователя. Запускайте через systemd-юнит из `deploy/` |
| Забыт пароль | `sudo nkt passwd`. В крайнем случае — остановить сервис и удалить `/var/lib/netknownsthat/netknownsthat.db` |
| `bind: address already in use` | Порт занят, задайте другой через `NKT_ADDR` |
| Правки конфига отклоняются с `Read-only file system` | Каталог смонтирован только для чтения, либо нет доступа на запись в каталог логов, который открывает `nginx -t` |
| Кнопки отключены, изменения отклоняются | Либо роль `viewer`, либо `NKT_ALLOW_MUTATIONS=false` |
| Нечитаемые символы в консоли Windows | Кодовая страница не UTF-8: выполните `chcp 65001` |
| Нативная сборка фронтенда сломалась после `make build` | `make web` ставит зависимости внутри Linux-контейнера поверх того же каталога, заполняя `node_modules` линуксовыми сборками. Выполните `npm install` заново внутри `web/` |

Решение проблем с хабом — в отдельном разделе [HUB.md](HUB.md).

## Ограничения

* Каждый `nkt` управляет одним хостом: своя карта, свои конфиги, своя
  база. Несколько хостов из одного места — только через хаб, проксируя
  к каждому отдельно, а не общей моделью данных.
* Пишутся только правила `ufw`; редактирование iptables напрямую
  намеренно не поддерживается. Поддерживаемые бэкенды — iptables/
  ip6tables и ufw — чистый `nftables` (без слоя iptables-nft) не
  разбирается.
* Правилу `declared-not-listening` нужен доступный `ss`. Оно молчит,
  если таблица сокетов не подтверждает ни одного объявленного порта —
  это значит, что читается другое сетевое пространство имён.
  Опубликованные порты контейнеров это правило вообще не проверяет: при
  `userland-proxy: false` docker пробрасывает их обычным DNAT, и на
  хосте вообще не существует слушателя.
* Валидация конфигов в режиме `fixtures` всегда «проходит успешно» —
  путь отказа тестируется на проверочном стенде или на реальном хосте.
* Поддерживаемые веб-серверы и балансировщики — nginx и haproxy. Caddy,
  Traefik, Envoy потребовали бы нового файла в `internal/parse`.
* Из инструментов виртуализации: классический LXC (`lxc-ls`/`lxc-info`,
  без JSON) не поддерживается — только LXD. Podman Quadlet не
  разбирается — виден только список работающих контейнеров.
* Сверка «что реально отдаёт сокет» — это одно TLS-соединение на
  сертификат, к его первому известному адресу. Если несколько
  сертификатов мультиплексируются по SNI на одном порту, проверяется
  только первый (`Sites[0]`). В режиме `fixtures` не выполняется вовсе.
* Самоподписанный сертификат не убирает предупреждение браузера — это
  временное решение для внутренних и тестовых сервисов. Приложение не
  правит конфиг автоматически: директивы нужно вставить руками через
  редактор, где правка проходит ту же валидацию сервиса с авто-откатом.
* Обновления пакетов ОС поддерживаются только для Debian/Ubuntu
  (`apt-get`).
