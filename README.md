# NetKnownsThat

Приложение для одного Linux-хоста: разбирает конфигурации **nginx**, **haproxy**,
**docker/compose**, **iptables** и **ufw**, сопоставляет их с тем, что реально
происходит на машине, строит **карту сетевых ресурсов**, ведёт **расписание
доступности и использования** и даёт **дашборд для управления** сервисами,
конфигами и правилами firewall.

Один статический бинарник (~16 МБ) с тремя интерфейсами:

```
nkt          веб-дашборд и фоновый сбор данных
nkt tui      терминальный интерфейс для работы по SSH
nkt scan     разовая проверка, код возврата 2 при критичных находках
```

На хосте не нужны ни Python, ни Node, ни отдельные статические файлы: веб-интерфейс
вшит в бинарник.

---

# 1. Запуск и развёртывание

**Целевая платформа — только Linux.** Продакшен-бинарник собирается в
Linux-окружении и нигде больше. Windows и macOS годятся только как рабочие
машины для разработки в режиме снапшота; попытка запустить там `NKT_MODE=local`
завершится понятной ошибкой, а не наполовину работающим дашбордом.

## 1.1. Команды сборки

Всё собирается через `make`. Список целей всегда под рукой: `make` без
аргументов печатает его сам.

| Команда | Что делает |
|---|---|
| `make build` | **Основная цель.** Собирает продакшен-бинарник: сначала веб-интерфейс в контейнере `node:22-alpine`, затем `go build` в контейнере `golang:1.26-alpine` с `CGO_ENABLED=0 GOOS=linux`. Результат — `dist/nkt`, статический ELF ~16 МБ. Версия берётся из `git describe`. Для другой архитектуры: `make build GOARCH=arm64`. |
| `make web` | Только веб-интерфейс: `npm ci && npm run build` в контейнере. Кладёт результат в `internal/webui/dist`, откуда его вшивает `go:embed`. Отдельно нужен редко — `make build` вызывает эту цель сам. |
| `make build-dev` | Нативный бинарник для текущей ОС (`./nkt` или `nkt.exe`) без контейнеров. **Только для разработки в режиме снапшота** — в продакшен такой артефакт не отправляют. |
| `make test` | `go test ./...` и проверка типов фронтенда. |
| `make check` | То же плюс `go vet` и проверка форматирования; падает, если хоть один файл не прошёл `gofmt`. Это то, что стоит гонять перед коммитом. |
| `make stand` | Поднимает проверочный стенд с настоящими nginx, haproxy и docker — см. 1.4. |
| `make stand-down` | Останавливает стенд и удаляет его тома. |
| `make install` | Ставит на **этот** Linux-хост: бинарник в `/usr/local/bin`, unit в systemd, пример конфигурации в `/etc/netknownsthat`. Существующий `nkt.env` не перезаписывает. На не-Linux отказывается работать. Требует готового `dist/nkt`. |
| `make clean` | Удаляет `dist/` и локальные бинарники. |

Кэш модулей Go и npm живёт в именованных docker-томах, поэтому повторная сборка
не тянет зависимости заново. Сбросить кэш, если он испортился:

```bash
docker volume rm nkt-gomod nkt-gocache nkt-npm
```

Под Windows `make` обычно отсутствует — эквивалентные команды `docker run`
приведены в следующем разделе.

## 1.2. Продакшен: Linux-хост

### Шаг 1. Собрать бинарник

Сборка идёт внутри контейнера `golang`, поэтому артефакт получается одинаковым
независимо от того, с какой машины его запустили:

```bash
make build            # → dist/nkt, linux/amd64, статический
make build GOARCH=arm64   # для ARM-хоста
```

Из PowerShell, если `make` нет под рукой, — та же команда напрямую:

```powershell
docker run --rm -v "${PWD}:/src" -w /src/web node:22-alpine sh -c "npm ci && npm run build"
docker run --rm -v "${PWD}:/src" -w /src -e CGO_ENABLED=0 -e GOOS=linux golang:1.26-alpine `
  go build -trimpath -ldflags "-s -w" -o dist/nkt ./cmd/nkt
```

Собирать можно и прямо на целевом хосте, если там есть Go 1.25+ и Node 20+:

```bash
cd web && npm ci && npm run build && cd ..
CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=$(git describe --tags --always)" \
  -o dist/nkt ./cmd/nkt
```

Порядок важен: `go:embed` вшивает веб-интерфейс **на этапе компиляции**, поэтому
`npm run build` всегда выполняется до `go build`.

### Шаг 2. Проверить, что хост читается

Перед установкой сервиса убедитесь, что приложение видит конфигурации:

```bash
sudo ./dist/nkt scan
```

Команда напечатает найденные слушатели, контейнеры, правила firewall и список
проблем. Нужен root: `iptables-save` и `systemctl` от обычного пользователя
недоступны.

На Linux боевой режим включён по умолчанию — задавать `NKT_MODE` не требуется.
Состояние по умолчанию пишется в `/var/lib/netknownsthat`, то есть туда же, куда
его пишет systemd-юнит: запущенный вручную `nkt tui` читает ту же базу, что
наполняет сервис, а не заводит рядом с бинарником пустую.

### Шаг 3. Установить

```bash
sudo make install          # положит бинарник, конфиг и unit на место
sudo $EDITOR /etc/netknownsthat/nkt.env
sudo systemctl enable --now netknownsthat
sudo journalctl -u netknownsthat -n 30     # здесь будет пароль администратора
```

Вручную то же самое:

```bash
sudo install -m 0755 dist/nkt /usr/local/bin/nkt
sudo install -d -m 0750 /etc/netknownsthat
sudo install -m 0640 deploy/nkt.env.example /etc/netknownsthat/nkt.env
sudo install -m 0644 deploy/netknownsthat.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now netknownsthat
```

Пароль администратора печатается в журнал **один раз** при первом запуске и
больше нигде не хранится в открытом виде. Чтобы задать его заранее, впишите
`NKT_BOOTSTRAP_ADMIN_PASSWORD` в `/etc/netknownsthat/nkt.env` до старта.

Дальше пароли меняются командой `nkt passwd` — подробности в 1.7.

### Шаг 4. Открыть

По умолчанию сервис слушает `127.0.0.1:8077`. Наружу отдавайте только через
reverse proxy с TLS — `NKT_COOKIE_SECURE=true` включён по умолчанию, кука
сессии без HTTPS браузер не примет. Быстрый доступ без проксирования —
туннель:

```bash
ssh -L 8077:127.0.0.1:8077 user@host
```

Туннель отдаёт браузеру голый HTTP, поэтому для входа через него добавьте в
`/etc/netknownsthat/nkt.env` `NKT_COOKIE_SECURE=false`.

Либо вообще без браузера, прямо в SSH-сессии:

```bash
sudo nkt tui
```

**Доступ к приложению равносилен root на хосте** — оно правит конфиги, управляет
сервисами и меняет firewall. Не выставляйте его в интернет без отдельного слоя
аутентификации.

## 1.3. Терминальный интерфейс

Тот же набор данных и те же действия, что в вебе. Десять экранов, переключение
цифрами `1`…`9`, `0` или `Tab`:

| Экран | Что показывает и что умеет |
|---|---|
| Обзор | плитки состояния, список проблем, сервисы, firewall, доступность |
| Проблемы | таблица находок с подробностями; `f` фильтр по серьёзности |
| Карта | дерево «внешняя сеть → слушатель → пул → backend → контейнер → сеть» |
| Доступность | тепловая карта простоев по часам недели, графики, список простоев; `p` проверить сейчас, `space` пауза |
| Нагрузка | динамика, рейтинг потребителей, расписание использования; `m` сменить показатель |
| Конфигурации | просмотр и правка; `e` редактор, `v` история версий, `u` откат |
| Сервисы | systemd-юниты и контейнеры; `s` `x` `t` `l` запуск, стоп, перезапуск, reload; `c` проверить конфиг |
| Firewall | правила ufw и пакетного фильтра; `a` добавить, `x` удалить |
| Сертификаты | сроки, расписание истечения, состояние автообновления и сверка с сокетом; `Enter` показать файл, `g` выпустить самоподписанный |
| Журнал | все изменения с указанием пользователя и результата |

Общие клавиши: `F5` обновить, `r` пересканировать хост, `?` справка, `q` выход.
В редакторе `Ctrl+S` сохраняет — с той же проверкой сервисом и автооткатом при
отказе, что и в вебе.

Две особенности:

* **TUI не собирает историю.** Пробы, метрики и разбор логов выполняет фоновый
  планировщик, то есть запущенный сервис `netknownsthat`. Терминал читает ту же
  базу; без сервиса экраны доступности и нагрузки будут пустыми. Разовая
  проверка ресурса — клавиша `p`.
* **Входа по паролю нет.** Если вы на хосте, вы и так root. Действия пишутся в
  журнал под именем `tui:<логин>`, причём под `sudo` берётся исходный
  пользователь, а не `root`. Ограничение `NKT_ALLOW_MUTATIONS=false` действует и
  здесь.

## 1.4. Проверочный стенд

Настоящие nginx и haproxy с настоящими бэкендами, рядом — NetKnownsThat в режиме
`local`, читающий те же файлы и работающий с настоящим демоном docker.

```bash
make stand              # или: docker compose -f stand/docker-compose.yml up -d --build
docker logs nkt         # пароль администратора
make stand-down         # остановить и удалить тома
```

| Адрес | Что это |
|---|---|
| <http://127.0.0.1:8077> | NetKnownsThat |
| <http://127.0.0.1:8081> | nginx, проксирует на два бэкенда |
| <http://127.0.0.1:8082> | haproxy, балансирует те же бэкенды |
| <http://127.0.0.1:8404> | панель статистики haproxy (намеренно без пароля) |
| `127.0.0.1:6380` | redis, намеренно опубликован на всех интерфейсах |

Стенд проверяет по-настоящему: разбор живых конфигов, Docker Engine API,
управление контейнерами и цикл правки конфигурации с настоящим `nginx -t`,
включая ветку отказа с автооткатом.

Не покрывает: systemd и firewall хоста (внутри контейнера их нет), а также
сравнение «объявлено против слушается» для nginx и haproxy — они в своих сетевых
пространствах имён, и `ss` их сокетов не видит. Приложение это распознаёт и
молчит, вместо того чтобы объявить весь хост мёртвым.

`make stand-down` с флагом `-v` обязателен: учётная запись живёт в томе, и без
его удаления пересозданный стенд не напечатает новый пароль.

## 1.5. Разработка на своей машине

Режим `fixtures` читает снапшот хоста из `fixtures/host` — пример
production-сервера с намеренно заложенными проблемами. Работает на Windows,
macOS и Linux. **Для продакшена не предназначен.**

```powershell
cd web; npm install; npm run build; cd ..
go build -o nkt.exe ./cmd/nkt      # либо: make build-dev
.\nkt.exe
```

На Windows и macOS это режим по умолчанию. Если разрабатываете **на Linux**,
задайте его явно — иначе приложение полезет читать настоящий хост:

```bash
NKT_MODE=fixtures ./nkt
```

Пароль печатается в консоль при первом запуске. Открыть <http://127.0.0.1:8077>.
На дашборде сразу будет 25 находок: открытый наружу Redis, конфликт порта 8443,
контейнер в цикле перезапуска, панель haproxy без пароля, устаревший TLS.

Фронтенд с горячей перезагрузкой — два процесса:

```powershell
.\nkt.exe                    # API на :8077
cd web; npm run dev          # интерфейс на :5173, проксирует /api
```

**Про синтетические данные.** Описанных в снапшоте сокетов на вашей машине нет, а
счётчики в нём заморожены, поэтому пробы и метрики моделируются, а история за
14 дней засевается один раз при первом запуске. Интерфейс говорит об этом
баннером, API отдаёт `"simulated": true`. Отключается через
`NKT_DEMO_BACKFILL=false`. В режиме `local` всё измеряется по-настоящему.

## 1.7. Учётные записи и пароли

Приложение хранит пароли только в собственной базе (`argon2id`, необратимо) — 
достать «текущий» пароль неоткуда, даже из базы напрямую. Сброс всегда идёт
через выпуск нового.

**Сменить пароль администратора** (сработает и для любого другого логина):

```bash
sudo nkt passwd            # спросит новый пароль дважды, без эха на экране
```

**Забыли пароль и не можете войти** — то же самое решает проблему: `nkt passwd`
задаёт новый пароль напрямую в базе, без входа в старую сессию.

**Завести ещё одну учётную запись**, например только на чтение — команда
создаёт её, если такого логина ещё нет, и требует явно указать роль:

```bash
sudo nkt passwd ops -role viewer
sudo nkt passwd ops2 -role admin
```

**Сгенерировать пароль** вместо ввода — годится для автоматизации:

```bash
sudo nkt passwd -random
```

**Посмотреть, какие учётные записи есть**, кто когда заходил, кто отключён:

```bash
sudo nkt users
```

**Передать пароль без интерактивного ввода** (скрипты, Ansible) — через stdin,
одна строка:

```bash
echo 'новый-пароль-подлиннее' | sudo nkt passwd ops
```

**Сменить свой пароль из веб-интерфейса**: кнопка «Сменить пароль» внизу
боковой панели — попросит текущий пароль и дважды новый. После смены все
сессии этой учётной записи завершаются, включая ту, из которой меняли пароль:
потребуется войти заново. Минимальная длина везде — 10 символов, считаются
именно символы, а не байты UTF-8.

**Завести или изменить чужую учётную запись из веб-интерфейса**, не заходя на
сам хост: пункт «Пользователи» в боковой панели (виден только `admin`) —
список всех логинов с ролью, состоянием, датой создания и последним входом;
там же форма «Новая учётная запись» и кнопки сменить роль / отключить /
удалить у каждой строки. Пароль при создании задаётся сразу, сбросить забытый
пароль эта страница не умеет — только `sudo nkt passwd <логин>` на хосте.
Собственную учётную запись со страницы нельзя ни разжаловать из admin, ни
отключить, ни удалить — так исключается случайная потеря доступа.

Каждая смена пароля и создание учётной записи пишутся в журнал действий
(`nkt users`, экран «Журнал» в TUI, вкладка «Журнал действий» в вебе) с
пометкой `cli:<логин хоста>`.

## 1.8. Настройка

Все параметры — переменные окружения `NKT_*`, полный список с пояснениями лежит
в [deploy/nkt.env.example](deploy/nkt.env.example). Самое нужное:

| Переменная | Смысл |
|---|---|
| `NKT_MODE` | `local` — читать настоящий хост, `fixtures` — снапшот. По умолчанию `local` на Linux и `fixtures` на остальных системах |
| `NKT_DATA_DIR` | где хранить базу и историю конфигураций. По умолчанию `/var/lib/netknownsthat` в режиме `local` и `./data` в режиме `fixtures` |
| `NKT_ADDR` | адрес прослушивания, по умолчанию `127.0.0.1:8077` |
| `NKT_ALLOW_MUTATIONS` | `false` переводит всё приложение в режим только чтения |
| `NKT_COOKIE_SECURE` | `true` по умолчанию (кука сессии только по HTTPS); `false` — только для голого HTTP, например SSH-туннеля |
| `NKT_COMPOSE_FILES` | список compose-файлов через запятую |
| `NKT_PROBE_INTERVAL` | как часто проверять доступность; голое число — секунды |
| `NKT_AUTO_RENEW_CERTS` | `true` — раз в `NKT_AUTO_RENEW_INTERVAL` (по умолчанию 6h) сама запускает `certbot renew` для certbot-сертификатов не старше `NKT_AUTO_RENEW_WITHIN` (по умолчанию 30 дней) до истечения. По умолчанию `false` |
| `NKT_CERTBOT_TIMEOUT` | сколько ждать `certbot renew` — отдельно от `NKT_COMMAND_TIMEOUT`, потому что это сетевой запрос к Let's Encrypt, а не быстрая команда хоста. По умолчанию `3m` |

## 1.9. Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| Страница «Фронтенд не собран» | Бинарник собран раньше интерфейса. Выполните `npm run build`, затем **заново** `go build`: `go:embed` вшивает файлы при компиляции. |
| `режим local работает только на Linux` | Ровно то, что написано: боевой режим на Windows и macOS не запускается. Для разработки — `NKT_MODE=fixtures`. |
| `каталог снапшота … не найден` | Включён режим `fixtures`, а каталога с примерами рядом нет. На боевом хосте нужен `NKT_MODE=local` (на Linux он и так по умолчанию — значит, переменная задана явно где-то ещё). Для разработки запускайте из корня репозитория или укажите `NKT_FIXTURES_ROOT`. |
| `не удалось создать каталог данных /var/lib/netknownsthat` | Запуск не от root. Либо `sudo`, либо своё расположение через `NKT_DATA_DIR`. |
| `failed to connect to the docker API` | Не запущен Docker. Нужен для сборки релиза, стенда и для чтения контейнеров в режиме `local`. |
| Источники `firewall` и `services` недоступны | Нужен root: `iptables-save` и `systemctl` от обычного пользователя не работают. Запускайте через systemd-юнит из `deploy/`. |
| Пароль потерян | Остановите сервис и удалите `/var/lib/netknownsthat/netknownsthat.db`. В режиме `fixtures` — каталог `data/`, на стенде — `make stand-down`. |
| `bind: address already in use` | Порт занят, задайте другой через `NKT_ADDR`. |
| Правки конфигов отклоняются с `Read-only file system` | Каталог конфигурации примонтирован только на чтение, либо нет прав на запись в каталог логов, который открывает `nginx -t`. |
| Кнопки неактивны, изменения запрещены | Либо роль `viewer`, либо `NKT_ALLOW_MUTATIONS=false`. |
| В консоли Windows кракозябры | Кодовая страница не UTF-8: `chcp 65001`. Файл с перенаправленным выводом читайте как `Get-Content файл -Encoding UTF8`. |
| После `make build` перестала работать нативная сборка фронтенда | `make web` ставит зависимости внутри Linux-контейнера поверх того же каталога, и `node_modules` заполняется linux-сборками. Для локальной разработки выполните `npm install` в `web/` заново. |

# 2. Возможности

## 2.1. Проверка конфигураций

Конфиги не просто читаются, а сопоставляются друг с другом и с реальным
состоянием хоста: вывод `ss -tulpnH`, счётчики `iptables-save -c`, список
контейнеров из Docker Engine API.

| Правило | Серьёзность | Что находит |
|---|---|---|
| `port-conflict` | high | Два сервиса объявляют один и тот же порт на пересекающихся адресах |
| `declared-not-listening` | high | Порт описан в конфиге сервиса, но никто его не слушает |
| `listening-not-declared` | medium/info | Процесс слушает порт, не описанный ни в одном конфиге |
| `no-default-deny` | high | Политика INPUT — ACCEPT и ufw выключен |
| `public-port-blocked` | medium | Сервис слушает 0.0.0.0, но firewall его не пропускает |
| `docker-bypasses-firewall` | critical/high | Контейнер публикует порт на 0.0.0.0 — DNAT обходит INPUT и правила ufw |
| `stale-firewall-rule` | low | Правило разрешает порт, который никто не слушает |
| `sensitive-port-public` | critical/high | Redis, PostgreSQL, MongoDB и т. п. слушают все интерфейсы |
| `weak-tls` | medium | В `ssl_protocols` остались TLSv1 / TLSv1.1 |
| `missing-hsts` | low | TLS-сервер не отдаёт Strict-Transport-Security |
| `tls-cert-missing` | high | `listen ... ssl` без `ssl_certificate` |
| `tls-cert-expired` | critical | Срок действия сертификата уже истёк |
| `tls-cert-expiring` | high/medium | Истекает в ближайшие 7 или 30 дней |
| `tls-cert-not-yet-valid` | high | Ещё не вступил в силу — обычно сбиты часы хоста |
| `tls-cert-unreadable` | high | Файл, указанный в конфиге, не читается |
| `tls-cert-name-mismatch` | high | Сертификат не покрывает имя, под которым отвечает сервер |
| `tls-cert-renewal-not-automatic` | medium | certbot знает о сертификате, но ни таймер, ни cron его не продлят |
| `tls-cert-orphan-lineage` | high | Сертификат лежит в `/etc/letsencrypt/live`, а файла обновления нет |
| `tls-cert-self-signed` | low | Издатель совпадает с субъектом |
| `tls-cert-weak-key` | medium | Ключ RSA короче 2048 бит |
| `tls-cert-weak-signature` | medium | Подпись SHA-1 или MD5 |
| `tls-cert-not-reloaded` | high | На сокете отдаётся не тот сертификат, что лежит в конфиге — сервис не перечитал файл после обновления |
| `public-plaintext-proxy` | medium | Публичный HTTP-слушатель проксирует трафик без шифрования |
| `upstream-undefined` | high | Маршрут ссылается на несуществующий пул |
| `upstream-orphan` | low | Пул объявлен, но нигде не используется |
| `upstream-member-down` | high | Локальный backend пула не слушает свой порт |
| `all-backends-disabled` | critical | Все серверы пула помечены down/backup |
| `single-backend` | info | В пуле один сервер — нет резерва |
| `backend-no-healthcheck` | medium | В пуле больше одного сервера и нет проверки здоровья |
| `container-restarting` | high | Контейнер в цикле перезапуска |
| `container-not-running` | medium | Описан в compose, но не запущен |
| `container-undeclared` | low | Запущен, но не описан ни в одном compose-файле |
| `container-no-restart-policy` | low | Не задана политика перезапуска |
| `admin-interface-open` | high/medium | Панель статистики haproxy доступна без пароля |

Каждая находка содержит объяснение, ссылку на файл и строку, и конкретное
действие для исправления.

## 2.2. Карта сетевых ресурсов

Граф, где трафик читается слева направо:

```
внешняя сеть → сервис → слушатель → пул → backend-адрес → контейнер → сеть docker
```

Связи берутся из конфигураций (`proxy_pass`, `upstream`, `use_backend`,
`default_backend`, публикация портов), состояние узлов — из реальных слушателей,
состояния контейнеров и найденных проблем. Раскладка по колонкам, а не силовая:
она стабильна между сканами и читается как схема потока запросов. В терминале
та же карта показывается деревом.

## 2.3. Расписание доступности и использования

**Доступность.** Каждый объявленный слушатель и каждый backend пула проверяется
по расписанию — TCP-коннект или HTTP-запрос с правильным заголовком `Host`. Из
истории строятся тепловая карта «час недели × недоступность», графики
доступности и задержки, список простоев.

**Использование.** Приросты счётчиков iptables, `docker stats` и разбор
access-логов nginx и haproxy. Записи логов раскладываются по времени самой
записи, поэтому график показывает, когда нагрузка была на самом деле, а не когда
её собрали.

## 2.4. Сертификаты и их обновление

Пути берутся из директив `ssl_certificate` в nginx и `crt` в haproxy, файлы
читаются и разбираются как X.509. Для каждого сертификата видно: до какой даты
он действителен и сколько осталось дней, какие имена покрывает (CN и SAN),
кем выпущен, алгоритм и длину ключа, длину цепочки, самоподписанный он или нет.

У haproxy `crt` может указывать не на файл, а на каталог — тогда выбор
сертификата идёт по SNI из всех бандлов внутри (`bind ... ssl crt /certs`).
Такой каталог разворачивается в список отдельных сертификатов, по одному на
файл; служебные companion-файлы (`.key`, `.ocsp`, `.issuer`, `.sctl`),
которые haproxy держит рядом с бандлом, в этот список не попадают.

Отдельно проверяется **обновление**, потому что просроченный сертификат почти
всегда результат не забывчивости, а сломанной автоматики:

* сертификат лежит в `/etc/letsencrypt/live/<имя>`, но файла
  `/etc/letsencrypt/renewal/<имя>.conf` нет — certbot про него не знает и не
  продлит;
* файл обновления есть, но `certbot.timer` не активен и задания cron нет —
  продление не запустится само;
* путь вне `/etc/letsencrypt` — обновление, скорее всего, ручное. **Кроме
  одного случая**: приложение отдельно, напрямую читает сертификат каждой
  известной certbot-lineage (`/etc/letsencrypt/live/<lineage>/fullchain.pem`) —
  независимо от того, ссылается ли на этот путь хоть одна директива
  nginx/haproxy — и сравнивает по отпечатку SHA-256. Совпадение — типичный
  случай для haproxy, которому certbot не пишет напрямую: nginx умеет читать
  `ssl_certificate` и `ssl_certificate_key` раздельно прямо из
  `/etc/letsencrypt/live/...`, а haproxy требует сертификат и ключ в одном
  PEM, поэтому deploy-hook certbot склеивает `fullchain.pem`+`privkey.pem` в
  отдельный файл где-то ещё — иногда так, что оригинал в конфигурации вообще
  нигде не упомянут напрямую. Такой файл помечается `Renewal.Derived = true`,
  показывает путь к оригиналу (`Renewal.SourcePath`) и наследует его статус
  обновления вместо ложного
  «вручную».

**Перевыпуск.** Для сертификата с файлом обновления (`Renewal.Managed`) в
таблице появляется кнопка «продлить» (веб, столбец «Действия»; в TUI — клавиша
`r` на экране «Сертификаты»). Она запускает `certbot renew --cert-name
<lineage>` на хосте и доводит результат до конца, а не просто вызывает
команду:

* если lineage аутентифицируется через `--standalone` (значение
  `authenticator = standalone` в `/etc/letsencrypt/renewal/<lineage>.conf`) —
  certbot слушает `:80`/`:443` сам, поэтому перед вызовом приложение
  останавливает nginx и haproxy, а после — **всегда** запускает их обратно,
  независимо от того, чем закончилось продление: оставить сайт лежать из-за
  неудачного продления хуже, чем сохранить прежний сертификат;
* производную копию для haproxy (см. выше, `Renewal.Derived`) certbot не
  трогает — приложение само пересобирает её из свежих
  `fullchain.pem`+`privkey.pem` и перечитывает конфигурацию сервиса
  (`reload`), которому она принадлежит. Если lineage была `--standalone`,
  отдельный `reload` не нужен: файл уже пересобран к моменту, когда сервисы
  запускаются обратно.

Каждый шаг — продление, пересборка копии, остановка/запуск сервисов — пишется
в журнал действий отдельной записью. Доступна только `admin` и только при
`NKT_ALLOW_MUTATIONS=true`.

Вся операция может занимать минуты (сеть до Let's Encrypt, остановка/запуск
сервисов), поэтому кнопка не блокирует интерфейс одним спиннером: нажатие
запускает продление в фоне на сервере и сразу открывает окно с живым логом
(веб — модальное окно; TUI — та же панель, что и для остальных подробностей),
куда построчно, по мере выполнения, попадают все шаги: остановка nginx и
haproxy (если нужна), сама команда certbot и её вывод, какой именно файл
пересобран для haproxy (полный путь, не просто факт), перечитывание или
перезапуск сервисов, и финальное «Готово» либо текст ошибки. Окно можно
закрыть в любой момент, не дожидаясь конца — сама операция на хосте от этого
не остановится, а список сертификатов обновится, когда она всё же закончится.

Сам вызов `certbot renew` идёт под отдельным таймаутом — `NKT_CERTBOT_TIMEOUT`
(по умолчанию 3 минуты), а не общим `NKT_COMMAND_TIMEOUT` (30 секунд), который
рассчитан на быстрые команды хоста вроде `systemctl`. Обращение к Let's
Encrypt — сетевой запрос, и уложиться в 30 секунд ему не всегда по силам;
если бы certbot делил таймаут с быстрыми командами, продление обрывалось бы
на середине (`код -1`, оборванный вывод вроде «Processing
/etc/letsencrypt/renewal/…conf» без продолжения) без внятной причины.

**Собрать PEM для haproxy вручную.** Автоматическая пересборка выше срабатывает
только для уже существующего файла, отпечаток которого совпал с известной
lineage (см. «производные копии» выше) — то есть уже после того, как haproxy
однажды был подключён к этому сертификату. Для остальных случаев есть
отдельное действие «Собрать PEM для haproxy из certbot» (веб, карточка под
таблицей; в TUI — клавиша `c`). Оно ничего не продлевает и не вызывает
certbot — только читает уже выпущенные файлы:

* список lineage читается прямо из `/etc/letsencrypt/live`, каждая — со
  сроком действия (`N дн.` / `просрочен … назад` / `истекает сегодня`), чтобы
  не проверять «Подробности» отдельно;
* второе поле, «Куда записать» — список путей, которые haproxy уже использует
  прямо сейчас (те же строки, что видны в «Подробности»). Если выбрать один
  из них, приложение **перезаписывает именно этот файл** новым
  `fullchain.pem`+`privkey.pem` выбранной lineage и сразу перечитывает
  конфигурацию haproxy (`reload`) — вставлять ничего не нужно;
* если оставить «— новый файл —» (haproxy ещё никогда не использовал эту
  lineage, сравнивать не с чем), файл пишется в
  `<HAProxyRoot>/ssl-letsencrypt/<lineage>/combined.pem`, как самоподписанный
  сертификат, а на экран выводится директива `bind ... crt <путь>` для
  вставки через редактор конфигурации.

Если продлевать некому (таймер и cron выключены, как в примере выше), можно
включить **автоматическое продление**: `NKT_AUTO_RENEW_CERTS=true` заставляет
приложение самостоятельно, по расписанию (`NKT_AUTO_RENEW_INTERVAL`, по
умолчанию 6 часов), находить certbot-сертификаты не старше
`NKT_AUTO_RENEW_WITHIN` (по умолчанию 30 дней) до истечения — включая уже
просроченные — и продлевать их той же логикой, что и кнопка «продлить»
(остановка/запуск nginx и haproxy для `--standalone`-lineage, пересборка
производных копий для haproxy). Для `--standalone`-lineage это означает, что
фоновая задача сама, без участия человека, ненадолго останавливает сайт —
имейте это в виду, включая автопродление. Задача видна на экране «Журнал»
(панель «Фоновые задачи», запись `cert-renew`) и уважает
`NKT_ALLOW_MUTATIONS`: при `false` не запускается, даже если включена.

«Расписание истечения» показывает запас всех сертификатов на одной шкале, то
есть порядок, в котором они перестанут работать. Пороги совпадают с поведением
Let's Encrypt: 30 дней — предупреждение (автоматика уже должна была сработать),
7 дней — срочно.

**Сверка с тем, что реально отдаётся на сокете.** Файл на диске может быть
абсолютно здоровым — и всё равно не тем, что видят клиенты: `certbot renew`
подменяет файл, но пока сервис не перечитает конфигурацию (`reload`), он
продолжает отдавать старый сертификат из памяти. Разница не видна нигде, кроме
самого TLS-соединения. Поэтому при каждом скане на реальном хосте (не в
режиме `fixtures`) приложение дополнительно **устанавливает TLS-подключение**
к первому известному адресу каждого сертификата — с тем же SNI, что использует
конфигурация, — и сравнивает отпечаток (SHA-256) полученного сертификата с
файлом. Расхождение — это правило `tls-cert-not-reloaded`, единственная
находка в этом разделе, которая проверяет не файл, а провод.

Ошибка подключения (закрыт порт, фильтр, таймаут) не считается расхождением —
она просто помечается как «не проверялось», чтобы временная сетевая проблема
не превращалась в ложное обвинение сервиса.

**Выпуск самоподписанного сертификата.** Когда TLS для внешнего доступа не
настроен вовсе — типичная находка `public-plaintext-proxy` или
`tls-cert-missing` — на странице «Сертификаты» (и клавишей `g` там же в
терминале) можно тут же сгенерировать сертификат: RSA 2048/3072/4096, срок по
умолчанию 397 дней (максимум 825), несколько имён через запятую, включая
wildcard (`*.internal.example.com`). Имя можно ввести и в Unicode
(`испытание.рф`) — приложение само переведёт его в punycode
(`xn--80akhbyknj4f.xn--p1ai`), как того требуют DNS и TLS SNI, и покажет обе
формы рядом в результате. То же самое видно для уже существующих
punycode-имён certbot-lineage (в списке «Собрать PEM») и на карте сетевых
ресурсов — сноской в подробностях узла слушателя. Для nginx получаются два файла
(`fullchain.pem` и `privkey.pem`), для haproxy — один объединённый (`crt`
ожидает сертификат и ключ в одном PEM). Оба варианта пишутся в новый каталог
`ssl-selfsigned/<имя>/` внутри корня nginx или haproxy — то есть в ту же
зону, что уже разрешена для редактирования конфигов.

Приложение **не правит конфигурацию само** — сама правка `server{}` или
`frontend` слишком легко ломается автоматической подстановкой не в то место.
Вместо этого форма возвращает готовые директивы (`ssl_certificate …` /
`bind … ssl crt …`), которые нужно вставить через редактор на странице
«Конфигурации» — там же, где правка проходит проверку сервисом с автооткатом
при ошибке. Самоподписанный сертификат не убирает предупреждение браузера:
это способ быстро закрыть трафик шифрованием для внутреннего сервиса или
временно — не замена сертификата от доверенного центра.

## 2.5. Управление

* **systemd**: `start` / `stop` / `restart` / `reload`, проверка конфигурации.
* **docker**: `start` / `stop` / `restart` контейнеров через Engine API.
* **Конфиги**: редактор с версионированием. Перед записью содержимое проверяется
  самим сервисом (`nginx -t`, `haproxy -c -f`, `docker compose config -q`); **если
  проверка не прошла, файл автоматически возвращается в прежнее состояние**.
  Любую версию можно посмотреть, сравнить (unified diff) и откатить.
* **firewall**: добавление и удаление правил через `ufw`. Прямая правка iptables
  из интерфейса намеренно не поддерживается.

Все изменения пишутся в журнал с указанием пользователя, результата и вывода
команды.

# 3. Архитектура

```
cmd/nkt                 подкоманды: serve, tui, scan
internal/config         все настройки из NKT_* переменных
internal/collect        ЕДИНСТВЕННОЕ место, где расходятся fixtures и реальный хост
  ├── local.go          настоящая ФС, exec, unix-сокет docker (только Linux)
  └── fixtures.go       снапшот на диске, заготовленные ответы команд
internal/parse          nginx (crossplane), haproxy (config-parser), docker,
                        iptables, ufw, ss, systemd
internal/model          вендор-нейтральное описание найденного
internal/analyze        правила поиска проблем
internal/topology       построение графа ресурсов
internal/inventory      оркестрация скана, снапшоты, цели мониторинга
internal/monitor        пробы, метрики, access-логи, планировщик
internal/tlscheck       живой TLS-дозвон: что сокет отдаёт на самом деле
internal/control        сервисы, правка конфигов с версиями, firewall,
                        выпуск самоподписанных сертификатов
internal/store          SQLite (modernc, чистый Go — статическая сборка)
internal/api            HTTP API на chi
internal/webui          вшитый веб-интерфейс
internal/tui            терминальный интерфейс на tview
web/                    React + TypeScript, графики на голом SVG
```

Ключевое решение — интерфейс `collect.Collector`. Всё остальное приложение
работает с POSIX-путями хоста и не знает, читает оно настоящий сервер или
снапшот, поэтому парсеры и правила ведут себя одинаково везде.

Веб-интерфейс и терминальный — два равноправных потребителя одних и тех же
пакетов: оба вызывают `inventory`, `analyze`, `topology` и `control` напрямую, и
ни один не ходит через другой. Исправление в правилах или в построителе карты
одинаково видно и там, и там.

Внешние зависимости: `nginx-go-crossplane` (официальный парсер nginx),
`haproxytech/config-parser` (парсер из HAProxy Dataplane API), `modernc.org/sqlite`,
`go-chi/chi`, `rivo/tview`, `golang.org/x/crypto` (argon2id), `gopkg.in/yaml.v3`.
Docker опрашивается собственным минимальным клиентом Engine API — вместо трёхсот
пакетов официального SDK.

# 5. Безопасность

* Пароли — argon2id (64 МиБ, t=3, p=2). Сессии — случайные отзываемые токены в
  SQLite; cookie `HttpOnly`, `SameSite=Lax`.
* Роли: `viewer` — только чтение, `admin` — изменения. Плюс глобальный
  выключатель `NKT_ALLOW_MUTATIONS=false`.
* После пяти неудачных попыток вход по учётной записи блокируется с нарастающей
  задержкой.
* Правка конфигов ограничена белым списком каталогов (корни nginx и haproxy,
  перечисленные compose-файлы). Пути с `..` отвергаются.
* Действия над сервисами и firewall принимают только значения из фиксированных
  списков — имя сервиса или действие невозможно подставить в команду.
* Удаление правила ufw сверяется с текстом, который видел оператор: номера
  сдвигаются после каждого изменения, и удаление «не того» правила способно
  отрезать SSH.
* Оптимистичная блокировка при сохранении конфига по SHA-256: файл, изменившийся
  на диске после открытия в редакторе, не будет перезаписан молча.
* Каждое изменяющее действие пишется в `audit_log`.
* systemd-юнит из `deploy/` сужает права: `ProtectSystem=strict` с явным списком
  доступных на запись каталогов, урезанный `CapabilityBoundingSet`,
  `SystemCallFilter=@system-service`.

# 6. Ограничения

* Один хост. Нет ни агентов, ни сбора с нескольких машин.
* Пишутся только правила `ufw`; прямая правка iptables не поддерживается
  намеренно.
* Из firewall-бэкендов поддержаны iptables/ip6tables и ufw. Чистый `nftables`
  (без слоя iptables-nft) не разбирается.
* Правило `declared-not-listening` требует доступного `ss`; без него сравнивать
  конфиг не с чем. Оно также молчит, если таблица сокетов не подтверждает ни
  одного объявленного порта — значит, читается чужое сетевое пространство имён.
  Опубликованные порты контейнеров этим правилом не проверяются вовсе: при
  `userland-proxy: false` docker пробрасывает их чистым DNAT, и слушателя на
  хосте не существует.
* Проверка конфигурации в режиме `fixtures` всегда «успешна» — ветка отказа
  валидации проверяется на стенде или на настоящем хосте.
* Из веб-серверов и балансировщиков поддержаны nginx и haproxy. Caddy, Traefik,
  Envoy не разбираются — под них нужен новый файл в `internal/parse`.
* Сверка «что реально отдаётся на сокете» — это один TLS-дозвон на сертификат,
  к первому известному адресу. Если несколько разных сертификатов
  мультиплексируются по SNI на одном порту, проверяется только тот, что
  соответствует основному имени сертификата (`Sites[0]`); остальные на этом же
  порту не проверяются. В режиме `fixtures` эта проверка не выполняется вовсе
  — дозваниваться там не до чего.
* Самоподписанный сертификат не отменяет предупреждение браузера — это
  стопгэп для внутренних и тестовых сервисов, а не замена сертификата от
  доверенного центра. Приложение не редактирует nginx/haproxy конфигурацию
  автоматически: директивы нужно вставить руками через редактор.

# 7. Разработка

```bash
make check          # go vet, gofmt, go test ./... и проверка типов фронтенда
make test           # только тесты
make build-dev      # нативный бинарник для режима fixtures
```

Тесты работают против `fixtures/host` — снапшота, в который намеренно заложены
конфликт портов, открытый наружу Redis, контейнер в цикле перезапуска, панель
статистики без пароля, устаревший TLS и неиспользуемое правило firewall.
`TestScanFindsPlantedProblems` проверяет, что анализатор находит каждую из них с
ожидаемой серьёзностью.

Терминальный интерфейс тестируется headless: `tcell` отдаёт симулированный
экран, тест поднимает приложение целиком, нажимает клавиши и проверяет
отрисованные кадры. Панику или неверное поле в любом из десяти экранов это ловит
без настоящего терминала.

Добавление нового парсера: новый файл в `internal/parse`, возвращающий
`model.Endpoint` / `model.Upstream` / `model.SourceStatus`, и вызов в
`internal/inventory/scan.go`. Всё остальное — карта, анализ, мониторинг, оба
интерфейса — подхватит его автоматически.
