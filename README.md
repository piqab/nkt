# NetKnownsThat

Приложение для одного Linux-хоста: разбирает конфигурации **nginx**, **haproxy**,
**docker/compose**, **iptables** и **ufw**, сопоставляет их с тем, что реально
происходит на машине, строит **карту сетевых ресурсов**, ведёт **расписание
доступности и использования** и даёт **дашборд для управления** сервисами,
конфигами и правилами firewall.

Один статический бинарник с тремя интерфейсами: **веб-дашборд** (вшит в
бинарник), **терминальный интерфейс** для работы по SSH без браузера и
**разовый отчёт** для cron или CI. На хосте не нужны ни Python, ни Node, ни
отдельные статические файлы.

```
nkt          веб-дашборд и фоновый сбор данных
nkt tui      терминальный интерфейс
nkt scan     разовая проверка, код возврата 2 при критичных находках
```

---

## Что именно оно делает

### 1. Проверяет конфигурации

Конфиги не просто читаются, а сопоставляются друг с другом и с реальным
состоянием хоста: вывод `ss -tulpnH`, счётчики `iptables-save -c`, список
контейнеров из Docker Engine API.

Реализованные правила:

| Правило | Серьёзность | Что находит |
|---|---|---|
| `port-conflict` | high | Два сервиса объявляют один и тот же порт на пересекающихся адресах |
| `declared-not-listening` | high | Порт описан в конфиге сервиса, но никто его не слушает (конфиг не применён) |
| `listening-not-declared` | medium/info | Процесс слушает порт, не описанный ни в одном конфиге |
| `no-default-deny` | high | Политика INPUT — ACCEPT и ufw выключен |
| `public-port-blocked` | medium | Сервис слушает 0.0.0.0, но firewall его не пропускает |
| `docker-bypasses-firewall` | critical/high | Контейнер публикует порт на 0.0.0.0 — DNAT обходит INPUT и правила ufw |
| `stale-firewall-rule` | low | Правило разрешает порт, который никто не слушает |
| `sensitive-port-public` | critical/high | Redis, PostgreSQL, MongoDB и т. п. слушают все интерфейсы |
| `weak-tls` | medium | В `ssl_protocols` остались TLSv1 / TLSv1.1 |
| `missing-hsts` | low | TLS-сервер не отдаёт Strict-Transport-Security |
| `tls-cert-missing` | high | `listen ... ssl` без `ssl_certificate` |
| `public-plaintext-proxy` | medium | Публичный HTTP-слушатель проксирует трафик без шифрования |
| `upstream-undefined` | high | Маршрут ссылается на несуществующий пул |
| `upstream-orphan` | low | Пул объявлен, но нигде не используется |
| `upstream-member-down` | high | Локальный backend пула не слушает свой порт |
| `all-backends-disabled` | critical | Все серверы пула помечены down/backup |
| `single-backend` | info | В пуле один сервер — нет резерва |
| `backend-no-healthcheck` | medium | В пуле больше одного сервера и нет проверки здоровья |
| `container-restarting` | high | Контейнер в цикле перезапуска |
| `container-not-running` | medium | Описан в compose, но не запущен |
| `container-undeclared` | low | Запущен, но не описан ни в одном compose-файле |
| `container-no-restart-policy` | low | Не задана политика перезапуска |
| `admin-interface-open` | high/medium | Панель статистики haproxy доступна без пароля |

Каждая находка содержит объяснение, ссылку на файл и строку, и конкретное
действие для исправления.

### 2. Строит карту сетевых ресурсов

Граф, где трафик читается слева направо:

```
внешняя сеть → сервис → слушатель → пул → backend-адрес → контейнер → сеть docker
```

Связи берутся из конфигураций (`proxy_pass`, `upstream`, `use_backend`,
`default_backend`, публикация портов), а состояние узлов — из реальных
слушателей, состояния контейнеров и найденных проблем. Раскладка по колонкам,
а не силовая: она стабильна между сканами и читается как схема потока запросов.

### 3. Ведёт расписание доступности и использования

* **Доступность** — каждый объявленный слушатель и каждый backend пула
  проверяется по расписанию (TCP-коннект или HTTP-запрос с правильным
  заголовком `Host`). Из истории строится тепловая карта «час недели ×
  недоступность», графики доступности и задержки и список простоев.
* **Использование** — приросты счётчиков iptables, `docker stats` и разбор
  access-логов nginx и haproxy. Записи логов раскладываются по времени самой
  записи, поэтому график показывает, когда нагрузка была на самом деле.

### 4. Даёт управлять

* systemd: `start` / `stop` / `restart` / `reload`, проверка конфигурации.
* docker: `start` / `stop` / `restart` контейнеров через Engine API.
* Конфиги: редактор с версионированием. Перед записью содержимое проверяется
  самим сервисом (`nginx -t`, `haproxy -c -f`, `docker compose config -q`);
  **если проверка не прошла, файл автоматически возвращается в прежнее
  состояние**. Любую версию можно посмотреть, сравнить (unified diff) и откатить.
* firewall: добавление и удаление правил через `ufw`. Прямая правка iptables из
  веб-интерфейса намеренно не поддерживается.

Все изменения пишутся в журнал с указанием пользователя, результата и вывода
команды.

## Как запустить

Есть три способа, и они не заменяют друг друга: первый показывает интерфейс на
любой машине, второй проверяет работу на настоящих сервисах, третий — рабочая
установка.

### Что нужно установить

| Инструмент | Зачем | Версия, на которой проверялось |
|---|---|---|
| Go | собрать бинарник | 1.26.1; минимум 1.25 — его требует зависимость `modernc.org/sqlite` |
| Node + npm | собрать интерфейс | 24.14.1 / 11.11.0 (достаточно Node 20) |
| Docker | только для стенда | 29.6.2 |

**На боевом хосте не нужно ничего** — туда кладётся один статический бинарник.

---

### Способ 1. На своей машине, без Linux-хоста

Режим `fixtures` читает снапшот хоста из каталога `fixtures/host` — пример
production-сервера с намеренно заложенными проблемами. Работает на Windows,
macOS и Linux одинаково.

```powershell
# 1. Собрать интерфейс. Vite кладёт результат прямо в internal/webui/dist,
#    откуда он вшивается в бинарник.
cd web
npm install
npm run build
cd ..

# 2. Собрать бинарник. Делать это ПОСЛЕ сборки интерфейса: go:embed
#    вшивает файлы на этапе компиляции, а не при запуске.
go build -o nkt.exe ./cmd/nkt

# 3. Запустить. fixtures — режим по умолчанию, переменную можно не задавать.
.\nkt.exe
```

В консоли появится пароль — он печатается **один раз** и больше нигде не
хранится в открытом виде:

```
=== Создана учётная запись администратора ===
  логин:  admin
  пароль: 7AhLRmwbB8UWuXzQJA8t
  Сохраните пароль: он больше нигде не отображается.
time=... level=INFO msg="сервер запущен" addr=127.0.0.1:8077 mode=fixtures
```

Открыть <http://127.0.0.1:8077> и войти. На дашборде сразу будет 25 находок по
снапшоту (2 критичных, 4 высоких, 10 средних, 4 низких, 5 информационных):
открытый наружу Redis, конфликт порта 8443, контейнер в цикле перезапуска,
панель haproxy без пароля, устаревший TLS.

Задать пароль заранее, чтобы не ловить его из вывода:

```powershell
$env:NKT_BOOTSTRAP_ADMIN_PASSWORD = "своё-длинное-значение"
.\nkt.exe
```

**Что означают синтетические данные.** Описанных в снапшоте сокетов на вашей
машине нет, а счётчики в нём заморожены — поэтому пробы и метрики моделируются,
а история за 14 дней засевается один раз при первом запуске. Интерфейс говорит
об этом баннером, API отдаёт `"simulated": true`. Отключается через
`NKT_DEMO_BACKFILL=false`. В режиме `local` всё измеряется по-настоящему.

### Способ 2. Стенд с настоящими nginx, haproxy и docker

Нужен запущенный Docker.

```powershell
docker compose -f stand/docker-compose.yml up -d --build
docker logs nkt                     # здесь будет пароль администратора
```

Поднимается шесть контейнеров:

| Адрес | Что это |
|---|---|
| <http://127.0.0.1:8077> | сам NetKnownsThat в режиме `local` |
| <http://127.0.0.1:8081> | nginx, проксирует на два бэкенда |
| <http://127.0.0.1:8082> | haproxy, балансирует те же бэкенды |
| <http://127.0.0.1:8404> | панель статистики haproxy (намеренно без пароля) |
| `127.0.0.1:6380` | redis, намеренно опубликован на всех интерфейсах |

Приложение читает те же файлы конфигурации, что и сами сервисы, и разговаривает
с настоящим демоном docker. Можно, например, открыть **Конфигурации →
`/etc/nginx/sites-enabled/app.conf`**, сломать синтаксис и сохранить: настоящий
`nginx -t` отклонит правку, файл автоматически вернётся на место, а в журнале
останется точная причина отказа.

Остановить и убрать за собой:

```powershell
docker compose -f stand/docker-compose.yml down -v
```

Флаг `-v` важен: учётная запись администратора живёт в томе, и без него при
пересоздании стенда новый пароль напечатан не будет, а старый уже потерян.

**Что стенд проверяет по-настоящему:** разбор живых конфигов nginx и haproxy,
список контейнеров и сетей через Docker Engine API, управление контейнерами и
цикл правки конфига с настоящей валидацией, включая ветку отказа с автооткатом.

**Чего он не покрывает:**

* systemd — внутри контейнера его нет, источник `services` честно сообщает о
  недоступности, а действия над юнитами не проверить;
* firewall хоста — нет ни прав, ни правил, источник `firewall` недоступен;
* сравнение «объявлено против слушается» для nginx и haproxy — они работают в
  своих сетевых пространствах имён, и `ss` внутри контейнера nkt их сокетов не
  видит. Приложение это распознаёт и молчит, вместо того чтобы объявить весь
  хост мёртвым.

Эти пути проверяются только на настоящей Linux-машине.

### Способ 3. Боевой Linux-хост

Собрать можно прямо с Windows — бинарник статический, кросс-компиляция обычная:

```powershell
$env:GOOS = "linux"; $env:GOARCH = "amd64"; $env:CGO_ENABLED = "0"
go build -trimpath -ldflags "-s -w" -o nkt ./cmd/nkt
```

Дальше на хосте:

```bash
install -m 0755 nkt /usr/local/bin/nkt
install -d -m 0750 /etc/netknownsthat
install -m 0640 deploy/nkt.env.example /etc/netknownsthat/nkt.env
$EDITOR /etc/netknownsthat/nkt.env          # как минимум проверьте NKT_MODE=local

install -m 0644 deploy/netknownsthat.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now netknownsthat
journalctl -u netknownsthat -n 30           # здесь будет пароль администратора
```

Проверить, что всё читается, ещё до запуска сервиса:

```bash
NKT_MODE=local /usr/local/bin/nkt scan
```

Дальше с хостом можно работать прямо из SSH-сессии, без проброса портов и
браузера:

```bash
sudo nkt tui
```

По умолчанию приложение слушает `127.0.0.1:8077`. Наружу отдавайте только через
reverse proxy с TLS и выставьте `NKT_COOKIE_SECURE=true`. Помните, что доступ к
дашборду равносилен root на хосте.

### Терминальный интерфейс

Тот же набор данных и те же действия, что в вебе, но без браузера — удобно,
когда вы уже подключились к хосту по SSH:

```bash
nkt tui
```

Девять экранов, между ними переключение цифрами `1`…`9` или `Tab`:

| Экран | Что показывает и что умеет |
|---|---|
| Обзор | плитки состояния, список проблем, сервисы, firewall, доступность |
| Проблемы | таблица находок с подробностями; `f` фильтрует по серьёзности |
| Карта | дерево «внешняя сеть → слушатель → пул → backend → контейнер → сеть» |
| Доступность | тепловая карта недоступности по часам недели, графики, простои; `p` проверить сейчас, `space` пауза |
| Нагрузка | динамика, рейтинг потребителей и расписание использования; `m` сменить показатель |
| Конфигурации | просмотр и правка файлов; `e` редактор, `v` история версий, `u` откат |
| Сервисы | systemd-юниты и контейнеры; `s` `x` `t` `l` — запуск, стоп, перезапуск, reload; `c` проверить конфиг |
| Firewall | правила ufw и пакетного фильтра; `a` добавить правило, `x` удалить |
| Журнал | все изменения с указанием пользователя и результата |

Общие клавиши: `F5` обновить экран, `r` пересканировать хост, `?` справка,
`q` выход. Графики рисуются блочными символами, тепловые карты — цветным фоном;
серьёзность и состояние везде подписаны словом, а не только цветом.

Правка конфигурации проходит тот же путь, что и в вебе: `Ctrl+S` в редакторе
запускает проверку сервисом, и **если конфиг отклонён, файл автоматически
возвращается в прежнее состояние**.

Две особенности, о которых стоит знать:

* **Терминальный интерфейс не собирает историю.** Пробы, метрики и разбор логов
  выполняет фоновый планировщик, то есть запущенный сервис `netknownsthat`. TUI
  читает ту же базу и показывает то, что уже собрано; на экранах доступности и
  нагрузки без запущенного сервиса будет пусто. Разовую проверку ресурса можно
  сделать вручную клавишей `p`.
* **Входа по паролю нет.** Если вы уже на хосте, вы и так root. Действия
  записываются в журнал под именем `tui:<логин>`, причём под `sudo` берётся
  исходный пользователь, а не `root`. Ограничение `NKT_ALLOW_MUTATIONS=false`
  действует и здесь.

### Режим разработки интерфейса

Два процесса: бэкенд отдаёт API, Vite — интерфейс с горячей перезагрузкой и
проксированием `/api` на бэкенд.

```powershell
.\nkt.exe                       # терминал 1: API на :8077
cd web; npm run dev             # терминал 2: интерфейс на :5173
```

Открывать <http://localhost:5173>. Пересобирать бинарник при этом не нужно.

### Разовая проверка из командной строки

Печатает отчёт и завершается с кодом 2, если есть критичные находки — годится
для cron или как шаг в CI:

```powershell
.\nkt.exe scan
```

### Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| Открывается страница «Фронтенд не собран» | Бинарник собран раньше интерфейса. Выполните `npm run build` в `web/`, затем **заново** `go build` — `go:embed` вшивает файлы при компиляции. |
| `failed to connect to the docker API at npipe:...` | Не запущен Docker Desktop. Стенд и режим `local` без него не работают. |
| Пароль потерян | В режиме `fixtures` удалите каталог `data/` и запустите заново. На стенде — `docker compose -f stand/docker-compose.yml down -v`. На хосте — остановите сервис, удалите `/var/lib/netknownsthat/netknownsthat.db`. |
| `bind: address already in use` | Порт 8077 занят. Задайте другой: `$env:NKT_ADDR = "127.0.0.1:9077"`. |
| На реальном хосте источники `firewall` и `services` недоступны | Нужны права root: `iptables-save` и `systemctl` от обычного пользователя не работают. Запускайте через systemd-юнит из `deploy/`. |
| Все правки конфигов отклоняются с `Read-only file system` | Каталог конфигурации примонтирован только на чтение, либо у процесса нет прав на запись в каталог логов, который открывает `nginx -t`. |
| Изменения запрещены, кнопки неактивны | Либо роль `viewer`, либо выставлено `NKT_ALLOW_MUTATIONS=false`. |
| В консоли Windows вместо русского текста кракозябры | Кодовая страница консоли не UTF-8. Выполните `chcp 65001` перед запуском. Если перенаправляли вывод в файл — читайте его как `Get-Content файл -Encoding UTF8`. |

## Архитектура

```
cmd/nkt                 точка входа, graceful shutdown
internal/config         все настройки из NKT_* переменных
internal/collect        ЕДИНСТВЕННОЕ место, где расходятся fixtures и реальный хост
  ├── local.go          настоящая ФС, exec, unix-сокет docker
  └── fixtures.go       снапшот на диске, заготовленные ответы команд
internal/parse          nginx (crossplane), haproxy (config-parser), docker,
                        iptables, ufw, ss, systemd
internal/model          вендор-нейтральное описание найденного
internal/analyze        правила поиска проблем
internal/topology       построение графа ресурсов
internal/inventory      оркестрация скана, снапшоты, цели мониторинга
internal/monitor        пробы, метрики, access-логи, планировщик
internal/control        сервисы, правка конфигов с версиями, firewall
internal/store          SQLite (modernc, чистый Go — статическая сборка)
internal/api            HTTP API на chi
internal/webui          вшитый фронтенд
internal/tui            терминальный интерфейс на tview
web/                    React + TypeScript, графики на голом SVG
```

Веб-интерфейс и терминальный — два равноправных потребителя одних и тех же
пакетов: оба вызывают `inventory`, `analyze`, `topology` и `control` напрямую,
и ни один не ходит через другой. Поэтому исправление в правилах анализа или в
построителе карты одинаково видно и там, и там.

Ключевое решение — интерфейс `collect.Collector`. Всё остальное приложение
работает с POSIX-путями хоста и не знает, читает оно настоящий сервер или
снапшот, поэтому парсеры и правила одинаково работают и на Windows, и на
боевой машине.

Внешние зависимости: `nginx-go-crossplane` (официальный парсер nginx),
`haproxytech/config-parser` (парсер из HAProxy Dataplane API), `modernc.org/sqlite`,
`go-chi/chi`, `golang.org/x/crypto` (argon2id), `gopkg.in/yaml.v3`.
Docker опрашивается собственным минимальным клиентом Engine API — вместо
трёхсот пакетов официального SDK.

## API

Всё под `/api`, аутентификация — по cookie-сессии.

| Метод | Путь | Роль | Назначение |
|---|---|---|---|
| POST | `/auth/login`, `/auth/logout`, `/auth/password` | — / любая | Вход, выход, смена своего пароля |
| GET | `/overview` | viewer | Сводка для дашборда одним запросом |
| GET | `/inventory`, `/findings`, `/topology` | viewer | Полный снапшот, проблемы, граф |

## Безопасность

* Пароли — argon2id (64 МиБ, t=3, p=2). Сессии — случайные токены в SQLite,
  отзываемые; cookie `HttpOnly`, `SameSite=Lax`.
* Роли: `viewer` — только чтение, `admin` — изменения. Плюс глобальный
  выключатель `NKT_ALLOW_MUTATIONS=false`, переводящий всё приложение в режим
  чтения.
* Защита от перебора: после пяти неудачных попыток вход по учётной записи
  блокируется с нарастающей задержкой.
* Правка конфигов ограничена белым списком каталогов (корни nginx и haproxy,
  перечисленные compose-файлы). Пути с `..` отвергаются.
* Действия над сервисами и firewall принимают только значения из фиксированных
  списков — имя сервиса или действие невозможно подставить в команду.
* Удаление правила ufw сверяется с текстом, который видел оператор: номера
  правил сдвигаются после каждого изменения, и удаление «не того» правила
  способно отрезать SSH.
* Оптимистичная блокировка при сохранении конфига по SHA-256: файл, изменившийся
  на диске после открытия в редакторе, не будет перезаписан молча.
* Каждое изменяющее действие пишется в `audit_log`.

**Доступ к этому приложению равносилен root на хосте.** Слушайте только
localhost или отдавайте через reverse proxy с TLS и отдельной аутентификацией.

## Ограничения

* Один хост. Нет ни агентов, ни сбора с нескольких машин.
* Пишутся только правила `ufw`; прямая правка iptables не поддерживается
  намеренно.
* Из firewall-бэкендов поддержаны iptables/ip6tables и ufw. Чистый `nftables`
  (без слоя iptables-nft) не разбирается.
* Правило `declared-not-listening` требует доступного `ss`; без него сравнивать
  конфиг не с чем, и правило молчит. Оно также молчит, если таблица сокетов не
  подтверждает ни одного объявленного порта — значит, читается чужое сетевое
  пространство имён. Опубликованные порты контейнеров этим правилом не
  проверяются вовсе: при `userland-proxy: false` docker пробрасывает их чистым
  DNAT, и слушателя на хосте не существует; за состояние контейнеров отвечают
  отдельные правила.
* Проверка конфигурации в режиме `fixtures` всегда «успешна» — путь отказа
  валидации проверяется на стенде или на настоящем хосте.
* Из веб-серверов и балансировщиков поддержаны nginx и haproxy. Caddy, Traefik,
  Envoy не разбираются — под них нужен новый файл в `internal/parse`.

## Разработка

```powershell
go test ./...                  # парсеры, анализ, карта, полный скан и TUI
go vet ./...
gofmt -l .
cd web; npm run typecheck
```

Терминальный интерфейс тестируется headless: `tcell` умеет отдавать
симулированный экран, поэтому тест поднимает приложение целиком, нажимает
клавиши и проверяет отрисованные кадры. Панику или неверное поле в любом из
девяти экранов это ловит без настоящего терминала.

Тесты работают против `fixtures/host` — снапшота, в который намеренно заложены
конфликт портов, открытый наружу Redis, контейнер в цикле перезапуска, панель
статистики без пароля, устаревший TLS и неиспользуемое правило firewall.
Тест `TestScanFindsPlantedProblems` проверяет, что анализатор находит каждую из
этих проблем с ожидаемой серьёзностью.

Добавление нового парсера: новый файл в `internal/parse`, возвращающий
`model.Endpoint` / `model.Upstream` / `model.SourceStatus`, и вызов в
`internal/inventory/scan.go`. Всё остальное — карта, анализ, мониторинг,
интерфейс — подхватит его автоматически.
