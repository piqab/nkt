## Как сейчас связываются узлы кластера на разных хостах

Три режима сети между хостами (`internal/hub/cluster_wg.go`,
`internal/control/wgmesh.go`); хаб во всех — только оркестратор, трафик
узлов через хаб не идёт.

- **NAT** — только один хост.
- **Мост** — машины берут адреса из сети хостов; нужен один L2-сегмент.
- **WireGuard** — full mesh между хостами: `wg-quick@nktwg<N>`
  (`10.200.<N>.<i>/24`), сеть машин `10.<100+N>.<i>.0/24` на хост,
  подсети соседей в `AllowedIPs`, `PersistentKeepalive = 25`, endpoint —
  адрес хоста из списка или «адрес для соседей».

| Случай | Сейчас |
|---|---|
| Хосты в разных подсетях, подсети маршрутизируются друг к другу | Работает: WireGuard, между хостами должен проходить UDP 51820; если хаб ходит на хост по адресу, которого сосед не видит — «адрес для соседей». |
| Хосты с белыми IP | Работает: WireGuard, endpoint = белый IP, UDP 51820 открыть во внешнем файрволе. |
| Подсети друг друга не видят | **Не поддерживается**: WireGuard требует прямого UDP-пути, обхода через хаб нет — создание падает на проверке связи по туннелю. |

## Фаза A — WireGuard «через хаб» (звезда)

- [ ] Сухой прогон: хаб может поднять wg (права, пакет), порт открыт, с

## PQC: постквантовая миграция (обсуждено 2026-10-25)

Роль nkt — пройти путь «обнаружить → исправить → доказать» по парку:
видимость (что с TLS и SSH на каждом хосте и снаружи), исправление
профилями и сценариями, отчёт для аудита. Спрос на рынке подтверждается
перечнями криптографии и CBOM (IBM Quantum Safe, Keyfactor, SandboxAQ;
ЕС — начать переход и составить перечни к концу 2026, черновик NIST IR
8547 — RSA/ECC устаревают после 2030, запрещены после 2035); их слабое
место — исправление, а у nkt оно есть.

Целевые ОС: Debian 13 и Ubuntu 26.04 (OpenSSL 3.5 — X25519MLKEM768 в TLS
по умолчанию, OpenSSH 10 — mlkem768x25519); RHEL 10 — политикой. На
Debian 12 / Ubuntu 22.04–24.04 SSH уже гибридный (sntrup761), TLS — нет.

Решения: этапы 1–4 подряд; WireGuard Traffic Fly — Rosenpass; пробы
снаружи — через nkt-edge.

- [ ] **Этап 1 — видимость.** Проба TLS (версия, группа обмена ключами —
      X25519MLKEM768 или классика, алгоритм сертификата) и SSH (что
      предлагает сервер, о чём договорились, тип ключа хоста) с nkt-edge и
      с хаба; разбор `sshd -T` (KexAlgorithms, HostKeyAlgorithms),
      гибридные группы nginx/HAProxy/Caddy; находки «PQC-готовность»
      (OpenSSL 3.0, KEX без mlkem/sntrup, `ssl_ecdh_curve` без гибрида,
      только TLS 1.2, сертификаты RSA — в список на смену подписей).
- [ ] **Этап 2 — раздел «Криптография».** Сводка по парку, фильтры (хост,
      порт, ОС), переход к находке и исправлению, отчёт CSV/JSON и
      экспорт **CycloneDX CBOM** (сверить версию формата с разделом
      криптоактивов).
- [ ] **Этап 3 — исправление.** Профиль «SSH: гибридный KEX» с `sshd -t`
      и откатом; сниппеты гибридных групп для прокси (только если
      библиотека умеет, иначе находка «сначала обновите ОС»); сценарий
      «обновить пакеты/ОС и проверить снаружи»; **фасад** — сценарий
      «Traffic Fly с сертификатом на шлюзе перед старым хостом» и
      отметка «защищено фасадом» в «Криптографии».
- [ ] **Этап 4 — свои каналы nkt.** Тест, что HTTPS хаба, nkt-edge, агент
      и SSH хаб → хост согласуют гибрид (Go 1.26, x/crypto 0.57, ничего
      не отключено); **Rosenpass** в Traffic Fly (ключи генерируются на
      месте, хаб раздаёт только публичные, отдельный UDP-порт шлюза,
      галочка «Постквантовый туннель», в сводке «PQ: да/нет»; бинарник
      0.2.2 из релиза с проверкой sha256 — пакета в Debian нет, сверить);
      учёт ключей и сертификатов nkt (ed25519, ECDSA) на смену подписей.
