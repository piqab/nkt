# Traffic Fly: вход из интернета через VPS

Сервис стоит дома или в офисе за NAT, а пользователям нужен адрес в
интернете. **Traffic Fly** принимает трафик на дешёвом VPS с белым
адресом и отдаёт его по туннелю WireGuard на хосты — в контейнер, в
виртуальную машину, в LXD или в службу самого хоста. Клиент виден целям
под **своим настоящим IP**, работают **TCP и UDP**, а на одном порту
можно держать **пул целей с балансировкой** и проверками.

Настраивает всё хаб — во вкладке **«Выкладки» → «Traffic Fly»**, но
работают шлюз и хосты **без хаба**: туннели, правила и маршрутизатор
поднимаются сами после перезагрузки.

![Traffic Fly: карта и маршруты](/screens/ru/traffic-fly.png)

## Схема

```
клиенты ──80/443 по имени, TCP/UDP-порты──▶ VPS: nkt-edge (роль fly)
                                               │  WireGuard 51820/udp
                                               ▼
                                хост: туннель nkt-flyN → DNAT → контейнер,
                                машина, LXD, служба хоста, адрес в его сети
```

- **Шлюз** — VPS с [nkt-edge](/guide/edge) в роли `fly`. На шлюзе
  работает отдельная служба `nkt-fly` (root): WireGuard-интерфейс
  `nkt-fly`, правила nftables и маршрутизатор по именам. Сам edge
  остаётся без прав и только передаёт ей команды хаба по туннелю.
- **Хост** — у каждого хоста по туннелю к каждому шлюзу (`nkt-flyN`,
  `wg-quick@nkt-flyN`). Закрытые ключи создаются на своей машине и
  никуда не уходят — хаб видит только публичные.
- Ответы целей уходят обратно в тот же туннель по метке соединения —
  маршрут хоста по умолчанию не меняется.

## Маршруты

| Вид | Что | IP клиента |
|---|---|---|
| **HTTPS по имени** | порт 443, выбор по SNI; TLS не расшифровывается — сертификат у цели | PROXY protocol v2 |
| **HTTP по имени** | порт 80, выбор по заголовку `Host` | PROXY protocol v2 |
| **TCP-порт**, **UDP-порт**, **TCP+UDP** | порт целиком — в пул | настоящий, без доработок цели |

- **80 и 443 делятся по именам**: `app.example.com`, `*.example.com`;
  точное имя важнее маски. Одно имя — один маршрут.
- **Остальные порты**: один порт шлюза — один пул. Нужен второй пул на
  том же порту — возьмите другой порт или второй шлюз (VPS с другим
  адресом).
- Маршрут по имени передаёт IP клиента **PROXY protocol v2**: цель должна
  его принимать (nginx `listen 443 proxy_protocol`, Caddy, HAProxy,
  Traefik). Без галочки цель увидит адрес шлюза в туннеле.
- Маршрут по порту идёт **через ядро** (DNAT без подмены источника): цель
  видит настоящий адрес клиента сама.

## Пулы и балансировка

В маршруте — одна или несколько **целей**: хост и что на нём
(контейнер, машина, LXD-инстанс, сам хост или адрес в сети хоста) и
порт. Адрес контейнера или машины хаб узнаёт при применении.

![Маршрут: имена, балансировка, цели](/screens/ru/traffic-fly-edit.png)

| Балансировка | Где |
|---|---|
| **меньше соединений** | маршруты по имени |
| **по кругу** | везде |
| **по IP клиента (липко)** | везде; клиент держится одной цели |

- **Вес** — доля трафика цели относительно остальных.
- **Вывод** (drain) — новых соединений цель не получает, текущие
  доживают; так цель выводят на обслуживание.
- **Проверка**: TCP-подключение, HTTP-запрос (путь и код ответа) или без
  проверки; можно указать отдельный порт проверки. Цель считается
  недоступной после 3 неудач подряд и снова живой после 2 удач; проверка
  — раз в 5 с. Недоступная цель убирается из пула сразу, в том числе для
  маршрутов по порту. UDP-маршруту нужен TCP-порт проверки или «без
  проверки».

## Карта и сводка

Вверху вкладки — **карта**: шлюзы → маршруты → хосты → цели. Цвет —
состояние (зелёный — все живы, жёлтый — часть, красный — никого), толщина
связи — число активных соединений; карта обновляется раз в 5 с. Щелчок по
маршруту — подробности: цели с проверкой, откликом и соединениями,
трафик и число клиентов. **Администратор** видит адреса клиентов, пока
их не больше 30; дальше — только число. Наблюдатели видят карту и число
клиентов, адресов — нет.

## Правка, история и применение

- Маршрут меняет администратор; запись — через окно с **диффом** и
  пометкой, каждая запись — новая **версия**. Две правки одновременно не
  перезапишут друг друга: вторая получит отказ.
- **«История»** — разница между версиями и возврат любой из них.
- **«Сухой прогон»** — задание собирает конфигурации шлюзов и хостов,
  проверяет ключи и адреса целей, но ничего не записывает.
- **«Применить»** — задание по шагам: ключи шлюзов → ключи хостов и
  адреса целей → хосты (туннели, DNAT) → шлюзы (туннели, правила,
  маршрутизатор). Хосты раньше шлюзов: трафик пойдёт, когда туннели уже
  готовы. Хост или шлюз, которому больше нечего делать, снимает свои
  туннели и правила.
- На хост ставятся `wireguard-tools` и `nftables`, если их нет; на шлюз —
  при установке edge.

## Шлюз

**«Добавить шлюз»** открывает установку [nkt-edge](/guide/edge#установка-из-хаба)
с ролью `fly`: имя и сертификат не нужны, 80/443 шлюза принадлежат
маршрутам. Поэтому роль `fly` не совмещается с вебхуками, API и
колбэками — для них нужен отдельный edge; проверки снаружи (`probe`)
совмещать можно. Если на VPS включён `ufw`, шлюз сам открывает 51820/udp
и порты маршрутов по имени.

## События

Хаб раз в минуту сверяет сводки шлюзов и пишет в
[оповещения](/guide/hub-operations#оповещения): **цель недоступна / снова жива**,
**в пуле нет живых целей**, **туннель упал / поднялся**. Telegram, Slack,
исходящие вебхуки и узел n8n получают их как остальные события.

## Если не работает

| Признак | Что проверить |
|---|---|
| Шлюз «нет связи» | edge на связи с хабом? `systemctl status nkt-edge nkt-fly` на VPS |
| Туннель не поднимается | под шлюзом в «Шлюзах» написана причина: «хост ещё не настроен» — «Применить» до него не дошло; «UDP 51820 блокируется» — хост шлёт, шлюз не получает: откройте 51820/udp в файрволе провайдера VPS (и исходящий UDP у хоста); «ключи не сошлись» — «Применить» ещё раз; «туннель на хосте не поднят» — `systemctl status wg-quick@nkt-flyN` на хосте |
| «Хост не ответил за 20 с» | открывается ли страница хоста в хабе; `systemctl status netknownsthat` на хосте |
| «nkt не умеет Traffic Fly» | обновите nkt на хосте (нужен 1.13.12 или новее) |
| Цель «недоступна» | порт цели и проверки; контейнер слушает на своём адресе, а не только на 127.0.0.1 |
| Цель видит адрес 10.77.x.1 | маршрут по имени без PROXY protocol — включите галочку и настройте цель |
| Имя не открывается | DNS имени указывает на адрес шлюза; на 443 нет другого сервера |
