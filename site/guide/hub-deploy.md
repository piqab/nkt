# Выкладки: из Git — в кластеры и на хосты

Раздел хаба **«Выкладки»** выкладывает ваши приложения из репозитория Git:
манифестом в кластеры Kubernetes, Helm-релизом или сценарием хаба. Сборку
образов и тесты делает ваш CI (GitHub Actions, GitLab CI) или вы сами —
nkt берёт на себя вторую половину: «готово → выложить».

## Конвейер

Конвейер описывается в YAML (правка — в окне с диффом, у описания есть
история редакций):

```yaml
repo: https://github.com/org/app.git
ref: main                 # push в эту ветку — выкладка
# tags: "v*"              # или теги репозитория по шаблону

action: manifest          # manifest | helm | script
manifests: [deploy/k8s.yaml]
clusters: [prod]          # кластеры хаба
# group: prod             # или кластеры группы хостов

# poll: 5m                # опрос репозитория
# registry: ghcr.io/org/app
# registry_tags: '^v?\d+\.\d+\.\d+$'
```

- **manifest** — файлы манифестов из репозитория, `kubectl apply` на
  control plane каждого кластера; каждое применение попадает и в
  библиотеку манифестов хаба.
- **helm** — чарт из репозитория чартов, values — файлом из Git;
  `tag_key: image.tag` подставит тег образа.
- **script** — сценарий хаба из репозитория (параметры `TAG`, `COMMIT`,
  `REF`): `git pull` и `docker compose up`, перезапуск службы, миграции.

В манифестах и values подставляются `{{nkt.tag}}`, `{{nkt.commit}}` и
`{{nkt.ref}}`.

## Когда выкладывать

- **Кнопка «Выложить»** — вершина ветки или указанный тег.
- **Вебхук** — push в ветку или тег по шаблону. Подпись обязательна:
  GitHub и Gitea — HMAC-SHA256, GitLab — секретный токен, из шага CI —
  подпись nkt с отметкой времени (пример — в окне «Вебхук»). Повтор той
  же доставки отвергается; сам вебхук ничего не выбирает — что и куда
  выкладывать, задано в описании.
- **Опрос** (`poll`) — хаб сам видит новый коммит в ветке.
- **Registry** (`registry`) — хаб следит за тегами образа и выкладывает
  новейший, подходящий под шаблон.

Опрос и registry начинают работать после первой выкладки кнопкой —
новый конвейер сам ничего не выкладывает.

## Доступ и секреты

Токен или ключ развёртывания для закрытого репозитория и логин:токен
закрытого registry хранятся на хабе зашифрованными; показать их нельзя,
только заменить или убрать. Секрет вебхука показывается администратору с
записью в журнал действий и меняется одной кнопкой.

## История и откат

Каждая выкладка — задание хаба с журналом: что (коммит, тег), кто
запустил (кнопка, вебхук, опрос, registry), чем кончилось. «Откатить»
выкладывает заново коммит и тег прежней удачной выкладки.

## Хаб не виден из интернета

Вебхуку нужен адрес, доступный GitHub. Если хаб дома или в офисе за NAT:

- включите опрос репозитория или registry — открывать ничего не нужно;
- или поставьте на VPS **nkt-edge** — маленькую отдельную программу с
  сертификатом Let's Encrypt, которая принимает только вебхуки и
  передаёт их хабу по туннелю, который хаб сам к ней держит.

## nkt-edge: вебхуки без открытого хаба

**nkt-edge** — отдельная маленькая программа (около 8 МБ) для VPS с белым
адресом:

```
GitHub / GitLab / CI ──HTTPS (Let's Encrypt)──▶ VPS: nkt-edge
                                                  ▲
                                   туннель от хаба (TLS, токен)
                                                  │
                                    хаб за NAT, без открытых портов
```

- Хаб сам подключается к edge и держит соединение; адрес хаба может
  меняться, белый IP ему не нужен.
- Edge принимает только `POST /hooks/{id}` (тело до 1 МБ, ограничение
  частоты, по желанию — только адреса GitHub) и передаёт запрос хабу. Через
  туннель хаб обслуживает один этот маршрут: интерфейс и API хаба через
  edge недоступны.
- На edge нет ни базы, ни секретов конвейеров, ни доступа к хостам: подпись
  проверяет хаб. Захваченный VPS может лишь слать запросы, которые хаб без
  верной подписи отвергнет.
- Туннель — TLS 1.3 с закреплённым отпечатком сертификата edge и токеном.

**Установка из хаба:** добавьте VPS как обычный хост, заведите A-запись
домена (например `hooks.example.com`) на его адрес, затем «Выкладки» →
nkt-edge → «Установить на хост». Задание зальёт программу под архитектуру
хоста, поставит службу с минимальными правами (отдельный пользователь,
только привязка к 80 и 443), откроет 80, 443 и 8444 в ufw, запомнит
отпечаток сертификата туннеля и подключит хаб. После этого в окне
«Вебхук» конвейера появится адрес `https://hooks.example.com/hooks/…`.

**Вручную:** бинарник `nkt-edge-linux-<arch>` из релиза в
`/usr/local/bin/nkt-edge`, юнит
[`deploy/nkt-edge.service`](https://github.com/piqab/nkt/blob/main/deploy/nkt-edge.service),
настройки [`deploy/edge.env.example`](https://github.com/piqab/nkt/blob/main/deploy/edge.env.example)
в `/etc/nkt-edge/edge.env` (0600), затем «Настроить вручную» в хабе:
адрес `хост:8444`, домен и тот же `EDGE_TOKEN`.
