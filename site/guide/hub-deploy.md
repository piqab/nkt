# Выкладки: из Git — в кластеры и на хосты

Раздел хаба **«Выкладки»** выкладывает ваши приложения из репозитория
Git: манифестом в кластеры Kubernetes, Helm-релизом или сценарием хаба.
Сборку образов и тесты делает ваш CI (GitHub Actions, GitLab CI, Gitea)
или вы сами — nkt берёт на себя вторую половину: «готово → выложить».

![Выкладки](/screens/ru/deployments.png)

Почему так: ключи от хостов и кластеров остаются на хабе. CI получает
только право «дёрнуть» вебхук конкретного конвейера, а что и куда
выкладывать, решает описание на хабе — из запроса берутся лишь ветка,
коммит и тег.

## Конвейер

«Новый конвейер» → имя и описание в YAML. Правка — в окне с диффом, у
описания есть история редакций с заметками; перед записью оно
проверяется. Секретов в описании нет — они в «Доступе».

```yaml
repo: https://github.com/org/app.git
ref: main                 # push в эту ветку — выкладка
tags: "v*"                # и/или теги репозитория по шаблону

action: manifest          # manifest | helm | script
manifests: [deploy/k8s.yaml]
clusters: [prod]          # кластеры хаба
# group: prod             # или кластеры хостов группы

# poll: 5m                # опрашивать репозиторий
# registry: ghcr.io/org/app
# registry_tags: '^v?\d+\.\d+\.\d+$'
# registry_poll: 5m
```

### Все поля

| Поле | Для чего | Значение |
|---|---|---|
| `repo` | всегда | `https://…`, `ssh://…` или `git@host:path`. Логин и пароль в адрес не пишутся — токен или ключ задаются в «Доступе» |
| `ref` | ветка | Push в неё — выкладка её вершины. Нужен `ref` или `tags` |
| `tags` | теги | Шаблон (glob, `v*`): тег репозитория по нему — выкладка этого тега |
| `action` | всегда | `manifest`, `helm` или `script` |
| `manifests` | manifest | Список файлов в репозитории |
| `clusters` | manifest, helm | Имена кластеров из раздела «Кластеры» |
| `group` | manifest, helm | Группа хостов: все кластеры, чей первый control plane в этой группе. Можно вместе с `clusters` |
| `helm.repo_name`, `helm.repo_url` | helm | Репозиторий чартов (`helm repo add`) или `oci://…` |
| `helm.chart`, `helm.version` | helm | Чарт и версия (пусто — последняя) |
| `helm.release`, `helm.namespace` | helm | Имя релиза и namespace |
| `helm.values` | helm | Файл values в репозитории |
| `helm.tag_key` | helm | Ключ values, куда подставить тег образа: `image.tag` |
| `script` | script | Сценарий хаба в репозитории (`deploy/deploy.nkt`) |
| `poll` | триггер | Интервал опроса ветки, не короче `1m` |
| `registry` | триггер | Образ, за тегами которого следить: `ghcr.io/org/app`, `org/app` (Docker Hub), `registry.example.com:5000/app` |
| `registry_tags` | триггер | Регулярное выражение подходящих тегов; по умолчанию `^v?\d+(\.\d+){1,2}$` |
| `registry_poll` | триггер | Интервал проверки registry, по умолчанию `5m` |

Все значения проверяются по отдельности: ветки, теги и пути — по строгим
шаблонам, `git` вызывается с `--`, файлы читаются только внутри checkout
(выход наружу, в том числе ссылкой, запрещён).

### Подстановки

В манифестах и values подставляются:

| Подстановка | Значение |
|---|---|
| <code v-pre>{{nkt.tag}}</code> | тег из запроса, кнопки или registry; без тега — короткий коммит (12 знаков) |
| <code v-pre>{{nkt.commit}}</code> | полный коммит |
| <code v-pre>{{nkt.ref}}</code> | ветка или тег репозитория |

В сценарии те же значения приходят параметрами `TAG`, `COMMIT`, `REF`
(`param TAG "тег образа"` в начале сценария).

## Действия

- **manifest** — файлы манифестов из репозитория склеиваются, в них
  делаются подстановки, и на control plane каждого кластера идёт
  `kubectl apply` (через API узла, по тому же каналу, что и остальные
  запросы к хосту). Каждое применение попадает в библиотеку манифестов
  хаба («Кластеры» → «Манифесты») с заметкой `pipeline <имя> <коммит>`.
- **helm** — `helm upgrade --install` в каждом кластере: values из файла,
  тег — в `tag_key`. На control plane нужен Helm — если его нет,
  поставьте кнопкой «Установить Helm» во вкладке Kubernetes узла.
- **script** — сценарий хаба из репозитория: `docker stack … up`,
  `git clone`, перезапуск службы, `wait … http` — всё, что умеет
  [язык сценариев](/guide/hub-scripts). Кластер не нужен.

Кластеры берутся только в статусе «готов». Если выкладка не удалась в
части кластеров, задание кончается ошибкой «не удалась в N из M», а в
журнале видно, где и почему.

## Compose-стек

Действие **compose** выкладывает docker compose-стек из репозитория на
хосты хаба — **по очереди**:

```yaml
repo: https://codeberg.org/me/shop.git
ref: main
action: compose
compose:
  file: deploy/docker-compose.yml   # compose-файл в репозитории
  project: shop                     # стек на хосте: /srv/compose/shop
  hosts: [web1, web2]               # или group: prod; машина хаба — localhost
  files: [deploy/nginx.conf, deploy/conf/]  # что ещё нужно стеку
  wait_timeout: 5m                  # ждать подъёма и healthcheck
  site: shop.example.com            # после выкладки проверить по HTTPS (или блоком — см. ниже)
```

- В compose-файле и файлах рядом делаются [подстановки](#подстановки):
  <code v-pre>image: ghcr.io/org/shop:{{nkt.tag}}</code>.
- Файлы из `files` (каталоги — целиком) должны лежать **внутри каталога
  compose-файла**: на хосте стек — этот каталог, и относительные ссылки
  compose (`./nginx.conf`) должны остаться верными. Только текстовые
  файлы; двоичным место в образе.
- На каждом хосте: файлы пишутся в `/srv/compose/<project>` с историей
  версий, затем `docker compose config` проверяет стек — если не принял,
  файлы возвращаются как были. Дальше заданием хоста — `pull` и
  `up -d --remove-orphans --wait`: задание ждёт, пока контейнеры
  поднимутся и пройдут healthcheck. **Следующий хост — только после
  успеха предыдущего**; первая неудача останавливает выкладку.
- Без Docker — Podman (`podman compose`): ожидание — пока все
  контейнеры проекта работают и здоровы.
- Перед первым хостом хаб спрашивает у всех хостов, есть ли docker (или
  podman) и работает ли compose. Если где-то нет — выкладка не
  начинается, и ни один хост не тронут: иначе часть хостов обновилась бы,
  а на остальных стек остался бы прежним.
- Только готовые образы: сервис с `build:` без `image:` хаб отвергнет
  до обращения к хостам — сборку делает CI.
- **`.env` стека** задаётся в «Доступе» конвейера: хранится на хабе
  зашифрованным, на хост пишется с правами 0600, в историю версий и
  журналы не попадает.

**Compose по ссылке.** В окне нового конвейера — вставьте ссылку на
compose-файл (GitHub `…/blob/<ветка>/<путь>`, GitLab `…/-/blob/…`,
Codeberg/Gitea/Forgejo `…/src/branch/…`, их raw-варианты), выберите
хосты — описание заполнится само: репозиторий, ветка, путь, имя стека.
Дальше — обычная правка с диффом.

![Compose по ссылке](/screens/ru/deploy-compose.png)

Хосты проверяются **сразу при выборе**: рядом с именем — «docker с compose
— готов», «нет docker и podman» или «docker без compose». Где нет —
кнопка **«Установить Docker»** (или «Установить compose»): `docker.io` и
плагин compose из репозитория дистрибутива, фоновым заданием хоста в
стандартном окне журнала. Уже стоящий docker (в том числе `docker-ce` из
репозитория Docker) не трогается — доставляется только compose. Та же
проверка — в мастере «Сайтов», когда цель — сервис стека.

**Сухой прогон** — кнопка в окне «Выложить» и в редакторе конвейера (там
проверяется текущий текст, в том числе несохранённый). Делает всё, что
сделала бы выкладка, кроме изменений: берёт репозиторий, делает
подстановки, собирает файлы стека, и на каждом хосте:

- docker или podman и версия compose;
- стек новый или есть — какие файлы появятся, изменятся, останутся, что
  с `.env`;
- `compose config` на копии стека во временном каталоге рядом со
  стеками (сам стек и контейнеры не трогаются, копия удаляется);
- сервисы и образы: есть ли образ в registry (только манифест, без
  скачивания), скачан ли на хост. «В registry нет» — ошибка; «проверить
  не удалось» (закрытый registry без входа, podman без skopeo) —
  предупреждение.

Итог — задание хаба с журналом: «выкладка прошла бы» или число проблем.
Запись в историю выкладок не делается.

![Сухой прогон](/screens/ru/deploy-dryrun.png)

**Пример: httpbin.** В репозитории nkt —
[`examples/httpbin`](https://github.com/piqab/nkt/tree/main/examples/httpbin):
стек [go-httpbin](https://github.com/mccutchen/go-httpbin) на готовом образе
`mccutchen/go-httpbin:2.25.0` и конвейер к нему. Выкладывается прямо по
ссылке `https://github.com/piqab/nkt/blob/main/examples/httpbin/deploy/docker-compose.yml`
(имя стека — `httpbin`) или кнопкой **«Пример: httpbin»** в окне нового
конвейера: она заполнит ссылку и имена, останется выбрать хост. Сайт —
блоком `site:` в конвейере (закомментирован в описании) или вручную в
«Сайтах»: стек `httpbin`, сервис `httpbin`, порт 8080. Compose-файл оригинала,
[postmanlabs/httpbin](https://github.com/postmanlabs/httpbin), собирает
образ из исходников (`build: '.'`) — его хаб отвергнет с объяснением.

## Сайты

Вкладка **«Сайты»** — домен на хосте за прокси с сертификатом Let's
Encrypt:

![Новый сайт](/screens/ru/deploy-sites.png)

1. **Хост и имена → «Проверить».** С хаба (то есть снаружи): указывает
   ли каждое имя на хост, и отвечают ли порты 80 и 443. «Свободен»
   (отказ соединения) — путь открыт, certbot сам встанет на порт; «нет
   ответа» — порт, скорее всего, закрыт файрволом провайдера или NAT, и
   Let's Encrypt до хоста не дойдёт. Если имя ведёт в частную сеть —
   пометка: хаб видит порты изнутри. С хоста — какие прокси установлены
   и работают, кто держит 80/443, стеки в `/srv/compose` с сервисами и
   портами, файрвол.
2. **Прокси:** nginx, HAProxy или Caddy — показано, что установлено и
   что работает. Если не установлено ничего — ставится nginx. Если
   80/443 держит контейнер (Traefik, свой Caddy) — предупреждение: такой
   прокси nkt не настраивает.
3. **Цель:** сервис compose-стека (стек, сервис, порт контейнера) или
   `адрес:порт` (приложение не в compose). Неопубликованный порт сервиса
   nkt публикует **только на 127.0.0.1** — файлом `compose.nkt.yml`
   рядом со стеком (выкладка и профили его учитывают), так что наружу
   сервис доступен лишь через прокси. Уже опубликованный на всех адресах
   порт используется как есть, с предупреждением.
4. **«Настроить»** — задание хаба: DNS и порты, прокси (установка, если
   нужно), затем задание хоста — открыть 80/443 в ufw/firewalld (по
   галочке), опубликовать сервис, **сертификат** (действующий дольше 20
   дней — как есть, иначе `certbot certonly --standalone`: прокси на
   время выпуска останавливается и запускается снова; продлевает nkt
   так же), **конфигурация прокси** через «Конфигурации» — с проверкой
   (`nginx -t`, `haproxy -c`, `caddy validate`), откатом при ошибке и
   историей версий:
   - nginx — `conf.d/nkt-<домен>.conf`: 80 → редирект на HTTPS, 443 с
     HTTP/2, WebSocket и заголовками `X-Forwarded-*`;
   - HAProxy — блок `nkt-sites` в `haproxy.cfg` (все сайты nkt хоста:
     frontend 80/443 с SNI и backend на сайт), сертификат — объединённым
     PEM в `/etc/haproxy/nkt-certs`; если 80/443 уже слушает другой
     frontend — отказ с объяснением;
   - Caddy — `/etc/caddy/nkt/<домен>.caddy`, подключённый из Caddyfile;
     сертификат Caddy получает и продлевает сам (ключи certbot ему, не
     root, не прочитать).
5. **Проверка HTTPS снаружи** — код ответа и срок сертификата; «Проверить»
   в строке сайта повторяет её в любой момент.

«Удалить» убирает сайт из хаба, по галочке — и конфигурацию прокси на
хосте (с записью в историю); сертификат и публикация сервиса остаются.

### Сайт в конвейере

Сайт можно описать прямо в конвейере `action: compose` — блоком `site:`
вместо строки:

```yaml
compose:
  file: deploy/docker-compose.yml
  project: shop
  hosts: [web1]                  # сайт — только при одном хосте
  site:
    domains: [shop.example.com, www.shop.example.com]
    service: web                 # сервис стека
    port: 80                     # порт контейнера
    proxy: nginx                 # необязательно: иначе какой есть на хосте, нет ни одного — nginx
    firewall: true               # открыть 80/443 (по умолчанию да)
```

- **Первая выкладка:** стек, затем сайт — тем же путём, что «Настроить» в
  мастере (DNS и порты снаружи, прокси, публикация на 127.0.0.1,
  сертификат, конфигурация, HTTPS). Сайт появляется во вкладке «Сайты» с
  пометкой «конвейер …».
- **Следующие выкладки:** сайт настроен и в `site:` ничего не менялось —
  только проверка HTTPS, сертификат заново не выпускается. Поменялись
  имена, сервис, порт, прокси или хост — сайт настраивается заново (со
  старого хоста конфигурация прокси убирается).
- **Не настроился** (DNS ещё не указывает на хост, порт 80 закрыт) —
  выкладка всё равно удалась: стек обновлён. Причина — в журнале
  выкладки и у сайта во вкладке «Сайты».
- **Сухой прогон** показывает, что будет с сайтом: прокси (или что он
  будет установлен), DNS и порты снаружи, есть ли такой сервис в стеке.
- Строка `site: имя` по-прежнему — только проверка HTTPS после выкладки.
- Правка такого сайта в мастере сработает, но следующая выкладка вернёт
  настройки из `site:`, если они расходятся.

## Когда выкладывать

- **Кнопка «Выложить»** — вершина ветки из описания; можно указать
  другую ветку или тег репозитория и тег образа.
- **Вебхук** — push в ветку `ref` или тег по шаблону `tags`; запрос из
  CI с тегом образа (см. ниже).
- **Опрос** (`poll`) — хаб сам видит новый коммит в ветке.
- **Registry** (`registry`) — хаб видит новый тег образа, новее прежнего
  (сравнение по числам: `v1.10.0` новее `v1.9.3`), и выкладывает ветку
  `ref` с этим тегом.

Опрос и registry начинают работать **после первой выкладки кнопкой** —
только что сохранённый конвейер сам ничего не выкладывает. Выключенный
конвейер («Включён» снят) не реагирует ни на что, кроме кнопки. Пока
выкладка конвейера идёт, новая от опроса не запускается.

## Вебхук

Окно **«Вебхук»** конвейера: адрес (напрямую к хабу —
`https://хаб/api/hub/hooks/<id>`, и через [nkt-edge](/guide/edge), если
он настроен), «Показать секрет» (с записью в журнал действий), «Новый
секрет» и готовые инструкции для GitHub, GitLab и шага CI.

Подпись обязательна; поддерживаются:

| Отправитель | Заголовки | Проверка |
|---|---|---|
| GitHub | `X-Hub-Signature-256: sha256=…`, `X-GitHub-Delivery` | HMAC-SHA256 тела |
| Gitea, Forgejo | `X-Gitea-Signature` / `X-Forgejo-Signature` | HMAC-SHA256 тела |
| GitLab | `X-Gitlab-Token` | секрет как есть |
| Шаг CI (nkt) | `X-NKT-Timestamp`, `X-NKT-Signature` | HMAC-SHA256 строки `<отметка>.<тело>`, отметка не старше 5 минут |

- **Повтор той же доставки** отвергается: хаб помнит идентификаторы
  доставок (у подписи nkt — саму подпись).
- **Ответы** скупые: и неизвестный адрес, и неверная подпись — `401`,
  чтобы подбором нельзя было узнать настоящий. Тело — до 1 МБ.
- `ping` от GitHub отвечает `pong`.
- Из тела берутся только `ref` (`refs/heads/…` или `refs/tags/…`),
  коммит (`after`, `checkout_sha` или `commit`) и `tag`. Удаление ветки
  или тега, другая ветка, тег не по шаблону — `200` с `ignored` и
  причиной.

**Подпись nkt из шага CI** — когда образ уже собран и нужно выложить
ветку с его тегом:

```bash
BODY=$(printf '{"ref":"refs/heads/main","commit":"%s","tag":"%s"}' "$SHA" "$TAG")
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$NKT_HOOK_SECRET" -hex | sed 's/^.* //')
curl -fsS -X POST "$NKT_HOOK_URL" \
  -H "Content-Type: application/json" \
  -H "X-NKT-Timestamp: $TS" -H "X-NKT-Signature: $SIG" \
  -d "$BODY"
```

Без `ref` (только `{"tag":"v1.2.3"}`) хаб выложит ветку из описания с
этим тегом. Ответ `202` — `{"status":"deploying","deployment_id":…}`.

Готовые конвейеры CI — на странице [Примеры CI/CD](/guide/cicd-examples).

## Доступ и секреты

«Доступ» конвейера:

- **Репозиторий** — токен (для `https://`, например GitHub fine-grained
  с Contents: read) или закрытый ключ развёртывания (для `ssh`/`git@`).
- **Registry** — `логин:токен` для закрытого registry (для слежения за
  тегами).
- **.env стека** — для `action: compose`: переменные окружения стека
  (`KEY=значение` по строке).

Хранятся на хабе зашифрованными, в описание, журналы и командные строки
не попадают (git получает их через окружение); показать нельзя — только
заменить или убрать. Хабу нужна программа `git` (в образе хаба она есть):
если её нет, на вкладке «Конвейеры» — плашка и кнопка **«Установить git»**
(пакет из репозитория дистрибутива, фоновым заданием машины хаба).

## История и откат

Каждая выкладка — задание хаба с журналом: что (коммит, ветка, тег),
кто запустил (кнопка, вебхук, опрос, registry, откат), когда и чем
кончилось. **«Откатить»** у прежней удачной выкладки выкладывает заново
её коммит и тег — образ уже лежит в registry, пересборки нет.

Удаление конвейера удаляет его историю; выложенное в кластерах и на
хостах остаётся.

## Пример

Готовый пример — [`examples/hello-app`](https://github.com/piqab/nkt/tree/main/examples/hello-app):
приложение на Python, Dockerfile, CI для GitHub Actions, GitLab CI и
Gitea Actions и три варианта выкладки — манифест, Helm, хост с Docker
Compose. Разбор по шагам — [Примеры CI/CD](/guide/cicd-examples).

## Хаб не виден из интернета

- Включите **опрос** репозитория или **registry** — открывать ничего не
  нужно.
- Или поставьте на VPS **[nkt-edge](/guide/edge)** — маленькую программу
  с сертификатом Let's Encrypt, которая принимает только вебхуки и
  передаёт их хабу по туннелю, который хаб сам к ней держит.

## Если не выкладывается

| Симптом | Причина и что делать |
|---|---|
| Вебхук `401` | Неверный секрет или подпись; повтор доставки («Redeliver» в GitHub шлёт тот же ID); у подписи nkt — часы CI и хаба расходятся больше чем на 5 минут. Причина — в журнале действий хаба (`pipeline.hook.rejected`) |
| `200 ignored: другая ветка` | Push не в `ref`; тег — не по шаблону `tags` |
| `ни один кластер не подходит` | Имена в `clusters` не совпадают с разделом «Кластеры», у группы нет кластеров или кластер не «готов» |
| `на хабе нет программы git` | Кнопка «Установить git» на вкладке «Конвейеры» или `apt install git` на машине хаба |
| `в репозитории нет ветки или тега` | Опечатка в `ref`, тег ещё не отправлен (`git push origin v1.0.0`) |
| `git …: Authentication failed` / `Permission denied (publickey)` | Закрытый репозиторий без «Доступа», у токена нет права чтения, ключ не добавлен как deploy key |
| `в репозитории нет файла …` | Путь в `manifests`, `helm.values` или `script` — от корня репозитория |
| `Helm на хосте не установлен` | Поставьте Helm на control plane: вкладка Kubernetes узла → Helm → «Установить Helm» |
| Поды `ImagePullBackOff` | Образ закрытый: сделайте пакет публичным или добавьте в кластер `imagePullSecret`; тег образа не совпадает с тем, что собрал CI |
| Опрос или registry молчат | Первой выкладки кнопкой ещё не было; конвейер выключен; `registry_tags` не пропускает теги (по умолчанию — только версии вида `1.2.3`) |
| `выкладка этого конвейера уже идёт` | Дождитесь конца текущей — журнал в «Истории» |
