# Кластеры Kubernetes

::: warning Экспериментальная возможность
Кластеры на нескольких хостах, WireGuard между хостами и Cilium
обкатаны на тестовых стендах. Перед настоящим созданием — «сухой прогон»,
после — журнал задания.

Раздел, карточка «Кластеры» в списке хостов и «Новый кластер» видны, если
в «О системе» → «Экспериментальные функции» включены «Кластеры
Kubernetes» (уже созданные кластеры работают и без этого).
:::

Хаб собирает кластер из машин на хостах с виртуализацией (и, если
нужно, из самих хостов): создаёт машины из облачного образа, ставит в
них nkt, а nkt на каждом узле выполняет шаги установки k3s или kubeadm.
Узлы — обычные машины хаба под своим хостом; kubeconfig лежит в
карточке кластера.

Пошагово от создания до тестового пода, открытого снаружи через Ingress и
Traffic Fly, — [Кластер: от нуля до первого пода](/guide/k8s-first-pod).

## Кластер на одном хосте

«Новый кластер» у хоста с виртуализацией: вариант (**k3s** или
**kubeadm**), **версия Kubernetes** (актуальная stable по умолчанию и три
предыдущие ветки), топология — одна машина / 1 control plane + N worker /
3 control plane + N worker (у kubeadm — с **общим адресом control plane**,
ниже), размеры машин, образ, сеть, **проброс
портов** с хоста (API 6443 и порты приложений), **Cilium** по галочке
(с заменой kube-proxy) и тома **Longhorn** с выбором версии (ниже). Внутри узла порт API всегда 6443; порт в
«пробросить наружу» относится к хосту.

## Раздел «Кластеры»: несколько хостов

Диалог «Новый кластер на нескольких хостах» — таблица размещения: хост →
роль → **машины** (сколько, размеры, образ, мост) или **сам хост** как
узел. Образ выбирается из каталога хоста («будет скачан», если его ещё
нет) или из библиотеки хаба (см. ниже); форма сама сообщает о неверном
числе control plane, об отсутствующем общем адресе control plane у
kubeadm и о пропущенном мосте.

### Общий адрес control plane (kubeadm)

У **kubeadm** узлы входят в кластер не по адресу первого control plane, а
по общему адресу — `--control-plane-endpoint`. В API кластера задаётся
полем `endpoint` (или параметром `endpoint` шага `k8s create`) —
`ХОСТ` или `ХОСТ:ПОРТ`, порт по умолчанию 6443. Что с ним происходит:

- он попадает в `kubeadm init --control-plane-endpoint`, и kubeadm сам
  кладёт его в сертификат API **каждого** control plane — отдельно
  добавлять его в TLS SAN не нужно;
- по нему узлы входят (`kubeadm join`) и по нему отдаётся kubeconfig —
  адрес в карточке кластера становится адресом кластера, а не одного
  узла;
- при Cilium с заменой kube-proxy он же уходит агенту как
  `k8sServiceHost`/`k8sServicePort` — порт endpoint'а, а не жёсткий 6443;
- **при трёх control plane он обязателен**: без общего адреса API
  кластера висит на первом узле, и вход остальных двух ничего не меняет.

Ключ сертификатов для входа дополнительного control plane хаб берёт
перед каждым входом (`kubeadm init phase upload-certs`): он живёт два
часа, поэтому один раз при создании его не запасают. Если kubeadm не
напечатал ключ или напечатал не его, задание падает с внятной строкой, а
не уходит на узел с пустым `--certificate-key`.

У **k3s** общей точки входа нет: узлы входят по адресу конкретного
server'а, поэтому поле `endpoint` для k3s не принимается — форма кластеров
предлагает три control plane обоим вариантам, но у kubeadm без общего
адреса создание не запускается.

### Слушатель общего адреса

Сам хаб балансировщика не заводит — для этого есть **Traffic Fly**:
маршрут `api-<имя кластера>` на шлюзе, целями которого становятся control
plane кластера. Слушатель — шаг задания создания: он ложится **до** первого
control plane (kubeadm в конце `init` ждёт API именно по общему адресу —
фаза `apicheck`) и снимается заданием удаления кластера.

Слушатель нужен там, куда указывает общий адрес:

- адрес endpoint'а совпадает с адресом шлюза или его A-запись содержит
  этот адрес — хаб ставит слушатель на этом шлюзе;
- шлюзов несколько, и адрес указывает ровно на один — выбирается он;
- адрес не указывает ни на один шлюз (свой VIP, внешний haproxy, имя ещё
  не заведено) — шаг пишет в журнал, что адрес обслуживает не хаб, и
  задание продолжается: чужой порт на шлюзе кластеру не помощник.

Поля формы — **«Общий адрес control plane»**, **«Где слушать»** и
**«Кому ещё»** — появляются только у kubeadm.

![Общий адрес control plane в окне нового кластера](/screens/ru/hub-cluster-ha.png)

«Где слушать» по умолчанию выбирается по адресу; названный шлюз —
указание ставить слушателя именно там, даже если имя ещё никуда не
указывает (в журнале тогда появится строчка, что видно по адресу). Через
API это поля `gateway` (edge id шлюза) и `allow_extra`, в сценарии —
параметры `gateway ШЛЮЗ` (имя или адрес шлюза) и
`allow АДРЕС[,АДРЕС…]`.

Порт маршрута — порт endpoint'а, цели — control plane на их 6443,
балансировка — по адресу источника (соединения с API живущие, мотать их
между узлами смысла нет). Белый список обязателен: адрес шлюза — это вход
в kube-apiserver и через него в etcd всего кластера. Хаб кладёт в него
наружные адреса хостов размещения и то, что добавил человек; пустой
список у Traffic Fly означает «все», поэтому пустой список — отказ, а не
открытый порт. Хост за NAT, чей адрес снаружи не виден, попадает в журнал
с «!» — его узлы окажутся заперты, и это надо видеть до создания.

**Сухой прогон** показывает всё это чек-листом: шлюз и его адрес, порт и
цели маршрута, кто в белом списке, занят ли порт на шлюзе чужим
маршрутом, и «!» там, где адрес смотрит не на шлюз или шлюза вовсе нет.

**Сеть между хостами** — как узлы на разных хостах видят друг друга:

| Режим | Когда | Что нужно |
|---|---|---|
| **NAT** | все узлы на одном хосте | ничего: сеть libvirt хоста |
| **Мост** | хосты в одном L2-сегменте | мост на каждом хосте с машинами; адреса машин — из сети хостов |
| **WireGuard** | хосты в разных сетях | UDP 51820 между хостами: хаб генерирует ключи, ставит `wireguard-tools`, поднимает `wg-quick@nktwg<N>` и отдельную сеть машин на каждом хосте; подсети соседей идут через туннель |

WireGuard работает, когда хосты видят друг друга по адресу (LAN, VPN,
белые IP — тогда откройте UDP 51820 во внешнем файрволе). Если хаб ходит
на хост по адресу, которого соседи не видят, задайте на хост **«адрес
для соседей»**. Хосты, чьи сети не видят друг друга вовсе, туннель
сейчас не свяжет — обход через хаб в планах ([TODO](https://github.com/piqab/nkt/blob/main/TODO.md)).
Трафик узлов через хаб не идёт никогда — хаб только раздаёт ключи и
конфиги.

**Сухой прогон** проходит проверки по каждому хосту — KVM и libvirtd,
память и ядра, порты, нужные пакеты, образ, мост или адрес для
WireGuard, ping между хостами, доступность ссылок — и пишет чек-лист
(✓ / ! / ✗) в журнал поверх формы: настройки остаются на месте, их можно
поправить и запустить создание. С галочкой «заодно подготовить» хаб
сразу скачивает образы и пакеты в кэш и поднимает сеть libvirt.

## Что ещё умеет раздел

- **Находки Kubernetes по кластерам** — сводка со всех control plane.
- **Ingress для клиентов** — узел кластера и порт HTTP ingress-контроллера,
  куда Traffic Fly ведёт маршруты токенов на их namespace (`fly own … cluster
  … namespace …`, MCP `fly_own_add`); без него маршрут на namespace
  клиента не завести. Окно — с диффом, пусто — выключено.
- **Маршруты Traffic Fly по узлам** — маршрут, привязанный к кластеру,
  берёт цели из его узлов: узел прибыл — цель появилась, узел ушёл — цель
  ушла. Порт целей — ingress для клиентов, либо названный человеком
  (NodePort идёт насквозь). Перекладка — заданием создания и удаления,
  наблюдением раз в минуту и кнопкой: в карточке кластера — **«Цели
  Traffic Fly»** (появляется, когда у кластера есть привязанные маршруты,
  их число — в подсказке), в самом маршруте — **«Сверить цели»**.
  Слушатель общего адреса автомат не перекладывает: у него только
  control plane. Подробности — [Traffic Fly](/guide/traffic-fly).

  ![Карточка кластера с кнопкой «Цели Traffic Fly»](/screens/ru/hub-cluster-fly.png)
- **Ресурсы для клиентов** — ресурсы операторов (CRD), которые клиенты
  создают в своих namespace: по одному в строке, `ресурс.группа`
  (`registries.registry.rgstr.io`). Хаб применяет ClusterRole
  `nkt-client-crds` с метками `aggregate-to-edit` и `aggregate-to-admin` —
  роль `edit` namespace клиента получает на них все права. Группы
  Kubernetes, прав, допуска, сети, Cilium и Longhorn не отдаются; что оператор
  создаёт по ресурсу клиента, проходит те же политики допуска. Окно — с
  диффом, список едет в экспорт. Пример —
  [rgstr и rgstroperator](/guide/hub-plugin-rgstr).
- **Helm в кластеры** — один релиз в выбранные кластеры (или в кластеры
  группы хостов) заданием хаба, по очереди, с итогом по каждому.
- **Обновление кластера** — «Обновить» у кластера: версия, затем по
  узлам (control plane первыми) cordon, drain, обновление, ожидание
  Ready, uncordon; на ошибке задание останавливается и продолжается с
  того же узла.
- **Манифесты: один YAML в несколько кластеров** — манифест и выбор
  кластеров; перед записью — дифф текста с прошлой редакцией и `kubectl
  diff` по каждому кластеру, запись — `kubectl apply` на первом control
  plane каждого, итог по кластерам. Каждое применение хранится на хабе
  редакцией; прежнюю можно открыть в редакторе и применить заново.
- **Образы для кластеров** — свой qcow2/img/raw загружается на хаб один
  раз (до 10 ГБ) и выбирается в размещении как «с хаба: …»; при
  создании хаб заливает его на каждый хост, где образа ещё нет.
- **Сохранённые наборы** — «сохранить набор» запоминает всю форму под
  именем, выбор набора заполняет её заново; наборы едут в экспорт/импорт.
- **Кэш хаба для узлов без интернета** — если у хоста включён «apt через
  хаб», машина кластера получает эту галочку сама (проброс хаб держит до
  машины своим соединением, сеть машины наружу не открывается), и через
  тот же порт идут файлы по ссылке (установщик и бинарник k3s с
  airgap-образами, Cilium CLI, ключ `pkgs.k8s.io`, образы машин, архив
  helm и tarball чарта Longhorn — дополнение ставится на таких узлах) и
  **зеркало registry** (docker.io, quay.io, registry.k8s.io, ghcr.io,
  gcr.io) — containerd узлов настраивается на него сам. Всё оседает на
  хабе и уходит в интернет один раз; apt машины ходит через хаб и по
  `https` тоже — раньше одна лишь http-строка оставляла `https`-зеркала
  вне кэша.
- **kubectl** — кнопка у готового кластера открывает терминал на первом
  control plane с готовым `kubectl` (`KUBECONFIG`, автодополнение, алиас
  `k`); доступ к API снаружи не нужен.
- **Попробовать снова** — упавшее задание создания продолжается с того
  места, где остановилось: созданные машины, туннель и установленные
  роли не делаются заново.
- Перед установкой роли узел обновляется до версии nkt хаба; при
  повторе остатки неудачного `kubeadm init/join` убираются сами —
  состояние узла определяется по манифестам control plane (ниже).
- Удаление кластера убирает машины, туннель и сеть машин; узел-хост
  остаётся в списке хостов.

В сценариях то же — `k8s create` с `nodes "hv1: cp 1, w 2; hv2: w 2;
hv3: host w"`, `network nat|bridge|wireguard`, `version 1.34`, `image
hub:<файл>`, `endpoint АДРЕС` ([Сценарии](/guide/hub-scripts)).

## Подробности установки

- **kubeadm** ставит пакеты из `pkgs.k8s.io` выбранной ветки; ветка
  записывается в кластер, и добавленные потом worker'ы получают ту же.
  Старые ветки вроде v1.31 на Debian 13 не годятся: `sqv` отвергает их
  подпись как устаревшую.
- **Повтор «установки роли»** решает, готов ли узел, по манифестам, а не по
  `kubelet.conf`: `kubeadm join --control-plane` пишет `kubelet.conf` и
  манифесты apiserver/controller-manager/scheduler ещё в фазе
  `control-plane-prepare`, а участником etcd становится и пишет `etcd.yaml`
  только в фазе `etcd-join` — дальше которой вход и падал, когда etcd-адрес
  соседа был недоступен. Манифесты без `etcd.yaml` — недоделанный узел: его
  сносят и входят заново, а не объявляют готовым (по живому kubelet такой
  узел выглядел присоединённым, и зелёный шаг оставлял нерабочий control
  plane). Сносит состояние каскад `kubeadm reset`: сначала обычной попыткой,
  затем без вычёркивания участника etcd — первая фаза не проходит, когда
  etcd недоступен, reset выходит на ней, манифесты остаются, и следующий
  заход отказывает `FileAvailable--etc-kubernetes-manifests-*.yaml`, — затем
  одной только очисткой узла. Вывод reset'а виден в журнале задания: если
  снести не удалось, шаг падает с причиной, а не делает вид, что почистил.
- **containerd** на машине из облачного образа ставится пакетом
  дистрибутива; на «железном» хосте уже стоящий (например, `containerd.io`
  от Docker) не переустанавливается — у него включаются CRI и
  `SystemdCgroup`, прежний конфиг остаётся в `config.toml.nkt-bak`,
  контейнеры Docker не останавливаются.
- **Cilium** — после старта control plane ставится `cilium` CLI
  (последняя стабильная, с проверкой суммы) и `cilium install`; уже
  поставленный Cilium не переставляется — проверка идёт по `ds/cilium` в
  `kube-system`, а `cilium install` поверх занятого имени релиза helm
  отклоняет («cannot reuse a name that is still in use»), так что без
  такой проверки повтор упавшего задания спотыкался о рабочий Cilium;
  «заменить kube-proxy» — `--disable-kube-proxy` у k3s,
  `--skip-phases=addon/kube-proxy` у kubeadm.
- **Longhorn** (галочка «Longhorn» и версия чарта; в сценарии — `addon
  longhorn[=1.12.1]`, в API и MCP — `"addons":[{"name":"longhorn",
  "version":"1.12.1"}]`) — блочные тома с репликами по узлам. Ставится
  последним шагом, когда все узлы `Ready`:
  - `open-iscsi` и `nfs-common` (тома ReadWriteMany) ставит **cloud-init при
    первом запуске машины** — пока у неё ещё есть исходящий TCP: шагом
    подготовки узел уже сидит на Cilium вместо kube-proxy, а в NAT-сети
    хоста после этого TCP наружу может молчать, хотя ping и DNS остаются
    рабочими; на готовом узле пакеты проверяются (`dpkg -s`) и докачиваются
    только если их нет (узлы-хосты, машины прежних кластеров), с короткими
    таймаутами и внятной строкой в журнале, а не зависанием до таймаута
    задания; там же — модуль `iscsi_tcp`, служба `iscsid`; если работает
    `multipathd`, в журнале — предупреждение (его `multipath.conf` nkt не
    трогает);
  - на первом control plane — чарт в `longhorn-system` (helm ставится сам,
    если его нет), ожидание `longhorn-manager`. И helm, и tarball чарта
    берутся **через кэш хаба**, если у хоста открыт порт пакетов: узел без
    выхода наружу ставит дополнение с того же канала, что и k3s с Cilium,
    а скачанный чарт остаётся на узле в `/var/lib/nkt/addons/` и
    переиспользуется при обновлении. Не приехал чарт — установка берёт
    `longhorn/longhorn` из `https://charts.longhorn.io`, и команды
    репозитория при открытом кэше идут через прокси хаба;
  - реплик томов — по узлу, не больше трёх (у одиночного кластера —
    одна);
  - Longhorn — StorageClass **по умолчанию**: у прежнего (`local-path` в
    k3s) метка снимается, а k3s перестаёт вести его манифестом
    (`local-storage.yaml.skip`), иначе вернул бы метку при перезапуске.

  **Версия:** пусто — версия nkt по умолчанию (сейчас 1.12.1); список —
  последние патчи четырёх последних веток из `index.yaml` репозитория
  (кэш час, `GET /api/hub/k8s-addon-versions?addon=longhorn`), версии, не
  подходящие к Kubernetes кластера (`kubeVersion` чарта), выбрать нельзя.
  Сухой прогон проверяет версию по репозиторию и предупреждает, если диск
  узлов меньше 20 ГБ — реплики лежат в `/var/lib/longhorn` на нём же.
  Добавленные потом worker'ы готовятся тем же шагом. Группа `longhorn.io`
  клиентам не отдаётся («Ресурсы для клиентов») — они пользуются
  Longhorn только через PVC.
- **Дополнения у готового кластера** — кнопка «Дополнения»: какая версия
  Longhorn стоит (по `helm` на control plane), установка или обновление
  заданием (`POST /api/hub/clusters/{id}/addons {"name":"longhorn",
  "version":"1.12.1"}`, MCP `cluster_addons`, `cluster_addon_install`).
  Обновление — только вперёд и не дальше следующей минорной ветки за раз
  (1.11 → 1.12), как требует Longhorn; прежние values сохраняются
  (`--reuse-values`).
- **Пробросить наружу** — DNAT с портов хоста (`6443`, `80`, `443`, любой
  можно заменить или обнулить) на control plane: свои цепочки `NKT-PF`,
  юнит `nkt-portforward.service` восстанавливает их при загрузке.
  kubeconfig тогда указывает на хост и выбранный порт API.
- **WireGuard**: интерфейс `nktwg<N>` с адресом `10.200.<N>.<i>/24`, сеть
  машин `10.<100+N>.<i>.0/24`; `PostUp` открывает UDP-порт, пропускает
  FORWARD через туннель и снимает маскарад libvirt между подсетями машин —
  узлы видят друг друга по настоящим адресам. Перед созданием машин хаб
  проверяет связь каждой пары хостов по туннелю; без рукопожатия в
  журнале — «UDP 51820 закрыт или адрес неверный».
- **Мост**: адрес машины узнаётся через `qemu-guest-agent`, который
  cloud-init ставит при первом запуске.
- **NAT и WireGuard** (узел не на мосту): когда машина узла завелась, хаб
  закрепляет за ней адрес — бронь DHCP по MAC в сети libvirt (`virsh
  net-update <сеть> add-last|modify ip-dhcp-host --live --config`) по тому
  адресу, который хост у машины видит сейчас. Адрес узла живёт в маршрутах
  Traffic Fly, в пробросе портов и в kubeconfig, а аренда без брони
  кончается: перезапустилась машина — адрес другой, и цель маршрута больше
  не находится. Не закрепилось (сеть не отвечает, машина адрес ещё не
  получила) — в журнале предупреждение, создание узла не отменяется.
- Задание создания — задание хаба: машины создаются тем же путём, что
  «Новая машина», дальше установка роли, токен, присоединение остальных
  узлов, ожидание `Ready`, проброс и kubeconfig. API повтора: `POST
  /api/jobs/{id}/retry`, `POST /api/hub/clusters/{id}/retry`.
