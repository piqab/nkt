# nkt hub — Android-клиент

Нативное Android-приложение (Kotlin/Jetpack Compose), выполняющее роль
клиента к уже существующему JSON API `nkt hub` — так же, как это делает
`web/` (React-фронтенд). Хаб-сервер (VPS, держащий SSH-туннели к
управляемым хостам) не меняется: приложение лишь добавляет ещё один
способ говорить с тем же API, что и браузер.

Полный план (архитектура, разбивка на фазы, разведка по API/WebSocket/
экранам) — в репозитории Claude-плана этой сессии; при необходимости
попросите его продублировать сюда. Коротко: план разбит на 8 фаз —
от каркаса до полного паритета со всеми ~18 экранами веб-интерфейса,
коммит на каждую фазу.

## Статус

Реализовано:
- Gradle-проект (AGP 8.6.0, Kotlin 2.0.20, Compose, `kotlinx.serialization`).
- Сетевой слой (`net/HubClient.kt`) — один `OkHttpClient` + персистентный
  `CookieJar` (`net/PersistentCookieJar.kt`, поверх DataStore), host-scoping
  по правилу `web/src/api.ts`'s `hostScope` (`net/HostScope.kt`).
- JSON-модели (`net/model/Models.kt`), сверенные с Go-структурами.
- Экран входа (`ui/login`), список хостов только для чтения (`ui/hosts`),
  экран «О системе» (`ui/about`) — версия хаба + статус базы уязвимостей,
  без кнопок обновления (см. `AboutViewModel`'s doc-комментарий — почему).
- TOFU-закрепление TLS-сертификата хаба (`net/CertPinning.kt`) — та же
  модель, что у самого хаба в `internal/hub/tunnelpin.go`.
- Экран хоста (`ui/host/HostScreen.kt`) с боковым меню на 15 разделов:
  Обзор, Проблемы, Сервисы, Контейнеры, Уязвимости, Доступность,
  Нагрузка, Конфигурация, Firewall, Сертификаты, Интерфейсы, Разное,
  Карта, Пользователи, Журнал.
- Действия: жизненный цикл сервисов и контейнеров (Docker/Podman/LXD/ВМ),
  CRUD пользователей, запуск скана уязвимостей с опросом прогресса.
  Все пути и тела запросов проверены живыми вызовами к `nkt serve`.
- Карта ресурсов — нативная, на жестах (щипок/сдвиг/касание). Веб-версия
  построена исключительно на мышиных событиях, поэтому это не порт, а
  отдельная реализация с раскладкой по концентрическим кольцам.
- Конфигурация: просмотр, правка, история версий, diff и откат. Запись
  всегда идёт с `expected_sha256`, поэтому чужая правка не затирается
  молча; хост валидирует новый конфиг владеющим сервисом и сам
  возвращает прежний файл, если проверка не прошла, — результат этой
  проверки экран показывает первым делом. Перечитывание сервиса после
  записи — отдельная галочка, по умолчанию выключенная.

- **Терминал и монитор btop** — живой PTY по WebSocket с собственным
  эмулятором VT100 (`terminal/TerminalEmulator.kt`) и панелью спецклавиш
  (Ctrl, Esc, стрелки, ^C/^D/^Z/^L, PgUp/PgDn). Готовой библиотеки
  терминала под Android в Maven Central нет, поэтому эмулятор свой — зато
  это чистая логика без зависимостей от Android, и она покрыта тестами на
  реальном выводе bash и tmux, снятом с живого сервера.

- Firewall: конструкторы правил ufw и firewalld, удаление и перечитывание.
  Удаление по номеру всегда шлёт текст правила, который был на экране, —
  ufw перенумеровывает правила после каждого изменения, и сервер сверяет
  их прежде чем что-то трогать. Правило, закрывающее порт доступа к хосту
  (22, 8077, 8078), требует отдельного подтверждения с прямым
  предупреждением.
- Сертификаты: выпуск через certbot, продление существующих lineage,
  самоподписанные и сборка PEM для haproxy. Выпуск и продление идут
  фоновым заданием на хосте, поэтому показывается живой лог, а не
  бесконечный спиннер.

### Чего пока нет

- **Управление хостами на уровне хаба** (добавление, удаление,
  экспорт/импорт с шифрованием) — только список и открытие.

### Тесты

`android/scripts/build.sh test` разбирает настоящие ответы сервера
(`app/src/test/resources/api/*.json`, снятые с `nkt serve` в режиме
фикстур) моделями приложения. Это ловит расхождение моделей с Go-стороной
— единственный класс ошибок, который иначе виден только на устройстве.
После изменения формы ответов на Go-стороне фикстуры надо переснять.

## Сборка из командной строки, без Android Studio

Один раз на машину — подготовка тулчейна (JDK 17, Android SDK). Работает
на Linux и macOS (Intel и Apple Silicon), root/sudo не нужен:

```bash
android/scripts/setup-toolchain.sh
```

Скрипт сначала ищет то, что уже стоит на машине, — JDK 17+ (включая
встроенный в Android Studio и поставленный через Homebrew), Android SDK
(в том числе SDK самой Android Studio) и уже установленные его пакеты, —
и скачивает только реально недостающее, в `$HOME/.local`. Повторный
запуск не качает ничего. Сам Gradle не ставится: `android/gradlew`
скачает нужную версию при первой сборке.

Дальше сборка:

```bash
android/scripts/build.sh                  # debug APK
android/scripts/build.sh assembleRelease  # любые аргументы уходят в Gradle
```

Либо вручную, тем же путём:

```bash
cd android
source scripts/env.sh
./gradlew assembleDebug
```

Результат — `android/app/build/outputs/apk/debug/app-debug.apk`.
Установка на подключённое устройство/эмулятор:

```bash
$ANDROID_HOME/platform-tools/adb install -r \
  android/app/build/outputs/apk/debug/app-debug.apk
```

Android Studio при этом никуда не девается: `android/` — обычный
Gradle-проект, его можно открыть в IDE и собирать оттуда тем же
wrapper'ом.

### Что проверено, а что нет

Сборка и тесты проходят в той среде, где код писался. Само приложение
там **не запускалось** — эмулятора и устройства нет, поэтому всё, что
касается рантайма (отрисовка, жесты, экранная клавиатура), проверяется
только на реальном телефоне. Несколько ошибок так и нашлись: btop не
помещался в экран, клавиатуру нечем было вызвать, список хостов при
старте писал «Хаб не настроен».

Отсюда и подход к тестам: всё, что можно свести к чистой логике, вынесено
из UI и покрыто тестами на JVM — эмулятор терминала, расчёт сетки
терминала, сопоставление состояний с цветом, разбор ответов сервера.
Остальное проверяется живыми вызовами к запущенному `nkt serve`.

## Заметки по конфигурации

- `minSdk = 26`, `targetSdk = compileSdk = 35`.
- `network_security_config.xml` разрешает `cleartextTrafficPermitted`
  на уровне base-config — хаб по умолчанию слушает без TLS в доверенной
  сети (см. README.md корня проекта, `NKT_COOKIE_SECURE=false`); при
  выпуске в реальную эксплуатацию через недоверенную сеть используйте
  реверс-прокси с TLS перед хабом и уберите это разрешение.
