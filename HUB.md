# Хаб NetKnownsThat — управляющий центр для нескольких VPS

Обычный `nkt` следит за одним Linux-хостом. `nkt hub` — тот же бинарник в
другом режиме: разворачивается на одной VPS и оттуда устанавливает и
обслуживает `nkt` на остальных ваших хостах по SSH. Дальше каждый хост
открывается прямо в интерфейсе хаба — те же страницы (Docker, Podman, LXD,
сертификаты, карта ресурсов, конфиги...), что и у обычного `nkt` на одном
хосте, просто с выбором хоста наверху.

Подробное описание архитектуры и API — в
[README.md](README.md#hub-many-hosts-from-one-place). Этот файл — только
про то, как запустить.

По умолчанию — обычный systemd-сервис, как и у самого `nkt` (раздел 1
основного README): без Docker, без контейнеров, тот же принцип наименьших
привилегий. Docker — альтернативный, самодостаточный вариант упаковки, если
он вам удобнее (раздел 2.2 ниже).

## 1. Что нужно

* Linux-хост для самого хаба — тот же профиль прав, что и у обычного `nkt`
  (root + ограниченный набор capabilities, см. раздел 4), потому что хаб
  сам сканирует и меняет состояние этой же машины под именем «localhost» в
  списке хостов. Отдельно ставить Go не обязательно — если системного `go`
  нет или он не запускается (например, `snap`-пакет под жёстко урезанным
  systemd-юнитом, см. раздел 7), хаб при первой установке хоста сам скачает
  и распакует Go с go.dev в свой каталог данных — ровно то же, что
  `make native-build` уже делает для сборки самого `nkt`.
* SSH-доступ с этой машины до каждого хоста, который вы хотите добавить:
  IP/имя, порт, пользователь с правом `sudo`/root (установка кладёт файлы в
  `/usr/local/bin`, `/etc/systemd/system`, `/etc/netknownsthat`) и либо
  пароль, либо приватный ключ.
* Целевые хосты — Linux, amd64, arm64 или 32-бит ARM (Raspberry Pi и
  подобные — armv6l/armv7l, собирается с GOARM=6). Больше ничего заранее
  ставить на них не нужно: хаб сам соберёт и зальёт нужный бинарник.
  Архитектура самого хаба (на котором он запущен) роли не играет — сборка
  всегда кросс-компилируется под целевой хост, независимо от того, где
  работает хаб.

## 2. Запуск

### 2.1. Без Docker (по умолчанию)

Соберите и установите как обычный `nkt`, только другой юнит и env-файл:

```bash
git clone https://github.com/piqab/nkt.git /opt/netknownsthat
cd /opt/netknownsthat
make build                    # или make native-build, если нет Docker для самой сборки
sudo make hub-install
sudo systemctl enable --now netknownsthat-hub
```

`hub-install` кладёт бинарник в `/usr/local/bin/nkt`, юнит
`netknownsthat-hub.service` и заготовку `/etc/netknownsthat/hub.env` (правьте
её — как минимум `NKT_HUB_SOURCE_ROOT`, если репозиторий не в
`/opt/netknownsthat`). Юнит запускается от root с тем же ограниченным
набором capabilities, что и обычный `netknownsthat.service` — хаб сам
сканирует и меняет состояние этой же машины под именем «localhost» в
списке хостов (раздел 4), поэтому ему нужен тот же профиль прав, что и
любому `nkt`, следящему за своим хостом.

Клон репозитория здесь нужен для кросс-компиляции — но не строго
обязателен: если хаб установлен из готового бинарника с [Releases]
(https://github.com/piqab/nkt/releases) (см. README, раздел «Запуск на
хосте»), безо всякого `git clone`, хаб при первой установке нового хоста
сам скачивает готовый бинарник и systemd-юнит нужной версии с GitHub —
см. раздел 7, «исходники nkt не найдены». Клон и `make build` остаются
рекомендованным путём: работает без доступа к `github.com` и без
привязки к тому, опубликован ли уже релиз конкретной версии.

Соответственно, тот же бинарник с Releases можно поставить как хаб и
вовсе без клонирования — вручную теми же двумя файлами, что и
`hub-install` кладёт сам:

```bash
sudo install -d -m 0750 /etc/netknownsthat
curl -fsSL https://raw.githubusercontent.com/piqab/nkt/main/deploy/hub.env.example \
  | sudo install -m 0640 /dev/stdin /etc/netknownsthat/hub.env
curl -fsSL https://raw.githubusercontent.com/piqab/nkt/main/deploy/netknownsthat-hub.service \
  | sudo install -m 0644 /dev/stdin /etc/systemd/system/netknownsthat-hub.service
sudo $EDITOR /etc/netknownsthat/hub.env
sudo systemctl daemon-reload
sudo systemctl enable --now netknownsthat-hub
```

Проверить, что поднялось:

```bash
curl -s http://127.0.0.1:8077/api/health
journalctl -u netknownsthat-hub -f
```

По умолчанию слушает только `127.0.0.1` — как и обычный `nkt`, снаружи нужен
свой reverse proxy с TLS (см. раздел 1.4 основного README — та же схема).

### 2.2. Через Docker (альтернатива)

Из корня репозитория:

```bash
docker compose -f deploy/docker-compose.hub.yml up -d --build
# или: make hub
```

Первая сборка образа собирает фронтенд и Go-бинарник — займёт пару минут;
дальше пересборки идут из кэша. Этот путь сразу публикует порт наружу
(`0.0.0.0` внутри контейнера, см. раздел 6) — поставьте перед ним свой TLS,
если это не только локальный тест.

```bash
curl -s http://127.0.0.1:8443/api/health
```

С v1.10.70 хаб в контейнере работает **не от root** (пользователь `nkt`,
uid 1000): SSH к хостам, база и кэш сборки Go лежат в томе данных. Том,
заведённый прежней версией от root, надо один раз отдать этому
пользователю — хаб при старте выйдет с понятной ошибкой и командой:

```bash
docker run --rm -v nkt-hub-data:/data alpine chown -R 1000:1000 /data
```

(имя тома — `deploy_nkt-hub-data` или как в вашем compose: `docker volume
ls`). Манифест Kubernetes делает то же через `fsGroup: 1000` сам.

### 2.3. Готовым образом, без клонирования (Docker Compose и Kubernetes)

Не нужен ни `git clone`, ни локальная сборка — образ публикуется в GHCR под
каждый релиз. К самому релизу приложены манифесты с **точной версией**
образа вместо `:latest` — `docker-compose.hub.release.yml` и
`k8s-hub.yaml` (их суммы в `SHA256SUMS`): мутабельный тег можно
переставить, а том хаба хранит мастер-ключ и секреты хостов. В
репозитории те же файлы остаются на `:latest`, чтобы `docker compose
pull` подтягивал свежий образ. Команды и манифест
(`deploy/docker-compose.hub.release.yml`,
`deploy/k8s/hub.yaml`) — в README, раздел
[«Хаб в контейнере»](README.md#launch-the-hub-in-docker).

## 3. Первый вход

При первом старте хаб сам создаёт учётную запись администратора и печатает
пароль в лог:

```bash
journalctl -u netknownsthat-hub                                    # без Docker
docker compose -f deploy/docker-compose.hub.yml logs hub           # через Docker
```

Ищите блок:

```
=== Создана учётная запись администратора хаба ===
  логин:  admin
  пароль: <строка>
```

Он больше нигде не отображается — сохраните пароль. Логин — по адресу,
который вы опубликовали (`http://127.0.0.1:8077` без Docker,
`http://127.0.0.1:8443` в примере с Docker).

## 4. Хост «localhost» — сама машина хаба

Первой строкой в таблице «Хосты», ещё до ручной установки, всегда закреплён
хост **«localhost»** — та машина, на которой запущен сам хаб. Хаб сканирует
её тем же кодом, что использует обычный `nkt` (nginx/haproxy/caddy, systemd,
firewall, docker/podman/LXD/libvirt), но без SSH, без установки отдельного
бинарника и без риска конфликта портов с самим собой — работает сразу после
первого входа. Нажмите «открыть» — дальше это тот же дашборд, что и у любого
подключённого хоста.

Из-за этого `deploy/netknownsthat-hub.service` запускается с тем же
профилем прав, что и обычный `netknownsthat.service` (root +
`CapabilityBoundingSet`, доступ на запись к `/etc/nginx`, `/etc/haproxy`,
`/etc/caddy`, `/etc/letsencrypt`), а не изолированным `DynamicUser` —
иначе сканировать и менять что-либо на этой машине было бы нечем. Если хаб
запущен без этих прав (например, старый юнит, не обновлённый через
`hub-install`) — строка «localhost» просто не появится в таблице, всё
остальное в интерфейсе продолжит работать как обычно.

У «localhost» нет ни установки/переустановки, ни удаления, ни SSH-полей —
единственное действие — «открыть».

## 5. Добавить хост

На странице «Хосты» после входа заполните форму:

* **Имя** — как хост будет называться в интерфейсе, произвольная метка.
* **Адрес** — IP или DNS-имя.
* **SSH-порт** — обычно 22.
* **SSH-пользователь** — `root`, либо обычный пользователь с `sudo` без
  пароля (`NOPASSWD`) — так по умолчанию настроены типовые образы VPS
  (`ubuntu`, `debian`, `admin` и т.п. с cloud-init). Установка сама
  добавляет `sudo -n` к командам, которым нужны права записи в
  `/usr/local/bin` и `/etc/systemd/system`, когда пользователь не root; при
  этом `sudo`, требующий пароль, сразу даёт понятную ошибку, а не зависает.
* **Способ входа**:
  * **хаб сгенерирует ключ** (по умолчанию, рекомендуется) — ничего
    вставлять не нужно. После сохранения хаб покажет публичный ключ —
    добавьте эту строку в `~/.ssh/authorized_keys` на самом хосте (у
    указанного пользователя), и только потом нажимайте «установить».
    Приватная половина ключа генерируется хабом и никогда никуда не
    передаётся — в отличие от способов ниже, вставлять её не нужно.
    Публичный ключ можно посмотреть повторно в любой момент кнопкой
    «публичный ключ» в таблице хостов (например, если хост пересоздали).
  * **свой приватный ключ** — вставляете содержимое существующего файла
    (`id_rsa`/`id_ed25519`, **не** `.pub`) в формате PEM; его публичная
    половина должна уже быть в `authorized_keys` на хосте.
  * **пароль** — обычный пароль пользователя по SSH.
* **Подготовить новый хост** — есть на обеих вкладках: при входе по
  паролю включена по умолчанию (свежий сервер, где есть только root и
  пароль), при ключе хаба выключена (ключ уже положен руками, хост,
  скорее всего, готов) — но её можно включить, тогда шаги идут под
  введённым пользователем через `sudo`. Разовый сценарий: выполняется
  один раз, прямо перед установкой, и не повторяется при обновлениях. Поддерживаются только Debian/Ubuntu-подобные системы —
  всё делается через `apt-get`, и на системе без него подготовка честно
  отказывается работать вместо того, чтобы молча пропустить полдела.

  Что делает по порядку:

  1. **Пакеты.** `dbus sudo iproute2 procps ca-certificates curl tmux
     btop` — список редактируется прямо в форме. Без `dbus` не
     открывается терминал и не работают установки пакетов из интерфейса,
     без `iproute2` пуст список слушающих сокетов, без `procps` не
     привязываются процессы к портам; `tmux` и `btop` включают режим
     tmux в терминале и живой просмотр нагрузки.
  2. **Пользователь** (если указан, по умолчанию `nkt`) — создаётся с
     домашним каталогом и правилом `NOPASSWD` в `/etc/sudoers.d/`. Файл
     проверяется `visudo -cf` во временном месте и только потом ставится
     на место: неверный файл в `sudoers.d` ломает `sudo` сразу для всех.
  3. **Ключ вместо пароля.** Хаб генерирует пару, дописывает публичную
     половину в `authorized_keys` (именно дописывает — чужой доступ на
     хосте не трогается) и проверяет вход **новым соединением**, а для
     не-root ещё и `sudo -n`. Только после этого запись хоста
     переводится на ключ. Если проверка не прошла, всё остаётся как
     было, и пароль продолжает работать.
  4. **Выключить вход по паролю** (по желанию) — отдельным drop-in'ом
     `/etc/ssh/sshd_config.d/99-nkt-no-password.conf`, с проверкой
     `sshd -t`, перезагрузкой без разрыва сессий и ещё одной проверкой
     входа по ключу. Если после перезагрузки демон перестал пускать,
     drop-in удаляется и sshd перезагружается обратно. Неудача на этом
     шаге не срывает установку: ключ уже работает, а вход по паролю
     просто остаётся включённым.

* **Включить веб-терминал на хосте** — выключено по умолчанию. При
  включении хаб передаёт хосту `NKT_TERMINAL_ENABLED=true` при следующей
  установке/обновлении — на самом хосте это открывает полноценный
  root-shell в браузере (раздел «Терминал»). Правка `nkt.env` на хосте
  вручную для этого не годится: `stageFiles` перезаливает этот файл при
  **каждой** установке/обновлении, так что ручная правка потеряется при
  следующем нажатии «обновить» — переключатель в форме хоста хранится в
  базе самого хаба и переживает это.

  Терминалу (и обновлению пакетов, и самообновлению хоста через резервный
  канал) для выхода из песочницы своего systemd-юнита нужен либо D-Bus,
  либо `CAP_SYS_ADMIN` в юните (запасной путь через `nsenter` в
  пространство имён PID 1 — см. `deploy/netknownsthat.service`). Оба уже
  включены в юнит, который заливает установка/переустановка — на хосте,
  установленном **до** этого изменения, их не будет, пока не нажать
  «переустановить» ещё раз. Если на конкретном хосте нет ни D-Bus, ни
  нужной capability — терминал всё равно откроется, но только в урезанном
  виде (без записи в системные пути); раздел «Терминал» покажет
  предупреждение и, если возможно, кнопку «Установить dbus».
* **Резервный канал связи на случай недоступности SSH** — включено по
  умолчанию для новых хостов (в отличие от веб-терминала — это не
  дополнительный доступ, а просто резерв на случай отказа основного).
  Хаб сам открывает на хосте ещё один порт (`8078` по умолчанию,
  `NKT_HUB_TUNNEL_PORT` на хабе — см. раздел 6) и сам же на него
  дозванивается — тем же адресом хоста, что уже используется для SSH,
  никакой отдельный адрес хаба настраивать не нужно: если хаб сам сидит в
  приватной сети без публичного адреса (домашняя/офисная сеть — обычный
  случай, не исключение), это никак не мешает.

  Если входящий 22-й порт на хосте заблокируют файрволом (самая частая
  причина «SSH недоступен» на практике, не обязательно падение самого
  sshd), дашборд, терминал **и** «обновить»/«переустановить» этого хоста в
  хабе продолжат работать через этот канал вместо того, чтобы просто
  перестать отвечать — если, конечно, тот же файрвол не блокирует заодно и
  порт `8078`: резервный канал идёт **в том же направлении**, что и сам
  SSH (хаб → хост), поэтому файрвол, полностью закрывающий входящие порты
  хоста, заблокирует и его тоже. Он спасает от более узкого, но
  распространённого набора причин — упавший или неверно настроенный sshd,
  протухшие учётные данные — а не от полной блокировки входящих. Хаб
  всегда пробует сначала обычный SSH — резервный канал подключается,
  только если дозвон по SSH не удался.

  Для дашборда/терминала это буквальный проброс тех же запросов через
  другой транспорт. Для «обновить»/«переустановить» — нет: SFTP и sudo
  через этот канал не ходят (он не даёт хабу ничего, кроме HTTP до
  API хоста), поэтому хаб вместо этого пушит уже собранный бинарник и
  рендер `nkt.env`/юнита на `POST /api/self-update` самого хоста, а тот
  раскладывает их по местам и перезапускает себя через тот же приём
  `systemd-run`, что уже используется для терминала и обновления пакетов
  (см. README, раздел «Безопасность»). Из-за этого у резервного пути есть
  одно ограничение, которого нет у SSH: он никогда не выполняет **самую
  первую** установку хоста (неоткуда взять архитектуру, да и порт `8078`
  ещё не поднят) — только последующие обновления/переустановки уже
  установленного хоста.

  Аутентификация — отдельный случайный токен на хост, генерируется заново
  при каждой установке/обновлении и передаётся хосту через уже доверенный
  SSH-канал; хаб хранит его у себя зашифрованным (нужно предъявлять заново
  при каждом новом соединении, поэтому, в отличие от пароля администратора
  и SSH-секрета, не хэш) и предъявляет при каждом подключении к порту
  `8078`. Хост проверяет присланный токен и, при 5 неудачных попытках с
  одного адреса, временно блокирует его — та же защита от перебора, что и
  у входа в сам хаб. TLS-сертификат хоста самоподписанный; обычной цепочки
  доверия для него нет, поэтому хаб проверяет не её, а отпечаток (SHA-256)
  самого сертификата — «доверие при первом подключении», как у SSH-ключей
  хоста в этом проекте, но, в отличие от них, реально закреплённое: отпечаток
  первого увиденного сертификата хаб запоминает и на каждом следующем
  подключении сверяет заново, а не доверяет любому сертификату бессрочно.
  Если отпечаток вдруг не совпал (сертификат хоста подменили, либо хост
  переустановили не через хаб, из-за чего привязка не сброшена) — хаб
  отказывается от соединения и пишет предупреждение в свой лог; переустановка
  через хаб сама сбрасывает привязку вместе с новым токеном. Токен —
  по-прежнему то, что на самом деле аутентифицирует соединение; привязка
  сертификата закрывает канал утечки этого токена перехватчику на пути.

  Колонка «Канал» в таблице хостов показывает состояние резервного канала:
  серым — выключен; зелёным «подключён» — включён и хаб держит соединение,
  но сейчас работает обычный SSH; жёлтым «через резервный канал» — SSH
  прямо сейчас недоступен, и всё (включая дашборд/терминал/обновление)
  реально идёт через эту резервную связь.

**Ключ SSH хоста.** При первом подключении хаб запоминает публичный ключ
SSH хоста (`hosts.ssh_host_key`) и дальше требует тот же — как
`known_hosts` у обычного `ssh`: если хост предъявит другой ключ, любое
подключение (установка, опрос, прокси) завершится ошибкой «ключ SSH
хоста изменился: запомнен SHA256:…, предъявлен SHA256:…» вместо входа с
паролем к возможно чужой машине. После переустановки хоста (новые ключи
sshd) нажмите **«забыть ключ хоста»** в форме «изменить» — следующее
подключение запомнит новый; там же виден отпечаток запомненного ключа.
Запомненный ключ входит в экспорт/импорт. Туда же входят настройки
разбора моделью (раздел 9.1): провайдер, адрес, модель, ключ API
(перешифровывается мастер-ключом принимающего хаба, как и секреты
хостов), правленые инструкции — и бета-канал обновлений.

После «Добавить хост» нажмите «установить» в таблице. Установка (и
каждое обновление, в том числе «обновить всё» и автообновление при
открытии отставшего хоста) — **задание хаба**: журнал открывается в том
же окне, что у остальных заданий, виден в разделе «Задания» на языке
читающего, переживает перезагрузку страницы, отменяется кнопкой в
строке хоста; «обновить всё» заводит по заданию на каждый отставший
хост (очередь — по хосту, они идут параллельно). Пока установка на хост
идёт, повторный запуск открывает её же журнал. Шаги в журнале:

1. подключение по SSH, определение архитектуры;
2. сборка (или взятие из кэша) бинарника `nkt` под неё;
3. доставка бинарника на хост и заливка systemd-юнита и `nkt.env` по
   SFTP. Бинарник хост либо **качает сам с GitHub Releases** (`curl`,
   контрольная сумма из `SHA256SUMS` релиза сверяется на хосте), либо
   получает **с хаба по SFTP** — что быстрее: при каждой доставке хаб
   меряет оба пути (первый мегабайт ассета с хоста и мегабайт по SFTP) и
   пишет в лог «GitHub с хоста X МБ/с, SFTP с хаба Y МБ/с — …»;
   прошлый итог не запоминается — доступность GitHub и скорость каналов
   меняются (последний путь записан в `hosts.binary_via` только для
   сведения). GitHub берётся, только когда он заметно быстрее и ассет
   релиза байт в байт совпадает с бинарником в кэше хаба (у сборки из
   исходников или версии без релиза копии на GitHub нет — тогда только
   SFTP); если хост не смог скачать (нет `curl`, нет интернета, сумма не
   сошлась), в том же задании бинарник заливается по SFTP. SFTP идёт
   параллельными пакетами;
4. `systemctl daemon-reload && systemctl enable netknownsthat && systemctl restart netknownsthat`
   — `restart`, не `enable --now`: тот не перезапускает уже запущенный
   сервис, и на «обновить»/«переустановить» уже работающего хоста новые
   бинарник/`nkt.env` легли бы на диск, а сам процесс продолжил бы
   работать со старым окружением до следующего вмешательства;
5. проверка `/health` и вход под сохранённой учётной записью администратора
   хоста — эта учётная запись дальше используется хабом, вручную
   логиниться на хосте не нужно. Если вход не проходит, потому что на
   хосте уже была учётная запись с другим паролем (например, от прошлой
   независимой попытки установки) — хаб сам сбрасывает пароль на хосте
   командой `nkt passwd` по тому же SSH-соединению и логинится заново;
   вручную ничего чистить не нужно.

Пока установка идёт, рядом с кнопкой появляется «отменить» — она
по-настоящему прерывает текущий шаг (разрывает SSH-соединение, если он
завис на нём), а не просто прячет окно. Если хаб перезапустили прямо во
время установки — при следующем запуске он сам находит зависшие на статусе
«установка» хосты и переводит их в «ошибка», так что кнопки снова
кликабельны без ручного вмешательства.

Когда статус хоста стал «подключён» — нажмите «открыть»: дальше это тот же
дашборд, что и у обычного `nkt`, только сверху добавляется узкая панель
хаба — какой хост открыт и кнопка «к списку хостов», чтобы вернуться.

Закрыли окно с логом установки, а посмотреть его снова нужно — кнопка
«журнал установки» в таблице (появляется после первой попытки) открывает
его заново: и для уже завершённой установки, и для той, что ещё идёт.

Когда версия `nkt` на хосте отличается от версии самого хаба (например,
хаб обновили, а хост ставился раньше) — в столбце «Версия nkt» появляется
подсказка «на хабе: …», а кнопка вместо «переустановить» становится
«обновить» и подсвечивается. Делает она то же самое (заново собирает и
заливает бинарник под архитектуру хоста — под новую версию кэш строится
заново, старый не переиспользуется), просто явно показывает, что есть что
обновлять.

Для такого отставшего хоста кнопка «открыть» сама сначала запускает то же
обновление (с тем же окном прогресса) и переходит в дашборд только после
того, как оно реально завершится успешно — открывать заведомо устаревшую
версию и полагаться, что оператор заметит и обновит её вручную, смысла
нет. Если обновление упадёт с ошибкой — переход не происходит, окно с
логом остаётся открытым с текстом ошибки, как при обычном «обновить».

Столбец **«Sudo»** показывает, что реально обнаружила последняя установка
или обновление для SSH-пользователя, не являющегося `root`: «без пароля»
(NOPASSWD подтверждён — заливка файлов и systemd-команды проходят), «нужен
пароль» (`sudo -n` отказал — раздел «Диагностика» ниже) или «неизвестно»
(установок ещё не было, либо «изменить» поменяло пользователя/адрес и
прежний статус больше не гарантирован). Ничего не проверяется отдельным
запросом — статус берётся из того, что и так уже происходит при установке.

Если статус «без пароля» — рядом появляется кнопка **«снять NOPASSWD»**.
Она удаляет ровно тот файл `/etc/sudoers.d/nkt-hub`, который раздел 5 просит
создать вручную — сознательный шаг для тех, кто хочет убрать постоянный
NOPASSWD-доступ после того, как хост настроен и обновлять его больше не
планируется. После этого хабу снова понадобится sudo (или `root` как
SSH-пользователь), чтобы что-либо ставить или обновлять на этом хосте.

Кнопка **«изменить»** в таблице позволяет поправить имя/адрес/порт/
пользователя в любой момент, не трогая сохранённый секрет — поле секрета в
форме редактирования необязательное, пустое значение оставляет прежний
пароль/ключ как есть. Там же можно сменить способ входа, в том числе
перевести хост на «хаб сгенерирует ключ» (например, вместо ранее введённого
пароля) — это заменит сохранённый секрет новым сгенерированным ключом и
покажет его публичную половину для добавления на хост.

Кнопки **«запустить все»**/**«остановить все»** в шапке страницы —
`systemctl start`/`stop netknownsthat` по SSH сразу на всех установленных
хостах (то же самое, что кнопки «запустить»/«остановить» у отдельного
хоста, только пачкой, с одним подтверждением и сводкой ошибок в конце).
Это не переустановка — бинарник и `nkt.env` не трогаются, только
состояние процесса; после «остановить» хост просто перестаёт отвечать на
периодический опрос хаба и показывается как недоступный.

**Профили групп.** Профили хаба редактируются в разделе «Профили» бокового
меню (это профили машины хаба); у каждого профиля есть цвет. Группе
профиль задаётся при создании («Создать группу» → «Профиль группы»):
машины, создаваемые в такой группе, делаются по нему (он подставлен в окне
«Новая машина»), а их строки в списке подкрашены цветом профиля.
Хосты, перенесённые в группу, не трогаются — ничего не применяется само.
Существующей группе профиль назначить нельзя — заведите новую и
перенесите хосты. Профиль группы показан в её заголовке; у группы без
профиля — подсказка ⓘ. Расхождение хоста с профилем видно в его
«Проблемах», применить заново можно с самого хоста.

**Найти машины на хосте** (вкладка в окне «Новая машина»). Домены
libvirt, созданные не через nkt, заводятся записями машин этого хоста.
У каждой найденной машины показаны **все её адреса** (только с NIC самой
машины: без loopback, link-local и внутренних мостов гостя вроде
`docker0`/`cni0`; источники — аренда libvirt, гостевой агент, ARP
хоста); если адресов несколько — выбор, и выбранный уходит в запись.
Реквизиты SSH (пользователь, порт, пароль) задаются как умолчания
сверху и **у каждой отмеченной машины отдельно** под её строкой —
машины с разными пользователями или портами добавляются за один раз.
Кнопка **«проверить доступ»** проверяет выбранный адрес с хоста (маршрут,
ping, порт SSH, как машина подключена) и с хаба напрямую и пишет диагноз
одной строкой; по итогу в запись попадает и способ связи. Машина на
**macvtap** помечается: хост своих macvtap-гостей не видит (кадры к ним
не заворачиваются через ту же сетевую карту), поэтому такой машине
нужна связь напрямую.

**Связь с машиной** (форма машины, поле «Связь с машиной»): *авто* —
хаб пробует порт SSH машины напрямую (1,5 с, итог помнится 10 минут) и
идёт мимо хоста, если тот отвечает, иначе через хост; *напрямую*;
*через хост*. До этого хаб всегда шёл через хост.

**Сценарии** (экспериментально — отката нет, обкатывайте на тестовых
машинах). Вкладка «Сценарии» в разделе «Профили» — построчный язык для
развёртывания: `group`, `host`, `install`, `wait`, а на хосте
`on ХОСТ… packages|service|firewall|docker|vm|apply|file|user add|system|cert|git clone …`
(в `on` можно перечислить несколько хостов); compose-файл и содержимое
файла кладутся в сценарий блоком до строки `end`. `param ИМЯ "подсказка"`
и `set ИМЯ ask` — значения, которые спрашиваются при запуске (так один
сценарий подходит разным стендам); `wait ХОСТ port|http|service …` ждёт
порт, ответ HTTP или активную службу. Полная справка с примерами —
вкладка «Справка» там же; вкладка «Схема» рисует сценарий: группы →
хосты → действия, машины внутри хоста. «Проверить» разбирает текст и
сверяет имена хостов, групп и профилей; «Сухой прогон» проходит сценарий,
ничего не меняя: у хостов спрашиваются планы (что бы изменилось),
остальные шаги пишутся в журнал как «сделал бы»; «Выполнить» сохраняет,
проверяет, спрашивает пароли, параметры и токены (в текст они не
попадают) и запускает задание хаба: шаг за строкой, остановка на первой
ошибке, продолжение после перезапуска хаба с той же строки. Действия на
хостах идут теми же вызовами, что и кнопки (большей частью — как
маленький профиль с планом и журналом на хосте); произвольных
shell-команд в языке нет намеренно.

Кнопки **«Экспорт»**/**«импорт»** сохраняют/загружают всё, что хаб
знает и что долго заводить заново: хосты с зашифрованными SSH- и
admin-секретами и настройками (связь с машиной, способ доставки
бинарника), группы (в том числе пустые), связь машины с
хостом-родителем (по имени), **кластеры Kubernetes** (запись, узлы с
ролями, адрес API, зашифрованные kubeconfig и план WireGuard — после
импорта кластер в разделе «Кластеры» с рабочими «kubectl», «+ worker»,
«продолжить»), профили и сценарии с историей редакций, шаблоны машин и
настройки хаба (оповещения, группа строки «localhost», умолчания
подготовки, лимит кэша пакетов), сохранённые наборы формы кластера.
Файл — JSON версии 3; файлы версий 1
и 2 по-прежнему импортируются. **Образы для кластеров** (qcow2 в
библиотеке хаба) в файл не входят — только их список: импорт сообщит,
каких файлов нет в `cluster-images` нового хаба, скопируйте их руками
(`scp`). Кэш пакетов, задания, журнал оповещений и учётные записи
пользователей не переносятся. Импорт **дописывает** к существующему —
хост, кластер, профиль, сценарий или шаблон, чьё имя уже занято,
пропускается с сообщением (секреты чужим файлом не перезаписываются);
настройки записываются только там, где их ещё не задавали.

Галочка и токен резервного канала (см. раздел 5) переносятся вместе с
остальным — специально ради переноса на новую машину: смена адреса
хаба — самый частый повод, по которому SSH вдруг перестаёт достучаться
до хоста (файрвол/security group на хосте помнят только старый IP хаба),
и именно тогда резервный канал нужнее всего. Привязка сертификата
хоста (TOFU) при этом не переносится — новый хаб закрепит свой отпечаток
сам при первом подключении, как и при обычной установке.

Экспорт всегда кладёт в файл и сам ключ шифрования хаба: хаб-получатель
на импорте расшифровывает секреты этим встроенным ключом и сразу
перешифровывает их своим собственным — переносить `NKT_HUB_MASTER_KEY`
отдельно не нужно, и после импорта совпадение ключей у двух хабов
больше ни для чего не требуется. Пока ключ в файле, самого файла
достаточно, чтобы расшифровать все секреты всех хостов — обращайтесь с
ним как с файлом паролей и удалите после того, как импортируете.

Именно поэтому «Экспорт» перед скачиванием **обязательно** предлагает
зашифровать сам файл паролем (не путать с ключом хаба внутри него) —
открывается небольшое окно с полем пароля; оставить его пустым и
скачать всё равно можно, но только через отдельное подтверждение. Шифрует
и расшифровывает браузер сам (Web Crypto API, PBKDF2 + AES-256-GCM) —
пароль никуда не отправляется. «импорт» сам распознаёт такой файл и
спросит пароль перед загрузкой. Формат общий с `nkt hub delete -export`/
`nkt hub import` — файл, зашифрованный в браузере, читается консольной
командой, и наоборот.

## 6. Настройка (переменные окружения)

Без Docker — в `/etc/netknownsthat/hub.env` (из `deploy/hub.env.example`,
устанавливает `hub-install`). Через Docker — в `deploy/docker-compose.hub.yml`
(секция `environment`) или файлом `.env` рядом с ним.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NKT_MODE` | `hub` | Не менять — это то, что включает режим хаба. |
| `NKT_ADDR` | `127.0.0.1:8077` без Docker, `0.0.0.0:8077` в примере с Docker | На чём слушает хаб. Без Docker — как у обычного `nkt`, только через reverse proxy наружу; в контейнере привязка к `0.0.0.0` нужна, чтобы сработал проброс порта. |
| `NKT_DATA_DIR` | `/var/lib/netknownsthat-hub` без Docker, `/var/lib/netknownsthat` в Docker-томе | Каталог с базой, кэшем бинарников и ключом шифрования. |
| `NKT_HUB_SOURCE_ROOT` | рабочий каталог при старте | Путь к чекауту исходников — оттуда кросс-компилируются бинарники для новых хостов. Без Docker задайте явно, если репозиторий не там, откуда запущен юнит. Если исходников нет вообще (хаб сам установлен из готового бинарника с Releases, без `git clone`) — хаб сам скачивает готовый бинарник и systemd-юнит с GitHub, версии, совпадающей с версией самого хаба; нужен только исходящий доступ к `github.com`. |
| `NKT_HUB_GO_BIN` | `go` (ищется в `PATH`) | Каким `go` кросс-компилировать бинарники для новых хостов. Если по этому пути ничего нет или он не запускается — хаб сам скачивает подходящий Go с go.dev в `NKT_DATA_DIR/go-toolchain` и дальше использует его; настраивать вручную нужно, только если хотите явно закрепить конкретный уже установленный `go` вместо автоустановки. Не используется вовсе, если сработал вариант выше — скачивание готового бинарника кросс-компиляцию (и Go) обходит. |
| `NKT_HUB_RELEASE_REPO` | `piqab/nkt` | `owner/repo`, откуда скачивается готовый бинарник/юнит, когда `NKT_HUB_SOURCE_ROOT` не находит исходников (см. выше). Меняйте только на форке со своей страницей Releases. |
| `NKT_HUB_MASTER_KEY` | *(пусто → генерируется сам)* | Ключ шифрования (AES-256, base64) для SSH-секретов хостов. Оставьте пустым для автогенерации в `NKT_DATA_DIR/hub.key`, либо задайте явно (`openssl rand -base64 32`), если хотите управлять им отдельно от тома/каталога данных. |
| `NKT_HUB_FINDINGS_POLL_INTERVAL` | `60s` | Как часто хаб в фоне опрашивает `/api/overview` каждого подключённого («online») хоста, чтобы держать под рукой актуальные счётчики находок и признак доступности — независимо от того, открыта ли веб-морда. Опрос идёт через уже установленное SSH-соединение с хостом, ничего дополнительно наружу не стучится. |
| `NKT_HUB_UPDATE_CHECK_INTERVAL` | `6h` | Как часто хаб в фоне проверяет GitHub Releases (`NKT_HUB_RELEASE_REPO`) на версию новее своей — только для бейджа в разделе «О системе» (раздел 9), само обновление применяется исключительно по кнопке там. |
| `NKT_HUB_APTCACHE_MAX_GB` | `20` | Лимит кэша пакетов на хабе (раздел 10), гигабайты; `0` — без лимита. Значение, сохранённое в «О системе», важнее. |
| `NKT_HUB_APTCACHE_PORT` | `3142` | Порт на хосте (`127.0.0.1`), куда хаб пробрасывает кэш пакетов по SSH; его же проверяет `nkt-apt-proxy` на хосте. |
| `NKT_HUB_CLAMDB_REFRESH_INTERVAL` | `24h` | Как часто хаб обновляет копию базы сигнатур ClamAV, которую раздаёт хостам («О системе» → «База ClamAV», на хосте — «база с хаба» во вкладке «Вредоносное»). Копия заводится вручную кнопкой; качается только изменившееся. `0` — не обновлять. |
| `NKT_HUB_VULNDB_REFRESH_INTERVAL` | `12h` | Как часто хаб в фоне поддерживает свежей централизованную базу уязвимостей trivy (раздел 9, «База уязвимостей») — фактическое обновление не чаще раза в сутки, это лишь как часто хаб проверяет, не пора ли. |
| `NKT_BOOTSTRAP_ADMIN_USER` | `admin` | Логин администратора хаба. |
| `NKT_BOOTSTRAP_ADMIN_PASSWORD` | *(пусто → генерируется сам)* | Пароль администратора хаба — как выше, оставьте пустым, если не нужен конкретный. |
| `NKT_TLS_ENABLED` | `false` | `true` — хаб сам слушает HTTPS вместо голого HTTP, без отдельного reverse proxy (см. README, раздел «Открыть»). Самоподписанный сертификат генерируется и переиспользуется в `NKT_DATA_DIR/tls`, если не заданы `NKT_TLS_CERT`/`NKT_TLS_KEY`. |
| `NKT_TLS_HOSTS` | `127.0.0.1,::1,<hostname>` | Какие имена/IP должен покрывать сгенерированный самоподписанный сертификат — добавьте публичный IP/LAN-имя хаба, если открываете его напрямую. |
| `NKT_TLS_CERT`, `NKT_TLS_KEY` | *(пусто)* | Свой сертификат/ключ вместо самоподписанного — оба сразу или ни одного. |
| `NKT_HUB_EXPORT_PASSWORD` | *(пусто)* | Пароль для `nkt hub delete -export .../hub import -file ...` без терминала — сценарий/cron. С терминалом пароль спрашивается интерактивно, без эха; эта переменная только для автоматизации (не передавайте пароль флагом — виден в выводе `ps`). |
| `NKT_HUB_HOST_API_PORT` | `8077` | Порт собственного API nkt на управляемых хостах: хаб пишет его в `nkt.env` при установке и ходит по нему через туннель (только loopback хоста, наружу не открыт). У отдельного хоста может быть свой — поле «Порт API» в его форме; смена перезапускает установку, чтобы переписать `nkt.env`. |
| `NKT_HUB_TUNNEL_PORT` | `8078` | Порт резервного канала (раздел 5): хаб пишет его хосту как `NKT_HUB_TUNNEL_LISTEN_ADDR` при установке и сам же на него дозванивается, тем же адресом хоста, что и SSH — отдельный адрес самого хаба задавать не нужно ни при какой топологии сети. Меняйте только при конфликте порта на каком-то из хостов. |

## 7. Диагностика

**Загрузка файлов через «Диски» → «Файлы»: часть файлов не сохранилась
(«хост недоступен» или другая ошибка).** До v1.10.74 единичная ошибка
теряла файл: повторов не было, а «хост недоступен» — это 502 от прокси
хаба, когда соединение с хостом умерло в пуле (NAT закрыл сессию,
перезапущен sshd). Теперь перед передачей файла хаб проверяет
соединение и меняет мёртвое, клиент повторяет неудачный файл до трёх
раз, а оставшиеся грузятся кнопкой «повторить неудачные»; потоков
загрузки два вместо трёх. Галочка **«без скрытых»** (по умолчанию
включена) не даёт отправить на хост `.git`, `.env` и то, что
перечислено в `.gitignore` загружаемой папки, — заодно исчезают тысячи
лишних запросов, на которых ошибки и вылезали.

**«Файлы» на хосте показывают пустые папки или загруженное не
появляется.** До v1.10.71 юнит хоста собирался с `ProtectHome=yes`:
служба nkt не видела `/home` вовсе — проводник показывал его пустым, а
файл, записанный туда командой снаружи песочницы, не появлялся в списке.
Теперь в юните `ProtectHome=read-only` (запись по-прежнему через выход
из песочницы), загрузка в невидимый каталог отвечает понятной ошибкой, а
раздел «Файлы» предупреждает, если на хосте ещё старый юнит —
**обновите nkt на хосте**, юнит перепишется. `/tmp` убран из корней по
умолчанию: у юнита с `PrivateTmp=yes` он свой, и это не тот `/tmp`,
куда кладут файлы снаружи.

* **Хост навсегда завис на статусе «установка», кнопки задизейблены** —
  нажмите «отменить»: она рядом с кнопкой установки, пока статус
  «установка». Прерывает реально выполняющийся шаг, а не только прячет
  окно с логом. Если это произошло из-за перезапуска самого хаба —
  чинится само при следующем старте, руками ничего делать не нужно.
* **Не пускает по SSH при добавлении хоста** — проверьте вручную:
  `ssh -p <порт> <пользователь>@<адрес>` с теми же данными, что вводили в
  форму. Хаб использует ровно тот же логин/пароль/ключ. При способе входа
  «хаб сгенерирует ключ» самая частая причина — публичный ключ ещё не
  добавлен в `authorized_keys` на хосте (см. раздел 5) или добавлен не
  тому пользователю/не в тот файл.
* **Ошибка при вставке своего ключа** («не похоже на PEM», «формат
  PuTTY», «защищён паролем») — форма проверяет ключ сразу при вводе,
  раньше, чем пробует подключиться. Сообщение называет конкретную причину:
  вставлен `.pub` вместо приватного ключа, файл в формате PuTTY `.ppk`
  (нужен экспорт через puttygen в OpenSSH-формат), или ключ защищён
  паролем (сейчас не поддерживается — снимите пароль `ssh-keygen -p`).
  Если ключ не свой, а нужно просто подключиться — переключитесь на «хаб
  сгенерирует ключ», проблема с форматом тогда не возникает вовсе.
* **«Заливаю бинарник… Ошибка: заливка бинарника: permission denied»** —
  указанный SSH-пользователь не root и не может писать в целевые пути
  напрямую по SFTP; это ожидаемо, установка сама переходит на `sudo`. Если
  ошибка идёт с шага «Устанавливаю файлы…» и упоминает пароль или sudoers —
  у пользователя нет `NOPASSWD` sudo на хосте; текст самой ошибки уже
  содержит готовые команды для этого конкретного пользователя, выполните их
  на самом хосте:
  ```
  echo 'ИМЯ ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/nkt-hub
  sudo chmod 0440 /etc/sudoers.d/nkt-hub
  ```
  либо укажите `root` как SSH-пользователя вместо этого.
* **Настроенный `go` не запускается (например, `go` — snap-пакет, а
  systemd-юнит хаба его блокирует своей же изоляцией:
  `NoNewPrivileges`/`RestrictNamespaces` не дают `snap-confine` собрать
  окружение)** — с этим ничего специально делать не нужно: хаб сам
  обнаруживает, что настроенный `go` не работает, и качает свой,
  изолированный от системного, в `NKT_DATA_DIR/go-toolchain` — в логе
  установки будет строка «go (…) недоступен — устанавливаю собственный Go
  для хаба…». Единственное условие — исходящий доступ к go.dev; если его
  нет (изолированная сеть), поставьте Go вручную и укажите путь в
  `NKT_HUB_GO_BIN` явно.
* **«исходники nkt не найдены (нет go.mod …)»** — хаб запущен не из
  каталога с исходниками, а `NKT_HUB_SOURCE_ROOT` не задан (по умолчанию
  он равен рабочему каталогу процесса). Хаб сам пробует каталог своего
  бинарника и его родителей, поэтому запуск `./nkt hub` из любого места
  внутри клона репозитория работает без настройки; если бинарник вынесен
  наружу (например, в `/usr/local/bin`), но клон репозитория где-то есть —
  задайте `NKT_HUB_SOURCE_ROOT` абсолютным путём к нему в
  `/etc/netknownsthat/hub.env` и перезапустите `netknownsthat-hub`.
  Если же клона нет вообще (хаб установлен из готового бинарника с
  Releases) — хаб молча переходит к скачиванию готового бинарника и
  юнита с GitHub (см. `NKT_HUB_RELEASE_REPO` в разделе 6), и в логе
  установки вместо этой ошибки видны шаги «скачиваю готовый бинарник…»/
  «контрольная сумма совпала». Текст про «исходники не найдены» в этом
  случае вообще не появляется — он всплывает только если скачивание
  тоже не удалось (нет исходящего доступа к `github.com`, версия ещё не
  выпущена на Releases), уже как часть одной объединённой ошибки,
  называющей обе причины сразу.
* **«неподдерживаемая архитектура»** — целевой хост не Linux/amd64,
  arm64 или 32-бит ARM; сейчас не поддерживается.
* **«установка netknownsthat.service … Job for netknownsthat.service
  failed»** — сам systemd на хосте принял юнит, но процесс не запустился.
  Хаб сразу же вытаскивает хвост `journalctl -u netknownsthat` с хоста по
  тому же SSH и показывает его в этом же сообщении после строки «журнал
  сервиса на хосте» — причина (занятый порт, битый env-файл и т.п.) видна
  там, отдельно ходить на хост не нужно.
  Частый случай — `status=226/NAMESPACE` и `Failed to set up mount
  namespacing: /run/systemd/unit-root/etc/haproxy: No such file or
  directory`: на хосте установлен только nginx или только haproxy (либо
  ни одного), а юнит требовал оба каталога через `ReadWritePaths`. С 2026
  оба помечены необязательными (`-/etc/nginx`, `-/etc/haproxy`) — если
  ошибка всё ещё встречается, обновите хаб (юнит перезаливается при
  каждой установке/обновлении хоста, отдельного шага не нужно).
* **Установка зависла на «Жду, пока сервис ответит…»** — на хосте нет
  systemd, либо порт 8077 внутри хоста уже занят чем-то ещё; проверьте
  `systemctl status netknownsthat` на самом хосте по отдельному SSH.
* **Хост показывает «ошибка»** — текст ошибки указан прямо в таблице
  хостов; повторная «переустановить» безопасна — файлы просто перезальются.
* **Колонка «Канал» у хоста с включённым резервным каналом навсегда серая
  «не подключён»** — хаб не может дозвониться до порта `8078` (или
  заданного `NKT_HUB_TUNNEL_PORT`) на этом хосте. Проверьте: файрвол/
  security group хоста пропускает входящие на этот порт (тот же адрес, что
  и SSH — если открыт только 22, порт резервного канала нужно открыть
  отдельно); на хосте вообще поднялся процесс `nkt` после установки
  (`systemctl status netknownsthat`); порт не занят чем-то ещё. Учтите
  также ограничение самого канала: если файрвол блокирует **все** входящие
  на хосте, а не только 22-й — резервный канал попадёт под ту же блокировку
  и не спасёт (см. раздел 5).
* **Забыли пароль администратора хаба** — самый простой способ: кнопка
  «Сменить пароль» внутри интерфейса, если ещё залогинены хоть где-то. Если
  нет — сброс прямо с машины, где крутится хаб:
  ```bash
  # через Docker — прямо на ходу, второй процесс в том же контейнере:
  docker compose -f deploy/docker-compose.hub.yml exec hub nkt passwd -random

  # без Docker — юнит держит базу открытой, так что сначала остановите его
  # (сброс пароля не трогает ничего, что нужно ему во время работы):
  sudo systemctl stop netknownsthat-hub
  sudo env NKT_MODE=hub NKT_DATA_DIR=/var/lib/netknownsthat-hub nkt passwd -random
  sudo systemctl start netknownsthat-hub
  ```

## 8. Остановить / удалить

```bash
# без Docker
sudo systemctl disable --now netknownsthat-hub

# через Docker
docker compose -f deploy/docker-compose.hub.yml down      # остановить, том остаётся
docker compose -f deploy/docker-compose.hub.yml down -v   # остановить и стереть данные хаба
# или: make hub-down
```

Остановка/удаление хаба не трогает уже установленный `nkt` на управляемых
хостах — он останется работать как обычный systemd-сервис; убрать его
оттуда нужно вручную (`systemctl disable --now netknownsthat` на самом
хосте).

`docker compose down -v` и удаление тома стирают файлы, но не более того —
тот, кто получит доступ к диску/снапшоту/бэкапу уже ПОСЛЕ такого удаления
(например, к недавно отданному в аренду VPS), теоретически может
восстановить остатки файлов обычными средствами восстановления с диска.
Для реальной безвозвратности — когда нужна уверенность, что ключ
шифрования (а с ним и SSH-/admin-секреты всех подключённых хостов) никто
посторонний с доступом к этой машине не восстановит — есть отдельная
команда:

```bash
sudo nkt hub delete
```

Спросит, нужен ли экспорт хостов с ключом перед удалением (для переноса на
новый хаб — см. раздел 4 «Добавить хост», кнопки «Экспорт»/
«импорт» делают то же самое из веб-интерфейса), и — если да — **обязательно**
предложит зашифровать сам файл экспорта паролем: файл несёт ключ шифрования
хаба и SSH-/admin-секреты всех хостов открытым текстом, у кого файл — у того
и они, так что хранить его как есть не стоит. Согласились — пароль
спрашивается дважды, без эха, и файл на диске оказывается уже
зашифрованным (AES-256-GCM, ключ из пароля через PBKDF2 — тот же формат,
что и у шифрования из веб-интерфейса, файлы взаимно читаются); отказались (пустой
пароль) — файл сохраняется как есть, но с явным предупреждением, что он
без пароля читается кем угодно. Затем — подтверждение самого удаления
словом «удалить», и только после этого:

1. останавливает и отключает `netknownsthat-hub` (best-effort — если это
   Docker-развёртывание без systemd-юнита, просто пропускается);
2. **затирает** (не просто удаляет — сначала перезаписывает случайными
   данными, потом убирает файл) ключ шифрования, базу (со всеми
   SSH-/admin-секретами хостов), историю правок конфигов и TLS-ключ;
   кэш собранных бинарников и самоустановленный Go-тулчейн — просто
   удаляет обычным способом, без перезаписи: в них нет ничего секретного,
   только публичный код, а Go-тулчейн — это тысячи мелких файлов, чьё
   пофайловое затирание с `fsync` на медленном диске VPS может растянуться
   на минуты и выглядеть так, будто команда зависла.

Восстановить экспортированные хосты на новом (или том же, заново поднятом)
хабе:

```bash
sudo nkt hub import -file nkt-hub-export.json
```

Понимает и обычный, и зашифрованный паролем файл сама — спросит пароль,
если файл им защищён (или возьмите его из `NKT_HUB_EXPORT_PASSWORD`, для
скриптов). Расшифровка происходит только в памяти, файл с открытым
содержимым на диске никогда не появляется.

Бинарник и сам systemd-юнит `hub delete` не трогает: `sudo systemctl start
netknownsthat-hub` сразу после этого поднимает полностью новый хаб — новый
ключ шифрования, новая учётная запись администратора — без переустановки.
Управляемые хосты и `nkt` на них эта команда не трогает вовсе — только
регистрацию хаба о них.

Обе команды только консольные, без кнопки в интерфейсе — специально, чтобы
их нельзя было вызвать ничем, кроме уже имеющегося доступа к самой машине
хаба. Без терминала (`-yes` или запуск не в TTY) `hub delete` требует явно
указать один из `-export <файл>`/`-no-export` — молча пропустить вопрос про
бэкап нельзя; шифрование в этом случае включается только через
`NKT_HUB_EXPORT_PASSWORD` (передавать пароль флагом небезопасно — виден в
выводе `ps`), не заданной переменной без терминала соответствует
предупреждение и незашифрованный файл, не отказ выполнить удаление
целиком. Как и у любого затирания на уровне файлов, есть честная оговорка:
на SSD из-за wear levelling и на журналируемых/copy-on-write файловых
системах (btrfs, ZFS) старые блоки данных могут пережить перезапись
где-то ещё на диске — это защищает от обычного восстановления удалённых
файлов, а не даёт крипто-гарантию для мира с форензик-лабораторией и
физическим доступом к самому носителю.

## 9. О системе (обновления хаба и централизованная база уязвимостей)

В веб-интерфейсе, рядом со страницей «Хосты» (виден до выбора хоста —
то же место, где сейчас «Хосты» на весь экран), есть раздел **«О
системе»**: собственная версия хаба, последняя версия на GitHub Releases
(`NKT_HUB_RELEASE_REPO`) и кнопка обновления. Это не про версии
управляемых хостов — они, как и раньше, на странице «Хосты»
(`isOutdated`/бейдж «доступно обновление» там же).

Хаб сам, в фоне, раз в `NKT_HUB_UPDATE_CHECK_INTERVAL` (по умолчанию 6ч,
раздел 6) спрашивает у GitHub, какая версия свежая, и показывает бейдж в
навигации, если она новее текущей — **только для сведения**, само
обновление ничего не применяет само по себе, только по нажатию кнопки
«Обновить до vX.Y.Z» на этой странице (плюс «Проверить снова» — разовая
проверка без ожидания фонового тика).

Там же — описание релиза с GitHub. Пока обновления нет, показываются
заметки **установленной** версии («Что нового в этой версии») — после
обновления полезно прочесть, что приехало, а пустое место на их месте
не говорит ничего. Как только выходит следующая версия, блок сам
переключается на её заметки.

**Бета-версии.** Тег `vX.Y.Z-beta` собирает такой же релиз, но
помеченный pre-release: бинарник несёт версию `X.Y.Z-beta`, образ хаба
публикуется как `:X.Y.Z-beta` и `:beta` (`:latest` не трогается).
Галочка **«использовать бета-версии»** в карточке версии переводит хаб
на бета-канал: беты считаются за обновления, «последняя доступная»
после переключения перепроверяется сразу. Без галочки хаб на бете
обновится до стабильной сборки той же версии, когда она выйдет (бета
считается старше стабильной с тем же номером). Хосты галочки не имеют:
они всегда приводятся к версии хаба — бета-хаб раздаёт бету. Бета-сборка
помечена бейджем «beta» рядом с «nkt» в шапке и рядом с версией в
«О системе».

Нажатие «Обновить»:

1. скачивает бинарник нужной версии под архитектуру этой машины и
   `deploy/netknownsthat-hub.service` того же тега с GitHub, сверяет
   SHA256SUMS — тот же механизм, что и у `NKT_HUB_SOURCE_ROOT`-фолбэка
   (раздел 6), просто версия не текущая, а последняя найденная;
2. кладёт бинарник в `/usr/local/bin/nkt` и юнит в
   `/etc/systemd/system/netknownsthat-hub.service`, затем
   `systemctl daemon-reload && systemctl restart netknownsthat-hub` — в
   отдельном неограниченном transient-юните через `systemd-run` (тот же
   приём, что и у веб-терминала и обновлений ОС, см. README, раздел
   «Безопасность»), поскольку `ProtectSystem=strict` самого хаба не даёт
   писать ни туда, ни туда напрямую;
3. хаб становится недоступен на несколько секунд, пока сам себя
   перезапускает — открытая страница «О системе» это отслеживает
   (опрашивает `/api/health`) и перезагружается сама, как только хаб
   снова отвечает.

**`hub.env` (или `.env`/переменные окружения контейнера) это обновление
не трогает** — в отличие от `nkt.env` управляемого хоста, который хаб
перегенерирует при каждой установке, `hub.env` полностью на совести
оператора.

Кнопка «Обновить» показывается, только если хаб прямо сейчас реально
запущен как systemd-юнит (в окружении процесса есть `INVOCATION_ID` —
его выставляет только сам systemd, при `systemctl start`). Без этого
кнопки не будет по двум разным причинам:

* **Docker/Kubernetes** — бинарник живёт внутри слоя образа, а не на
  перезаписываемом диске, и обновление — это `docker compose pull &&
  docker compose up -d` (или пересоздание пода/деплоймента) самим
  оператором, как и с любым контейнерным приложением;
* **бинарник скачан (например, curl'ом) и запущен вручную, не через
  systemd** — самообновлять в этом случае физически нечего перезапускать
  контролируемо: поставьте и запустите хаб как сервис (`sudo make
  hub-install && sudo systemctl enable --now netknownsthat-hub`, раздел
  2.1) — после этого `INVOCATION_ID` появится и кнопка станет доступна.

Раздел «О системе» в обоих случаях всё равно показывает текущую/
последнюю версию и бейдж — просто без кнопки, с пояснением вместо неё.

Под версией — **описание новой версии** (тело GitHub Release, которое
`release.yml` собирает из разделов `WHATSNEW.md`, накопившихся с
прошлого тега) на языке интерфейса: в тело релиза после маркера
`<!-- en -->` приклеиваются те же разделы из `WHATSNEW.en.md`, хаб
делит тело по маркеру и отдаёт английскому читателю английскую часть.
У релизов старше v1.10.61 английской части нет — показывается
русская.

### База уязвимостей

Ниже на той же странице — карточка **«База уязвимостей»**. До этого
раздела каждый управляемый хост при сканировании (страница
«Уязвимости») сам качал из интернета и trivy (~50 МБ), и его базу
(~100–150 МБ сжатой, ~1 ГБ распакованной) — независимо от остальных
хостов. Теперь эта база — одна на хаб, централизованная:

* хаб в фоне, раз в `NKT_HUB_VULNDB_REFRESH_INTERVAL` (по умолчанию
  12ч), сам поддерживает её свежей — фактическое скачивание не чаще
  раза в сутки, EnsureDB сама решает, устарела ли база;
* кнопка «Обновить сейчас» на этой же карточке форсирует проверку, не
  дожидаясь фонового тика (сам ~100 МБ повторно не качается, если база
  и так свежая);
* при нажатии «Сканировать» на странице «Уязвимости» **управляемого**
  хоста хаб больше не просит сам хост качать что-либо для пакетов ОС:
  хаб забирает у хоста манифест установленных пакетов (сотни КБ —
  дамп `dpkg`, `/etc/os-release`) через уже установленное SSH-соединение
  и сканирует его сам, своей базой. Хосту для этой части вообще не
  нужны ни trivy, ни база на диске;
* **сканирование образов контейнеров при этом остаётся на самом
  хосте** — оно раскладывает пакеты внутри образа через локальный
  Docker/Podman-сокет, до которого у хаба доступа нет и быть не может.
  Хост, у которого реально запущены контейнеры, всё равно один раз
  ставит себе trivy и базу — но только ради этой части, а не ради всего
  скана целиком, и не переустанавливает их при каждом сканировании.
  Хост без единого контейнера (частый случай) вообще ничего не качает.
* «localhost» (сама машина хаба, раздел 4) использует ровно ту же базу
  — она физически один и тот же каталог (`NKT_DATA_DIR/vuln`), что и у
  централизованного сканирования остальных хостов, поэтому не
  дублируется.

### 9.1. Разбор моделью (ИИ)

Карточка **«Разбор моделью (ИИ)»** в «О системе» — одна настройка на всю
установку: провайдер, адрес, модель, ключ. Ключ хранится на хабе
зашифрованным тем же мастер-ключом, что и секреты SSH, наружу не
отдаётся никогда (API сообщает только, задан он или нет), а запросы
уходят с хаба — **хостам интернет не нужен**.

Провайдеры: **Anthropic** и **OpenAI-совместимый** — последний включает
локальные модели (Ollama `http://127.0.0.1:11434`, vLLM, LM Studio,
внутренний шлюз). С локальной моделью наружу не уходит ничего; ключ ей
обычно не нужен.

Кнопка **«Проверить»** рядом с «Сохранить» отправляет модели короткий
пробный вопрос теми настройками, что сейчас в форме (ключ можно не
набирать заново — пустое поле значит «взять сохранённый»), и показывает
ответ и время. Неверный адрес или ключ видно сразу, а не при первом
разборе. Суточный лимит проверке не мешает.

**Время ожидания ответа** (10–1800 с, по умолчанию 90) — сколько хаб
ждёт модель. Облаку хватает 90 секунд; локальной модели на слабой машине
с длинным разбором нужно 300 и больше — «Проверить» с коротким вопросом
успевает, а разбор находки нет, и окно висит «модель думает…» до
ошибки. Счётчик секунд в окне показывает, что ожидание идёт; по
истечении срока приходит понятный отказ с подсказкой поднять значение.

По умолчанию всё выключено. Включённый разбор добавляет кнопку-лампочку
в строку **находки** (в том числе в карточке «Что сломано» на обзоре),
**уязвимости** (пакеты хоста и образы контейнеров), **вредоносного** —
и улик «Майнеры и признаки взлома», и находок ClamAV, — **оповещения**
хаба и к **ошибке задания**: модель объясняет, что это значит, чем
грозит именно здесь (хаб добавляет в запрос, что рядом: порты,
контейнеры, firewall) и что сделать — по шагам, с командами. Команды
только показываются: **модель ничего не выполняет**, применяете вы.

На странице **«Карта ресурсов»** — карточка «Архитектурный разбор»:
модель смотрит на карту целиком (узлы, связи, публичность, находки) и
говорит о точках отказа, лишней публичности, несогласованностях и о
том, с чего начать. На хабе тот же разбор доступен по всем хостам
сразу. Разборы сохраняются с датой — видно, что изменилось с прошлого
раза.

**Ответ остаётся у находки.** Лампочка без ответа — контурная
стандартного синего, как остальные иконки действий. После разбора она
становится **оранжевой** и открывает сохранённый ответ без нового
запроса (дата и модель под ответом; «спросить заново» и «удалить
ответ» — там же). Если **такая же находка** уже разбиралась на другом
хосте, лампочка **залитая синяя**:
окно сначала показывает тот ответ с пометкой «уже разбиралась: `web-1`,
дата», а свой запрос для этого хоста делается отдельной кнопкой — платить
за одну и ту же проблему на десяти хостах незачем, но и подменять ответ
чужим молча нельзя. Ключ находки — вид, заголовок, объект и файл;
подробности (PID, даты) в него не входят. «Очистить кэш» в «О системе»
чистит и сохранённые ответы.

**Инструкции модели (промпты).** В карточке ИИ, раздел «Инструкции
модели»: системная инструкция для **разбора находки** и для
**архитектурного разбора**, каждая на русском и английском. Стандартные
лежат в nkt; правка хранится на хабе. «Сохранить инструкцию» сначала
открывает окно с **диффом** «стандартная → ваша», и только «Применить»
записывает; «Вернуть стандартную» снимает правку. Смена инструкции
чистит сохранённые ответы — они получены другой инструкцией. Правленые
инструкции входят в экспорт/импорт.

**Ошибка правки конфигурации.** При любом отказе записи — проверка или
apply не прошли и правка откатилась, либо до записи не дошло (путь вне
разрешённых, конфликт версий, валидатор не установлен) — в баннере
ошибки редактора конфигураций, формы нового файла, блочного редактора и
XML машины — та же лампочка: модели уходят вывод проверки и **дифф
правки** «на диске → черновик», а не весь файл, с задачей объяснить, что
не так, и показать исправленный фрагмент.

**Секреты не уходят никогда.** Независимо от галочки ниже, из запроса
вырезаются пароли, токены и ключи: значения после `password`, `secret`,
`token`, `api_key` и подобных, блоки `PRIVATE KEY`, `Authorization:
Bearer …`, учётные данные в URL (`user:pass@`), ключи известных сервисов
по форме (`AKIA…`, `sk-…`, `ghp_…`, JWT). Имя ключа остаётся — модель
видит, что это пароль, но не его значение; обратно оно не
подставляется. «Показать запрос» под ответом показывает ровно то, что
ушло.

**Что уходит наружу.** По умолчанию включена галочка «скрывать адреса и
имена»: имена хостов и машин, IP, домены и почта заменяются
псевдонимами (`host-1`, `ip-1`, `domain-1`), а в ответе подставляются
обратно — модель видит структуру проблемы, а не ваши адреса. Кнопка
«показать запрос» под каждым ответом показывает ровно то, что ушло.
Ответы кэшируются по содержимому (одна находка на десяти хостах — один
запрос), расход считается по суткам с лимитом из настроек.

### 9.2. Приватный режим

Галочка **«скрыть чувствительное»** — для показа экрана и скриншотов: адреса и имена хостов и
машин, SSH- и admin-пользователи, ключи и токены, адреса API кластеров
и узлов, домены сертификатов, IP/MAC в интерфейсах и сокетах
размываются на всех страницах хаба и хостов; в свободном тексте
(журналы заданий, оповещения, «Проблемы», аудит) размываются IPv4/IPv6,
MAC, e-mail и имена хостов из списка хаба; терминал, логи и топология —
целиком. Домены (`api.example.com`, в том числе внутри путей вроде
`/etc/letsencrypt/live/api.example.com/fullchain.pem` и имён файлов
`app.example.com.pem`) размываются по списку ходовых TLD; домены и
lineage сертификатов со страницы «Сертификаты» — всегда. Модальные
окна тоже: заголовки с именем хоста/машины/домена, поля адреса, имени,
пользователя и ключей в формах, журналы установки и продления,
фрагменты конфигураций, тексты подтверждений. Ничего не показывается
по наведению — чтобы прочитать, выключите режим. Галочка — в «О
системе» (у одиночного nkt без хаба — внизу меню, за темой); состояние
помнится в браузере; метка режима — бейдж «nkt» в шапке сайдбара (и
«nkt — hub» над страницей хоста), в приватном режиме оранжевый. Имена групп, профилей, сценариев,
кластеров, пакетов и служб не скрываются — без них экран нечитаем.

### 9.3. Язык журналов заданий и оповещений

Журналы заданий (заголовок, шаг, строки, ошибка) и детали оповещений
хаба переводятся **при показе**: с v1.10.61 в базе рядом с текстом
хранится ключ сообщения и аргументы (`jobs.title_key/step_key/
error_key`, `job_log.key/args`, `host_events.detail_key/detail_args`),
и API подставляет строку на языке читающего — задание, запущенное из
русского интерфейса, английский пользователь видит по-английски, и
наоборот. Строки, записанные до этой версии, и сырой вывод инструментов
(apt, kubeadm, ssh, вывод сценариев) не переводятся — показываются как
записаны.

## 10. Кэш пакетов

Хосты качают пакеты через хаб, и каждый `.deb` уходит в интернет один
раз на все хосты. Устроено без публичного адреса у хаба и без новых
открытых портов у хостов:

* хаб держит к каждому хосту с включённым **«пакеты через кэш хаба»**
  (галочка в форме хоста, включена по умолчанию) отдельную SSH-сессию с
  **обратным пробросом порта**: на хосте `127.0.0.1:3142`
  (`NKT_HUB_APTCACHE_PORT`) ведёт в кэширующий прокси хаба; сессия
  переподключается сама, значок в колонке «Канал» показывает, держится
  ли проброс сейчас;
* на хосте лежат `/etc/apt/apt.conf.d/99nkt-hub-proxy` и
  `/usr/local/bin/nkt-apt-proxy` — штатный `Acquire::http::Proxy-Auto-Detect`:
  скрипт отвечает адресом прокси, если порт открыт, и `DIRECT`, если хаб
  не подключён — apt при этом работает как обычно. Раскладываются при
  установке nkt с хаба, а для уже установленного хоста — сразу по SSH при
  включении галочки (нужен root или sudo без пароля);
* кэшируется только неизменяемое — `pool/…` и `by-hash/…`; индексы
  репозиториев (`dists/…`) идут насквозь, `https`-репозитории
  туннелируются как есть (внутрь TLS прокси не смотрит);
* «О системе» → **«Кэш пакетов»**: размер, число файлов, попадания и
  промахи, трафик, сколько хостов на пробросе, лимит (гигабайты, `0` —
  без лимита; вытесняется самое давно не спрошенное) и очистка.

Строка «localhost» (сама машина хаба) через кэш не ходит — пробрасывать
порт самому себе незачем.

### 10.1. Файлы по ссылке и зеркало registry — хост без интернета

Тот же порт умеет больше, чем apt: всё, что хосту нужно из интернета для
кластеров и машин, при открытом порте идёт через хаб и **оседает в его
кэше** — хост без выхода наружу получает это с хаба, а хост с выходом
не качает по разу на узел то, что хаб уже видел. Признак у хоста тот же,
что у apt: открыт ли `127.0.0.1:3142` и отвечает ли он как кэш nkt
(`/nkt/ping`; чужой прокси на том же порту не примется за свой). Порт
закрыт — всё идёт напрямую, как раньше.

* **Файлы по ссылке** — `GET http://127.0.0.1:3142/nkt/artifact?url=…`:
  хаб качает ссылку сам и отдаёт из кэша. Так берутся установщик и
  бинарник k3s с его **airgap-образами** (`k3s-airgap-images-<arch>.tar.zst`,
  кладутся в `/var/lib/rancher/k3s/agent/images/`, k3s ставится с
  `INSTALL_K3S_SKIP_DOWNLOAD`), Cilium CLI, ключ репозитория
  `pkgs.k8s.io`, манифест Flannel, облачные образы машин. Ссылки с
  версией в пути (`…/releases/download/v1.2.3/…`) и `.deb` лежат
  бессрочно, остальное (`get.k3s.io`, `…/latest/…`, «текущий» образ
  Ubuntu) перекачивается, когда старше 6 часов; если источник недоступен,
  а копия есть — отдаётся копия.
* **Зеркало registry** (pull-through cache) — `/v2/…` на том же адресе.
  containerd на узле настраивается брать `docker.io`, `quay.io`,
  `registry.k8s.io`, `ghcr.io` и `gcr.io` через зеркало (k3s —
  `/etc/rancher/k3s/registries.yaml`, kubeadm —
  `/etc/containerd/certs.d/<registry>/hosts.toml`); к запросам containerd
  сам добавляет `?ns=<registry>`, по которому зеркало находит источник.
  Слои и манифесты по digest лежат бессрочно, «тег → digest» — 5 минут,
  при недоступном источнике берётся прошлое значение. К источникам хаб
  ходит анонимно (Bearer по вызову `WWW-Authenticate`, как у Docker Hub,
  quay.io, ghcr.io); приватные образы через зеркало не идут.
* `.deb` с `https`-репозиториев (`pkgs.k8s.io`) по-прежнему туннелируются
  без оседания — apt ходит по своим ссылкам внутри TLS.
* Сухой прогон кластера проверяет ссылки с хоста **через кэш хаба**, если
  он есть, и пишет об этом («через кэш хаба доступен …»).

## 11. Кластеры Kubernetes на виртуалках

У хоста с виртуализацией (QEMU/KVM, см. «Машины внутри хоста») рядом с
«новая машина» есть **«новый кластер»**:

* **вариант** — `k3s` (один бинарник, HA со встроенным etcd) или
  `kubeadm` (containerd, репозиторий `pkgs.k8s.io` актуальной stable-ветки
  — хаб узнаёт её по `dl.k8s.io/release/stable.txt` при создании,
  записывает в кластер и ставит одну и ту же на все узлы, включая
  добавленные потом worker'ы; в форме — поле «Версия Kubernetes»
  (актуальная stable и три предыдущие ветки; у k3s это канал `v1.36`),
  в сценарии — `version 1.34`. Порт API внутри узла всегда 6443 —
  порты в «пробросить наружу» относятся к хосту.
  Старые ветки вроде v1.31 на Debian 13 не годятся — apt там проверяет
  подписи через `sqv`, который отвергает их подпись как устаревшую.
  Flannel; containerd
  на машине из облачного образа ставится пакетом дистрибутива, а на
  «железном» хосте уже стоящий — например, `containerd.io` от Docker —
  не трогается: у него только включается CRI и `SystemdCgroup`, копия
  прежнего конфига остаётся в `config.toml.nkt-bak`, контейнеры Docker
  при перезапуске containerd не останавливаются);
* **топология** — одна машина (control plane без taint, он же worker);
  1 control plane + N worker; 3 control plane + N worker (пока только
  k3s);
* размеры машин отдельно для control plane и worker'ов, образ (Ubuntu
  24.04 по умолчанию), сеть libvirt;
* **Cilium** (галочка, по умолчанию включена) — вместо flannel: k3s
  поднимается без встроенного flannel, kubeadm — без Flannel, после
  старта control plane ставится `cilium` CLI (последняя стабильная версия,
  архив с GitHub с проверкой суммы) и `cilium install`; галочка «заменить
  kube-proxy на Cilium» — eBPF вместо kube-proxy (`--disable-kube-proxy` у
  k3s, `--skip-phases=addon/kube-proxy` у kubeadm);
* **пробросить наружу** — на хосте заводятся DNAT-правила с портов
  хоста (по умолчанию `6443`, `80`, `443`, любой можно заменить или
  обнулить — тогда он не пробрасывается) → `6443`/`80`/`443` control plane (свои цепочки `NKT-PF`, юнит
  `nkt-portforward.service` восстанавливает их при загрузке), и кластер
  доступен по адресу хоста; без проброса — только из сети хоста.

Задание хаба (журнал — в «Заданиях»): создаёт машины по одной тем же
путём, что «Новая машина» (cloud-init, nkt внутрь), ставит на первую
control plane официальной процедурой (`get.k3s.io` или `kubeadm init`),
берёт у неё токен, присоединяет остальные control plane и worker'ы,
ждёт, пока все узлы станут `Ready`, настраивает проброс и забирает
kubeconfig (адрес сервера в нём — хост и выбранный API-порт при пробросе,
иначе машина:6443). Раздел экспериментальный: отката нет, начинайте с
сухого прогона на тестовом хосте.
Узлы — обычные записи хостов (машины под своим хостом в списке) с ролями
`control-plane`/`worker`; отдельная группа под кластер не заводится —
узлы видны у хоста и в карточке кластера. У control plane в «Контейнеры
и ВМ» появляется вкладка **Kubernetes** (узлы, поды).

**Сухой прогон** в том же диалоге — проверки без изменений: план машин,
`/dev/kvm`, `libvirtd`, программы для машин, место в каталоге дисков,
память и ядра, сеть libvirt, образ, свободны ли имя кластера и имена
машин, порты 6443/80/443 при пробросе, доступность `get.k3s.io` /
`pkgs.k8s.io` и образа с хоста; итог — чек-лист в журнале задания. С
галочкой «заодно подготовить» скачиваются образ и пакеты для машин в
кэш apt (без установки), поднимается (или заводится как NAT) сеть
libvirt узлов, а если у хоста открыт кэш хаба — хаб сам кладёт в свой
кэш всё, что узел потом возьмёт с него: установщик, бинарник k3s с
суммами и airgap-образами своей ветки, Cilium CLI, ключ репозитория,
манифест Flannel, образ машины. Проверку ссылок при этом делает хаб
(«в кэше хаба: … (N МБ)»), а не хост через туннель. Те же проверки
идут первым шагом настоящего создания и останавливают его до первой
машины.

**kubectl.** У кластера в статусе «готов» кнопка **«kubectl»** открывает
в отдельном окне браузера терминал на первом control plane с готовым
`kubectl`: `KUBECONFIG` указывает на admin-конфиг (`/etc/kubernetes/
admin.conf` у kubeadm, `/etc/rancher/k3s/k3s.yaml` у k3s), подгружено
автодополнение, алиас `k`. Это обычный терминал хоста
(`/api/terminal/ws?kubectl=1`, от пользователя терминала через
`sudo -n`), так что у узла должен быть включён терминал — у машин,
созданных хабом, он включён; доступ к API снаружи не нужен. Та же
кнопка — во вкладке Kubernetes у control plane. Права — admin, как у
скачанного kubeconfig.

**Если создание упало** (скажем, на установке роли), начинать с нуля не
нужно: в окне журнала упавшего задания есть **«попробовать снова»**, а у
кластера со статусом «ошибка» в карточке — **«продолжить»**. Заводится
новое задание с теми же параметрами и сохранённым состоянием: созданные
машины, поднятый туннель, установленные роли пропускаются, упавший шаг
выполняется заново (`kubeadm init`/`join` при этом сами сносят остатки
неудачной попытки, живой узел не трогают). Старый журнал остаётся.
Так же продолжаются сценарии (`script.run`; ответы на вопросы `ask`
после провала хранятся в памяти хаба ещё час — за это время можно
повторить, потом только заново с вопросами) и установка Kubernetes на хосте
(сделанные шаги пропускаются). API: `POST /api/jobs/{id}/retry`, `POST
/api/hub/clusters/{id}/retry`; в ответе `/api/jobs/{id}` — признак
`resumable`. Если провалились ещё проверки (запись кластера уже удалена)
— «снова» скажет об этом, создавайте кластер заново из формы.

Карточка **«Кластеры Kubernetes»** под списком хостов: узлы и связь с
ними, `kubeconfig` (скачать), «+ worker» (ещё одна машина с теми же
настройками входит в кластер), удаление кластера — машины удаляются с
дисками вместе с записью. В сценариях то же самое —
`on ХОСТ k8s create ИМЯ [flavor …] [nodes single|1+N|3+N] … [expose]` и
`on ХОСТ k8s destroy ИМЯ`; размещение на нескольких хостах — строкой в
кавычках, как таблица раздела «Кластеры»:
`on hv1 k8s create lab nodes "hv1: cp 1, w 2; hv2: w 2; hv3: host w" network wireguard cni cilium expose api 16443`
(`cp N` / `w N` — машины с ролью, `host cp|w` — сам хост как узел,
`bridge МОСТ` в строке хоста или общий `bridge МОСТ` — для режима моста,
`endpoint АДРЕС` — адрес хоста для соседей по WireGuard;
`network nat|bridge|wireguard` — сеть между хостами).

### 11.1. Кластер на нескольких хостах — раздел «Кластеры»

Раздел «Кластеры» в меню хаба показывает все кластеры и создаёт кластер,
растянутый на несколько хостов. Форма — **таблица размещения**: строка =
хост из списка nkt → роль (control plane / worker) → **машины** (N штук,
размеры, образ) или **сам хост** (Kubernetes ставится прямо на него,
запись хоста остаётся при удалении кластера). Control plane — 1 или 3
(kubeadm — 1).

**Сеть между хостами:** `NAT` (сеть libvirt) — только когда все узлы на
одном хосте; `мост` — у каждой строки с машинами указывается мост
хоста, машины получают адреса из сети хостов (хосты — в одном
L2-сегменте; адрес узнаётся через `qemu-guest-agent`, который cloud-init
ставит при первом запуске); `WireGuard` — туннель между хостами. Проброс
наружу и адрес kubeconfig — с хоста первого control plane. Сухой прогон
проходит проверки по каждому хосту (для узла-хоста — что Kubernetes там
ещё не стоит; для моста — что он есть на хосте).

**Сохранённые наборы.** В форме сверху — «Сохранённые наборы»: «сохранить
набор» запоминает всю форму под именем (имя кластера, вариант и версия,
сеть, строки размещения, адреса для соседей, Cilium, порты) на хабе;
выбор набора заполняет форму заново (хосты — по имени; если хоста уже
нет — строка без хоста и подсказка). Наборы едут в экспорт/импорт.

**Свои образы.** Карточка «Образы для кластеров» в разделе: загрузите
qcow2/img/raw на хаб один раз (до 10 ГБ, каталог `cluster-images` в
данных хаба) — в форме размещения он появляется как «с хаба: …»
(`hub:<файл>`), в сценарии — `image hub:<файл>`. При создании хаб
заливает образ на каждый хост размещения, где его ещё нет (сравнивая
по размеру), в каталог дисков libvirt через API хоста по SSH-каналу, и
создаёт машины из `host:<файл>`; сухой прогон показывает, куда образ
будет залит и есть ли он в библиотеке. Образ должен быть облачным
(cloud-init) — так задаются пользователь и ключ. Удаление из
библиотеки копии на хостах не трогает.

**WireGuard.** Хосты не обязаны быть в одном сегменте и не нуждаются в
публичных адресах — достаточно, чтобы они видели друг друга (LAN, VPN)
по адресу из списка nkt или по «адресу для соседей», который задаётся в
форме на каждый хост (если хаб ходит на хост по адресу, которого соседи
не видят); между ними должен проходить UDP 51820. Хаб
генерирует ключи (хранятся зашифрованными в записи кластера) и на каждом
хосте: ставит `wireguard-tools`, если его нет; пишет
`/etc/wireguard/nktwg<N>.conf` и поднимает `wg-quick@nktwg<N>`
(интерфейс по номеру кластера, адрес `10.200.<N>.<i>/24`); заводит
отдельную сеть libvirt `nktwg<N>` (NAT, подсеть `10.<100+N>.<i>.0/24`) —
в неё попадают машины кластера на этом хосте. Подсети машин соседей
приходят через `AllowedIPs` (маршруты ставит wg-quick), а `PostUp`
открывает UDP-порт, пропускает FORWARD через туннель и снимает маскарад
libvirt для трафика между подсетями машин — узлы видят друг друга по
настоящим адресам. Узел-хост получает `--node-ip` с адресом в туннеле.
После подъёма хаб проверяет, что каждая пара хостов отвечает по
адресам туннеля (а если нет — смотрит рукопожатие `wg show`: без него
в журнале так и пишется «UDP 51820 закрыт или адрес неверный»), и
только потом создаёт машины; в сухом прогоне — адрес хоста (не
`127.0.0.1`, не совпадает у двух хостов), наличие `wireguard-tools` (с
подготовкой скачивается в кэш) и ping между хостами (предупреждение,
если ICMP закрыт). При удалении
кластера туннель и сеть машин убираются с каждого хоста.
