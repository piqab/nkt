# Хаб NetKnownsThat — управляющий центр для нескольких VPS

Обычный `nkt` следит за одним Linux-хостом. `nkt hub` — тот же бинарник в
другом режиме: разворачивается на одной VPS и оттуда устанавливает и
обслуживает `nkt` на остальных ваших хостах по SSH. Дальше каждый хост
открывается прямо в интерфейсе хаба — те же страницы (Docker, Podman, LXD,
сертификаты, карта ресурсов, конфиги...), что и у обычного `nkt` на одном
хосте, просто с выбором хоста наверху.

Подробное описание архитектуры и API — в [README.md, раздел 10](README.md#10-управляющий-центр-хаб).
Этот файл — только про то, как запустить.

По умолчанию — обычный systemd-сервис, как и у самого `nkt` (раздел 1
основного README): без Docker, без контейнеров, тот же принцип наименьших
привилегий. Docker — альтернативный, самодостаточный вариант упаковки, если
он вам удобнее (раздел 2.2 ниже).

## 1. Что нужно

* Linux-хост для самого хаба. Ему не нужны root-права на что-либо внутри
  себя (см. ниже). Отдельно ставить Go не обязательно — если системного
  `go` нет или он не запускается (например, `snap`-пакет под жёстко
  урезанным systemd-юнитом, см. раздел 6), хаб при первой установке хоста
  сам скачает и распакует Go с go.dev в свой каталог данных — ровно то же,
  что `make native-build` уже делает для сборки самого `nkt`.
* SSH-доступ с этой машины до каждого хоста, который вы хотите добавить:
  IP/имя, порт, пользователь с правом `sudo`/root (установка кладёт файлы в
  `/usr/local/bin`, `/etc/systemd/system`, `/etc/netknownsthat`) и либо
  пароль, либо приватный ключ.
* Целевые хосты — Linux, amd64 или arm64. Больше ничего заранее ставить на
  них не нужно: хаб сам соберёт и зальёт нужный бинарник.

## 2. Запуск

### 2.1. Без Docker (по умолчанию)

Соберите и установите как обычный `nkt`, только другой юнит и env-файл:

```bash
git clone <этот репозиторий> /opt/netknownsthat
cd /opt/netknownsthat
make build                    # или make native-build, если нет Docker для самой сборки
sudo make hub-install
sudo systemctl enable --now netknownsthat-hub
```

`hub-install` кладёт бинарник в `/usr/local/bin/nkt`, юнит
`netknownsthat-hub.service` и заготовку `/etc/netknownsthat/hub.env` (правьте
её — как минимум `NKT_HUB_SOURCE_ROOT`, если репозиторий не в
`/opt/netknownsthat`). В отличие от обычного `nkt`, юнит **не требует root**:
`systemd` сам заводит непривилегированного пользователя на время работы
(`DynamicUser=yes`) — хабу нечего делать с правами суперпользователя, он не
трогает состояние этой машины, только держит свои данные и ходит по SSH на
другие хосты.

Проверить, что поднялось:

```bash
curl -s http://127.0.0.1:8077/api/health
journalctl -u netknownsthat-hub -f
```

По умолчанию слушает только `127.0.0.1` — как и обычный `nkt`, снаружи нужен
свой reverse proxy с TLS (см. раздел 1.4 основного README — та же схема).

### 2.2. Через Docker (альтернатива)

Из корня репозитория:

```bash
docker compose -f deploy/docker-compose.hub.yml up -d --build
# или: make hub
```

Первая сборка образа собирает фронтенд и Go-бинарник — займёт пару минут;
дальше пересборки идут из кэша. Этот путь сразу публикует порт наружу
(`0.0.0.0` внутри контейнера, см. раздел 5) — поставьте перед ним свой TLS,
если это не только локальный тест.

```bash
curl -s http://127.0.0.1:8443/api/health
```

## 3. Первый вход

При первом старте хаб сам создаёт учётную запись администратора и печатает
пароль в лог:

```bash
journalctl -u netknownsthat-hub                                    # без Docker
docker compose -f deploy/docker-compose.hub.yml logs hub           # через Docker
```

Ищите блок:

```
=== Создана учётная запись администратора хаба ===
  логин:  admin
  пароль: <строка>
```

Он больше нигде не отображается — сохраните пароль. Логин — по адресу,
который вы опубликовали (`http://127.0.0.1:8077` без Docker,
`http://127.0.0.1:8443` в примере с Docker).

## 4. Добавить хост

На странице «Хосты» после входа заполните форму:

* **Имя** — как хост будет называться в интерфейсе, произвольная метка.
* **Адрес** — IP или DNS-имя.
* **SSH-порт** — обычно 22.
* **SSH-пользователь** — `root`, либо обычный пользователь с `sudo` без
  пароля (`NOPASSWD`) — так по умолчанию настроены типовые образы VPS
  (`ubuntu`, `debian`, `admin` и т.п. с cloud-init). Установка сама
  добавляет `sudo -n` к командам, которым нужны права записи в
  `/usr/local/bin` и `/etc/systemd/system`, когда пользователь не root; при
  этом `sudo`, требующий пароль, сразу даёт понятную ошибку, а не зависает.
* **Способ входа**:
  * **хаб сгенерирует ключ** (по умолчанию, рекомендуется) — ничего
    вставлять не нужно. После сохранения хаб покажет публичный ключ —
    добавьте эту строку в `~/.ssh/authorized_keys` на самом хосте (у
    указанного пользователя), и только потом нажимайте «установить».
    Приватная половина ключа генерируется хабом и никогда никуда не
    передаётся — в отличие от способов ниже, вставлять её не нужно.
    Публичный ключ можно посмотреть повторно в любой момент кнопкой
    «публичный ключ» в таблице хостов (например, если хост пересоздали).
  * **свой приватный ключ** — вставляете содержимое существующего файла
    (`id_rsa`/`id_ed25519`, **не** `.pub`) в формате PEM; его публичная
    половина должна уже быть в `authorized_keys` на хосте.
  * **пароль** — обычный пароль пользователя по SSH.
* **Включить веб-терминал на хосте** — выключено по умолчанию. При
  включении хаб передаёт хосту `NKT_TERMINAL_ENABLED=true` при следующей
  установке/обновлении — на самом хосте это открывает полноценный
  root-shell в браузере (раздел «Терминал»). Правка `nkt.env` на хосте
  вручную для этого не годится: `stageFiles` перезаливает этот файл при
  **каждой** установке/обновлении, так что ручная правка потеряется при
  следующем нажатии «обновить» — переключатель в форме хоста хранится в
  базе самого хаба и переживает это.

После «Добавить хост» нажмите «установить» в таблице. Откроется окно с
пошаговым логом:

1. подключение по SSH, определение архитектуры;
2. сборка (или взятие из кэша) бинарника `nkt` под неё;
3. заливка бинарника, systemd-юнита и `nkt.env` по SFTP;
4. `systemctl daemon-reload && systemctl enable netknownsthat && systemctl restart netknownsthat`
   — `restart`, не `enable --now`: тот не перезапускает уже запущенный
   сервис, и на «обновить»/«переустановить» уже работающего хоста новые
   бинарник/`nkt.env` легли бы на диск, а сам процесс продолжил бы
   работать со старым окружением до следующего вмешательства;
5. проверка `/health` и вход под сохранённой учётной записью администратора
   хоста — эта учётная запись дальше используется хабом, вручную
   логиниться на хосте не нужно. Если вход не проходит, потому что на
   хосте уже была учётная запись с другим паролем (например, от прошлой
   независимой попытки установки) — хаб сам сбрасывает пароль на хосте
   командой `nkt passwd` по тому же SSH-соединению и логинится заново;
   вручную ничего чистить не нужно.

Пока установка идёт, рядом с кнопкой появляется «отменить» — она
по-настоящему прерывает текущий шаг (разрывает SSH-соединение, если он
завис на нём), а не просто прячет окно. Если хаб перезапустили прямо во
время установки — при следующем запуске он сам находит зависшие на статусе
«установка» хосты и переводит их в «ошибка», так что кнопки снова
кликабельны без ручного вмешательства.

Когда статус хоста стал «подключён» — нажмите «открыть»: дальше это тот же
дашборд, что и у обычного `nkt`, только сверху добавляется узкая панель
хаба — какой хост открыт и кнопка «к списку хостов», чтобы вернуться.

Закрыли окно с логом установки, а посмотреть его снова нужно — кнопка
«журнал установки» в таблице (появляется после первой попытки) открывает
его заново: и для уже завершённой установки, и для той, что ещё идёт.

Когда версия `nkt` на хосте отличается от версии самого хаба (например,
хаб обновили, а хост ставился раньше) — в столбце «Версия nkt» появляется
подсказка «на хабе: …», а кнопка вместо «переустановить» становится
«обновить» и подсвечивается. Делает она то же самое (заново собирает и
заливает бинарник под архитектуру хоста — под новую версию кэш строится
заново, старый не переиспользуется), просто явно показывает, что есть что
обновлять.

Столбец **«Sudo»** показывает, что реально обнаружила последняя установка
или обновление для SSH-пользователя, не являющегося `root`: «без пароля»
(NOPASSWD подтверждён — заливка файлов и systemd-команды проходят), «нужен
пароль» (`sudo -n` отказал — раздел «Диагностика» ниже) или «неизвестно»
(установок ещё не было, либо «изменить» поменяло пользователя/адрес и
прежний статус больше не гарантирован). Ничего не проверяется отдельным
запросом — статус берётся из того, что и так уже происходит при установке.

Если статус «без пароля» — рядом появляется кнопка **«снять NOPASSWD»**.
Она удаляет ровно тот файл `/etc/sudoers.d/nkt-hub`, который раздел 4 просит
создать вручную — сознательный шаг для тех, кто хочет убрать постоянный
NOPASSWD-доступ после того, как хост настроен и обновлять его больше не
планируется. После этого хабу снова понадобится sudo (или `root` как
SSH-пользователь), чтобы что-либо ставить или обновлять на этом хосте.

Кнопка **«изменить»** в таблице позволяет поправить имя/адрес/порт/
пользователя в любой момент, не трогая сохранённый секрет — поле секрета в
форме редактирования необязательное, пустое значение оставляет прежний
пароль/ключ как есть. Там же можно сменить способ входа, в том числе
перевести хост на «хаб сгенерирует ключ» (например, вместо ранее введённого
пароля) — это заменит сохранённый секрет новым сгенерированным ключом и
покажет его публичную половину для добавления на хост.

Кнопки **«запустить все»**/**«остановить все»** в шапке страницы —
`systemctl start`/`stop netknownsthat` по SSH сразу на всех установленных
хостах (то же самое, что кнопки «запустить»/«остановить» у отдельного
хоста, только пачкой, с одним подтверждением и сводкой ошибок в конце).
Это не переустановка — бинарник и `nkt.env` не трогаются, только
состояние процесса; после «остановить» хост просто перестаёт отвечать на
периодический опрос хаба и показывается как недоступный.

Кнопки **«экспорт»**/**«импорт»** сохраняют/загружают список хостов
целиком, включая зашифрованные SSH- и admin-секреты — для бэкапа или
переноса хаба на новую машину. Секреты расшифруются только на хабе с тем
же `NKT_HUB_MASTER_KEY`, которым они были зашифрованы при экспорте; на
хабе с другим ключом хосты импортируются, но останутся недоступны, пока
секрет не ввести заново (кнопка «изменить»). Импорт **дописывает** хосты
к уже существующим — не заменяет список и не проверяет дубликаты по
имени/адресу, так что повторный импорт того же файла создаст вторые
копии тех же хостов.

Кнопка **«экспорт с ключом»** — то же самое, но дополнительно кладёт в
файл сам ключ шифрования хаба. Хаб-получатель на импорте расшифровывает
секреты этим встроенным ключом и сразу перешифровывает их своим
собственным — переносить `NKT_HUB_MASTER_KEY` отдельно не нужно, и после
импорта совпадение ключей у двух хабов больше ни для чего не требуется.
Пока ключ в файле, самого файла достаточно, чтобы расшифровать все
секреты всех хостов — обращайтесь с ним как с файлом паролей и удалите
после того, как импортируете.

## 5. Настройка (переменные окружения)

Без Docker — в `/etc/netknownsthat/hub.env` (из `deploy/hub.env.example`,
устанавливает `hub-install`). Через Docker — в `deploy/docker-compose.hub.yml`
(секция `environment`) или файлом `.env` рядом с ним.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NKT_MODE` | `hub` | Не менять — это то, что включает режим хаба. |
| `NKT_ADDR` | `127.0.0.1:8077` без Docker, `0.0.0.0:8077` в примере с Docker | На чём слушает хаб. Без Docker — как у обычного `nkt`, только через reverse proxy наружу; в контейнере привязка к `0.0.0.0` нужна, чтобы сработал проброс порта. |
| `NKT_DATA_DIR` | `/var/lib/netknownsthat-hub` без Docker, `/var/lib/netknownsthat` в Docker-томе | Каталог с базой, кэшем бинарников и ключом шифрования. |
| `NKT_HUB_SOURCE_ROOT` | рабочий каталог при старте | Путь к чекауту исходников — оттуда кросс-компилируются бинарники для новых хостов. Без Docker задайте явно, если репозиторий не там, откуда запущен юнит. |
| `NKT_HUB_GO_BIN` | `go` (ищется в `PATH`) | Каким `go` кросс-компилировать бинарники для новых хостов. Если по этому пути ничего нет или он не запускается — хаб сам скачивает подходящий Go с go.dev в `NKT_DATA_DIR/go-toolchain` и дальше использует его; настраивать вручную нужно, только если хотите явно закрепить конкретный уже установленный `go` вместо автоустановки. |
| `NKT_HUB_MASTER_KEY` | *(пусто → генерируется сам)* | Ключ шифрования (AES-256, base64) для SSH-секретов хостов. Оставьте пустым для автогенерации в `NKT_DATA_DIR/hub.key`, либо задайте явно (`openssl rand -base64 32`), если хотите управлять им отдельно от тома/каталога данных. |
| `NKT_HUB_FINDINGS_POLL_INTERVAL` | `60s` | Как часто хаб в фоне опрашивает `/api/overview` каждого подключённого («online») хоста, чтобы держать под рукой актуальные счётчики находок и признак доступности — независимо от того, открыта ли веб-морда. Опрос идёт через уже установленное SSH-соединение с хостом, ничего дополнительно наружу не стучится. |
| `NKT_BOOTSTRAP_ADMIN_USER` | `admin` | Логин администратора хаба. |
| `NKT_BOOTSTRAP_ADMIN_PASSWORD` | *(пусто → генерируется сам)* | Пароль администратора хаба — как выше, оставьте пустым, если не нужен конкретный. |

## 6. Диагностика

* **Хост навсегда завис на статусе «установка», кнопки задизейблены** —
  нажмите «отменить»: она рядом с кнопкой установки, пока статус
  «установка». Прерывает реально выполняющийся шаг, а не только прячет
  окно с логом. Если это произошло из-за перезапуска самого хаба —
  чинится само при следующем старте, руками ничего делать не нужно.
* **Не пускает по SSH при добавлении хоста** — проверьте вручную:
  `ssh -p <порт> <пользователь>@<адрес>` с теми же данными, что вводили в
  форму. Хаб использует ровно тот же логин/пароль/ключ. При способе входа
  «хаб сгенерирует ключ» самая частая причина — публичный ключ ещё не
  добавлен в `authorized_keys` на хосте (см. раздел 4) или добавлен не
  тому пользователю/не в тот файл.
* **Ошибка при вставке своего ключа** («не похоже на PEM», «формат
  PuTTY», «защищён паролем») — форма проверяет ключ сразу при вводе,
  раньше, чем пробует подключиться. Сообщение называет конкретную причину:
  вставлен `.pub` вместо приватного ключа, файл в формате PuTTY `.ppk`
  (нужен экспорт через puttygen в OpenSSH-формат), или ключ защищён
  паролем (сейчас не поддерживается — снимите пароль `ssh-keygen -p`).
  Если ключ не свой, а нужно просто подключиться — переключитесь на «хаб
  сгенерирует ключ», проблема с форматом тогда не возникает вовсе.
* **«Заливаю бинарник… Ошибка: заливка бинарника: permission denied»** —
  указанный SSH-пользователь не root и не может писать в целевые пути
  напрямую по SFTP; это ожидаемо, установка сама переходит на `sudo`. Если
  ошибка идёт с шага «Устанавливаю файлы…» и упоминает пароль или sudoers —
  у пользователя нет `NOPASSWD` sudo на хосте; текст самой ошибки уже
  содержит готовые команды для этого конкретного пользователя, выполните их
  на самом хосте:
  ```
  echo 'ИМЯ ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/nkt-hub
  sudo chmod 0440 /etc/sudoers.d/nkt-hub
  ```
  либо укажите `root` как SSH-пользователя вместо этого.
* **Настроенный `go` не запускается (например, `go` — snap-пакет, а
  systemd-юнит хаба его блокирует своей же изоляцией:
  `NoNewPrivileges`/`RestrictNamespaces` не дают `snap-confine` собрать
  окружение)** — с этим ничего специально делать не нужно: хаб сам
  обнаруживает, что настроенный `go` не работает, и качает свой,
  изолированный от системного, в `NKT_DATA_DIR/go-toolchain` — в логе
  установки будет строка «go (…) недоступен — устанавливаю собственный Go
  для хаба…». Единственное условие — исходящий доступ к go.dev; если его
  нет (изолированная сеть), поставьте Go вручную и укажите путь в
  `NKT_HUB_GO_BIN` явно.
* **«исходники nkt не найдены (нет go.mod …)»** — хаб запущен не из
  каталога с исходниками, а `NKT_HUB_SOURCE_ROOT` не задан (по умолчанию
  он равен рабочему каталогу процесса). Хаб сам пробует каталог своего
  бинарника и его родителей, поэтому запуск `./nkt hub` из любого места
  внутри клона репозитория работает без настройки; если бинарник вынесен
  наружу (например, в `/usr/local/bin`) — задайте `NKT_HUB_SOURCE_ROOT`
  абсолютным путём к клону в `/etc/netknownsthat/hub.env` и перезапустите
  `netknownsthat-hub`.
* **«неподдерживаемая архитектура»** — целевой хост не amd64/arm64/Linux;
  сейчас не поддерживается.
* **«установка netknownsthat.service … Job for netknownsthat.service
  failed»** — сам systemd на хосте принял юнит, но процесс не запустился.
  Хаб сразу же вытаскивает хвост `journalctl -u netknownsthat` с хоста по
  тому же SSH и показывает его в этом же сообщении после строки «журнал
  сервиса на хосте» — причина (занятый порт, битый env-файл и т.п.) видна
  там, отдельно ходить на хост не нужно.
  Частый случай — `status=226/NAMESPACE` и `Failed to set up mount
  namespacing: /run/systemd/unit-root/etc/haproxy: No such file or
  directory`: на хосте установлен только nginx или только haproxy (либо
  ни одного), а юнит требовал оба каталога через `ReadWritePaths`. С 2026
  оба помечены необязательными (`-/etc/nginx`, `-/etc/haproxy`) — если
  ошибка всё ещё встречается, обновите хаб (юнит перезаливается при
  каждой установке/обновлении хоста, отдельного шага не нужно).
* **Установка зависла на «Жду, пока сервис ответит…»** — на хосте нет
  systemd, либо порт 8077 внутри хоста уже занят чем-то ещё; проверьте
  `systemctl status netknownsthat` на самом хосте по отдельному SSH.
* **Хост показывает «ошибка»** — текст ошибки указан прямо в таблице
  хостов; повторная «переустановить» безопасна — файлы просто перезальются.
* **Забыли пароль администратора хаба** — самый простой способ: кнопка
  «Сменить пароль» внутри интерфейса, если ещё залогинены хоть где-то. Если
  нет — сброс прямо с машины, где крутится хаб:
  ```bash
  # через Docker — прямо на ходу, второй процесс в том же контейнере:
  docker compose -f deploy/docker-compose.hub.yml exec hub nkt passwd -random

  # без Docker — юнит держит базу открытой, так что сначала остановите его
  # (сброс пароля не трогает ничего, что нужно ему во время работы):
  sudo systemctl stop netknownsthat-hub
  sudo env NKT_MODE=hub NKT_DATA_DIR=/var/lib/netknownsthat-hub nkt passwd -random
  sudo systemctl start netknownsthat-hub
  ```

## 7. Остановить / удалить

```bash
# без Docker
sudo systemctl disable --now netknownsthat-hub

# через Docker
docker compose -f deploy/docker-compose.hub.yml down      # остановить, том остаётся
docker compose -f deploy/docker-compose.hub.yml down -v   # остановить и стереть данные хаба
# или: make hub-down
```

Остановка/удаление хаба не трогает уже установленный `nkt` на управляемых
хостах — он останется работать как обычный systemd-сервис; убрать его
оттуда нужно вручную (`systemctl disable --now netknownsthat` на самом
хосте).
